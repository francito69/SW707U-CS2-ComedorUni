## ADR-AUTH-001 — Mecanismo de autenticación: parsing de HTML del ORCE enviado por el cliente

**Categoría:** Elección de Tecnología

### Contexto

El sistema debe verificar que quien intenta acceder es un estudiante activo de la UNI con al menos 12 créditos matriculados en el ciclo vigente. La UNI no expone APIs públicas; la única fuente de datos es el portal web ORCE (INTRANET UNI). Se debe decidir cómo obtener y verificar esta información.

### Alternativas

1. **OAuth 2.0 con Google Workspace institucional.** Requiere coordinación con el área de TI de la UNI para federar identidades. No proporciona datos académicos (créditos, matrícula). Inviable sin acuerdo institucional.

2. **Scraping server-side del INTRANET UNI.** El servidor haría login en el ORCE por cada estudiante. Requiere gestionar sesiones, cookies y tokens CSRF del portal. Expone credenciales del estudiante al servidor. Alta fragilidad ante cambios de estructura del portal.

3. **El cliente obtiene el HTML del ORCE y lo envía al servidor para parsing.** El estudiante ya está autenticado en el ORCE desde su dispositivo. La app captura el HTML de las páginas relevantes (home, cursos, datos personales) y lo envía al backend. El servidor solo parsea — no gestiona sesiones ni credenciales del portal. Separación clara de responsabilidades.

### Criterios de Elección

- **Viabilidad sin coordinación institucional.**
- **Seguridad:** el servidor no almacena ni gestiona credenciales del ORCE.
- **Simplicidad** del backend: parsing de HTML estándar.

### Decisión

El cliente (app React Native) envía los HTMLs relevantes del ORCE al endpoint `POST /parse-data`. El backend parsea los datos del estudiante (código, nombre, créditos, foto) y crea la sesión.

### Sustento

El modelo cliente→parser desacopla completamente el backend de la sesión del portal ORCE. El estudiante se autentica en el portal con sus propias credenciales; el servidor nunca las ve. El trade-off aceptado es que el cliente puede manipular el HTML enviado; se mitiga porque los datos parsados (código, email) se cruzan con lo que ya existe en la tabla `estudiantes` y el acceso por créditos se verifica sobre el HTML recibido.

## ADR-AUTH-002 — El cliente envía el HTML del ORCE; el servidor no hace scraping directamente

**Categoría:** Asignación de Responsabilidades

### Contexto

Dado que se usa parsing de HTML del ORCE (ADR-AUTH-001), hay que decidir quién hace la solicitud HTTP al portal: el servidor o el cliente.

### Alternativas

1. **El servidor hace scraping del ORCE.** El backend recibe las credenciales del estudiante y hace login en el ORCE por él. Requiere gestionar sesiones de portal por cada usuario concurrente. Expone credenciales al servidor.

2. **El cliente realiza las solicitudes al ORCE y envía el HTML resultante al servidor.** El estudiante ya está logueado en el ORCE desde su sesión de navegador/app. La app extrae el HTML de las páginas que necesita el backend y lo envía en el body de `POST /parse-data`. El backend solo parsea texto estático.

### Criterios de Elección

- **Privacidad:** el servidor no debe recibir contraseñas del ORCE.
- **Simplicidad del backend:** el servidor hace parsing, no scraping.
- **Responsabilidad** clara entre capas.

### Decisión

La responsabilidad de obtener el HTML del ORCE recae en el cliente. El servidor recibe `home_html`, `cursos_html` y `datos_html` como strings y los parsea mediante `parse_student_data()`.

### Sustento

La asignación es natural: el cliente ya tiene la sesión abierta en el ORCE; el servidor tiene la lógica de parsing. El endpoint `POST /parse-data` recibe tres campos HTML y devuelve los datos estructurados del estudiante más el `sid` de sesión. El trade-off aceptado es que el cliente controla qué HTML envía; esto es asumible porque la información resultante (código de estudiante, créditos) es la que determina el acceso, y un estudiante que manipule su propio HTML para simular más créditos solo se afecta a sí mismo.

## ADR-AUTH-003 — Gestión de sesiones: UUID sid almacenado en Redis

**Categoría:** Modelo de Datos

### Contexto

Una vez que el backend parsea los datos del ORCE y verifica los créditos, debe mantener la identidad del estudiante para solicitudes subsecuentes (verificación biométrica, ingreso a cola). Se debe decidir el mecanismo de sesión.

### Alternativas

1. **JWT (JSON Web Token) almacenado en el cliente.** Sin estado en servidor. La invalidación antes del vencimiento requiere lista negra en Redis. El payload puede contener datos sensibles si no se cifra. Requiere rotación de secretos.

2. **UUID sid almacenado en Redis como clave de sesión con estado completo.** El backend genera un UUID aleatorio (`uuid4`), lo almacena como clave en Redis con el payload de sesión (código, nombre, email, créditos, foto_base64) y lo devuelve al cliente. El cliente adjunta el `sid` en cada solicitud posterior. Invalidación inmediata: borrar la clave en Redis. El estado completo está en el servidor, no expuesto al cliente.

3. **Cookie de sesión con almacenamiento en PostgreSQL.** Persistencia garantizada. Consulta a DB en cada request autenticado. Mayor latencia que Redis para el flujo de alta frecuencia del comedor.

### Criterios de Elección

- **Invalidación inmediata** al hacer logout o detectar anomalías.
- **Latencia de verificación** en cada request autenticado.
- **Simplicidad** de implementación.

### Decisión

Se usa UUID `sid` generado con `uuid.uuid4()`, almacenado como clave en Redis. El cliente lo envía en el body o como query param. El backend verifica con `get_session(sid)`.

### Sustento

Redis permite verificar la sesión en O(1) sin tocar PostgreSQL en cada request. La foto biométrica de referencia se almacena en la misma clave Redis, disponible inmediatamente para `verify-biometric` sin consulta adicional. Invalidar la sesión es `redis_client.delete(sid)` — instantáneo. El trade-off aceptado es que Redis es un punto único de fallo para las sesiones; se mitiga porque Redis también gestiona la cola virtual y ya tiene alta disponibilidad en la infraestructura del proyecto.

## ADR-AUTH-004 — Foto biométrica almacenada en sesión Redis (efímera, no persistida en DB)

**Categoría:** Asignación de Responsabilidades

### Contexto

El ORCE contiene una foto oficial del estudiante. Al parsear el HTML, se extrae la foto en base64. Esta foto se usa en `POST /verify-biometric` para comparar con la foto tomada en el momento del login. Se debe decidir dónde y por cuánto tiempo almacenarla.

### Alternativas

1. **Persistir la foto en PostgreSQL (columna BYTEA o referencia a objeto).** Disponible indefinidamente para validación en comedor. Aumenta el tamaño de la tabla `estudiantes`. Gestionar privacidad de datos biométricos persistentes.

2. **Almacenar la foto en MinIO o S3-compatible.** Separar binarios de la base de datos relacional. Añade una dependencia operativa adicional al stack. Requiere URLs pre-firmadas para acceso controlado.

3. **Almacenar `foto_base64` solo en la sesión Redis con el mismo TTL de la sesión.** La foto solo existe mientras la sesión está activa (tiempo de login y verificación biométrica). No se almacena en ningún sistema persistente. Cuando el usuario hace logout o expira la sesión, la foto desaparece junto con ella.

### Criterios de Elección

- **Privacidad:** minimizar la persistencia de datos biométricos.
- **Disponibilidad** para la verificación biométrica durante el flujo de login.
- **Simplicidad** sin dependencias adicionales.

### Decisión

`foto_base64` se almacena exclusivamente en la clave Redis de la sesión (`create_session(..., foto_base64=result["foto_base64"])`). No se persiste en PostgreSQL ni en ningún almacenamiento de objetos.

### Sustento

El único uso de la foto es en `POST /verify-biometric`, que ocurre inmediatamente después de `POST /parse-data` durante el flujo de login. No existe ningún caso de uso que requiera la foto biométrica fuera de ese flujo. Almacenarla solo en Redis con TTL de sesión sigue el principio de mínimo privilegio: la foto existe el tiempo justo que es necesaria. El trade-off aceptado es que si Redis se reinicia entre `/parse-data` y `/verify-biometric`, el estudiante debe repetir el login; esto es asumible porque ambos endpoints se invocan en el mismo flujo de la app.

## ADR-AUTH-005 — Resolución de configuración de infraestructura en tiempo de despliegue

**Categoría:** Tiempo de Enlace

### Contexto

El módulo de autenticación necesita las credenciales de conexión a Redis (`REDIS_HOST`, `REDIS_PORT`) y a PostgreSQL (`DATABASE_HOST`, `POSTGRES_USER`, etc.). Estas configuraciones no deben quedar en el código fuente.

### Alternativas

1. **Hardcodeadas en el código fuente.** Riesgo de exposición en el repositorio. Cambiar un parámetro requiere modificar código y redesplegar.

2. **Variables de entorno inyectadas en el contenedor en tiempo de despliegue.** El archivo `.env` centraliza las credenciales y se excluye del repositorio con `.gitignore`. Los módulos leen las variables con `os.getenv()`. Estándar de la industria (metodología 12-factor app).

3. **Archivo de configuración YAML versionado.** Las credenciales quedan en el repositorio si no se excluyen cuidadosamente. Mayor complejidad de lectura que variables de entorno.

### Criterios de Elección

- **Seguridad:** las credenciales no deben estar en el repositorio.
- **Simplicidad** de implementación.
- **Facilidad de actualización** sin recompilar.

### Decisión

Las credenciales de infraestructura se resuelven mediante variables de entorno inyectadas en el contenedor. El archivo `.env` se excluye del repositorio con `.gitignore`.

### Sustento

El estándar de la industria para aplicaciones contenerizadas. Redis y PostgreSQL se configuran con una sola variable de host porque ambos se despliegan como contenedores en la misma red Docker (`comedor-network`). El trade-off aceptado es que las variables de entorno no ofrecen rotación automática de secretos; asumible en el contexto académico.

## ADR-AUTH-006 — Verificación de acceso por créditos en memoria, dato no persistido

**Categoría:** Asignación de Responsabilidades

### Contexto

El ORCE proporciona la cantidad de créditos matriculados del estudiante en el ciclo vigente. La única función de este dato en el sistema es verificar si el estudiante puede acceder al dashboard de la cola (`créditos >= 12`). Se debe decidir qué hace el sistema con ese dato.

### Alternativas

1. **Persistir los créditos en la tabla `estudiantes`.** El dato queda en DB y se puede consultar sin hacer parsing del HTML. Se desactualiza entre ciclos académicos; requiere invalidación periódica. El sistema almacena datos que pertenecen al sistema académico de la UNI.

2. **Cachear el booleano `tiene_acceso` en Redis con TTL de 24 horas.** Evita re-parsear el HTML en cada login del día. Introduce ventana de inconsistencia si el estudiante pierde créditos en el ciclo actual.

3. **Verificación en memoria por cada login; dato no persistido.** El valor numérico de créditos se evalúa en tiempo de ejecución (`creditos_llevados >= 12`) y se descarta. Solo se persiste la decisión implícita de crear la sesión Redis (si el acceso fue concedido, hay sesión; si no, no hay sesión).

### Criterios de Elección

- **Privacidad y mínimo privilegio:** no almacenar datos del sistema académico de la UNI.
- **Correctitud:** la verificación debe reflejar el estado actual del ciclo vigente.
- **Simplicidad:** no agregar estructuras para un dato efímero.

### Decisión

Los créditos se usan de forma **estrictamente efímera**: se parsean del HTML recibido, se evalúa `creditos_llevados >= 12` en memoria y el valor numérico se descarta. Se almacena en la sesión Redis únicamente para poder mostrarlo en la UI (`GET /me`), no para control de acceso posterior.

### Sustento

El sistema de comedor no es propietario del dato de créditos; pertenece al sistema académico de la UNI. Almacenarlo duplicaría información con riesgo de desactualización. El principio de mínimo privilegio exige no persistir lo que no es necesario para la función del sistema. El trade-off aceptado es que cada login realiza el parsing del HTML; con el volumen universitario esperado (cientos de logins al día), esto no representa un cuello de botella.

## ADR-AUTH-007 — Modelo de datos del perfil del estudiante: tabla `estudiantes`

**Categoría:** Modelo de Datos

### Contexto

Al parsear el HTML del ORCE, el sistema obtiene: código de estudiante, nombres, apellidos y email institucional. Estos datos deben persistirse en PostgreSQL para que los módulos de cola virtual (M2/M3) puedan referenciar al estudiante por clave foránea.

### Alternativas

1. **Usar el código ORCE directamente como clave primaria en todas las tablas.** Simple; sin tabla de ID interno. El formato del código es `20XXXXXXL` (predecible pero de longitud fija). Dependencia directa del formato del código externo en todas las claves foráneas.

2. **Tabla `estudiantes` con ID interno (`SERIAL`) y código ORCE como campo único.** El ID interno desacopla el modelo de datos del identificador externo. El `codigo` queda como índice único para búsquedas eficientes. Las demás tablas referencian `estudiante_id` (INTEGER), más eficiente que un VARCHAR como FK.

### Criterios de Elección

- **Eficiencia de joins** en tablas de cola y seguimiento.
- **Desacoplamiento** del formato del código externo.
- **Extensibilidad** para agregar atributos del sistema.

### Decisión

Se crea la tabla `estudiantes` con `id SERIAL PRIMARY KEY`, `codigo VARCHAR(20) UNIQUE`, `nombres`, `apellido_paterno`, `apellido_materno`, `email`, `push_token` y `created_at`. Las tablas de cola (`turnos`, `cola_virtual`) y seguimiento (`historial_asistencia`) referencian `estudiante_id`.

### Sustento

El ID interno como clave primaria es el estándar para entidades que se referencian desde múltiples tablas. El `codigo` tiene un índice único que permite búsquedas O(log n) por código ORCE al crear o actualizar el perfil. La columna `push_token` se incluye en esta tabla porque el push token pertenece al estudiante y es necesario para M4. El upsert se realiza con `ON CONFLICT (codigo) DO UPDATE` para manejar re-logins sin duplicar filas.

## ADR-AUTH-008 — Unicidad de cuenta por código ORCE

**Categoría:** Asignación de Responsabilidades

### Contexto

El sistema debe garantizar que cada estudiante real tenga a lo sumo un perfil en la tabla `estudiantes`. El identificador natural del estudiante es su código ORCE (`20XXXXXXL`), asignado por la UNI.

### Alternativas

1. **Unicidad solo a nivel de aplicación (validación antes de INSERT).** Riesgo de condición de carrera en logins concurrentes del mismo estudiante desde dos dispositivos.

2. **Restricción `UNIQUE` sobre el campo `codigo` en PostgreSQL.** La base de datos garantiza unicidad con una restricción DDL. Cualquier intento de insertar un código duplicado falla con una excepción que la aplicación maneja con `ON CONFLICT`.

3. **Unicidad por email institucional.** El email `codigoXXXXXX@uni.pe` es derivable del código y también único. Redundante con la unicidad por código.

### Criterios de Elección

- **Garantía de unicidad** ante accesos concurrentes.
- **Consistencia** con el identificador natural del dominio.

### Decisión

La columna `codigo` tiene restricción `UNIQUE` en PostgreSQL. El upsert en `upsert_estudiante()` usa `ON CONFLICT (codigo) DO UPDATE SET` para actualizar datos sin duplicar perfiles al hacer re-login.

### Sustento

Delegar la garantía de unicidad al motor de base de datos elimina condiciones de carrera que existirían con validación solo en aplicación. `ON CONFLICT DO UPDATE` maneja re-logins (el estudiante vuelve a parsear el ORCE y puede haber actualizado su email o nombre) de forma atómica. El trade-off aceptado es que el código ORCE es el único identificador de control de unicidad; si la UNI reasignara un código (extremadamente improbable), generaría una colisión.

## ADR-AUTH-009 — Despliegue del módulo de autenticación: FastAPI modular en monolito

**Categoría:** Mapeo entre Elementos Arquitectónicos

### Contexto

El módulo de autenticación es transversal: todos los módulos que reciben un `sid` lo verifican contra Redis. Se debe decidir si se despliega como microservicio independiente o dentro del monolito modular.

### Alternativas

1. **Microservicio de autenticación independiente.** Escalable independientemente. Cada verificación de sesión desde otros módulos requiere una llamada HTTP inter-servicio. Latencia adicional en el camino crítico de la cola.

2. **Módulo de autenticación dentro del monolito FastAPI.** Un único proceso. La verificación de `sid` es una llamada a función interna; no hay latencia de red. Redis es accesible directamente desde cualquier módulo del mismo proceso.

### Criterios de Elección

- **Latencia de verificación de sesión** en cada request autenticado.
- **Complejidad operativa** acorde al equipo académico.

### Decisión

El módulo de autenticación se despliega como router FastAPI dentro del monolito modular (`src/modules/auth/router.py`), montado bajo el prefijo `/api/v1/auth`.

### Sustento

Al estar en el mismo proceso, `get_session(sid)` es una llamada directa a Redis sin overhead de red entre servicios. El volumen universitario no justifica la complejidad operativa de un microservicio independiente. El trade-off aceptado es que escalar la autenticación requiere escalar todo el monolito; asumible dado el volumen esperado.

## ADR-AUTH-010 — Coordinación entre autenticación y cola virtual: verificación de sid en Redis

**Categoría:** Modelo de Coordinación

### Contexto

El módulo de cola (M2/M3) debe verificar que cada solicitud de encolamiento proviene de un estudiante con sesión válida. La verificación debe ser de baja latencia porque ocurre en el camino crítico de cada operación de cola.

### Alternativas

1. **M2/M3 llaman a un endpoint HTTP del módulo de autenticación para verificar el sid.** Latencia de red incluso si los módulos están en el mismo proceso (pasaría por el routing HTTP). Innecesariamente complejo.

2. **M2/M3 llaman directamente a `get_session(sid)` del módulo de autenticación.** Como los módulos están en el mismo proceso, es una llamada a función interna. Redis responde en < 1 ms. Si la sesión no existe o expiró, se lanza `HTTPException 401`.

### Criterios de Elección

- **Latencia** de verificación en el camino crítico de encolamiento.
- **Simplicidad** de coordinación.

### Decisión

Los módulos M2 y M3 importan y llaman directamente a `get_session(sid)` desde `src/modules/auth/redis_store.py`. La verificación es síncrona e inmediata.

### Sustento

Al estar en el mismo proceso FastAPI, la importación directa es la coordinación de menor overhead posible. No existe un mecanismo de cache intermedio porque Redis ya opera como cache de la sesión. El trade-off aceptado es el acoplamiento por importación entre módulos; se mitiga porque `redis_store.py` es una interfaz estable que no cambiará.

## ADR-AUTH-011 — Comparación biométrica local con deepface

**Categoría:** Elección de Tecnología

### Contexto

El endpoint `POST /verify-biometric` recibe una foto tomada en el momento del login y la compara con la foto del ORCE almacenada en Redis. Se debe decidir cómo realizar la comparación facial.

### Alternativas

1. **API de reconocimiento facial externa (AWS Rekognition, Azure Face API).** Alta precisión y sin gestión de modelos. Introduce latencia de red y costo por llamada. Los datos biométricos salen del servidor.

2. **Librería local de comparación facial (deepface, face_recognition).** El procesamiento ocurre en el mismo proceso backend. Sin latencia de red. Los datos biométricos no salen del servidor. Requiere más RAM/CPU en el servidor.

3. **Embedding facial almacenado en DB; comparación por distancia vectorial.** Requiere persistir el embedding, lo cual contradice ADR-AUTH-004 (foto efímera en Redis).

### Criterios de Elección

- **Privacidad:** los datos biométricos no deben salir del servidor.
- **Latencia** aceptable en el flujo de login.
- **Costo** cero de llamadas externas.

### Decisión

Se usa `compare_faces()` implementado con librería local (deepface). La función recibe las dos imágenes en base64 y devuelve `(verified: bool, distance: float)`.

### Sustento

El procesamiento local garantiza que los datos biométricos no salen del perímetro del servidor. La librería deepface soporta múltiples backends de detección y puede calibrarse con un umbral de distancia. El trade-off aceptado es el consumo de CPU/RAM en el servidor; en un entorno académico con decenas de verificaciones concurrentes (no miles), esto es manejable.

## ADR-AUTH-012 — Patrón Singleton para la conexión Redis del módulo de autenticación

**Categoría:** Elección de Tecnología

### Contexto

El módulo de autenticación accede a Redis en cada operación de sesión (`create_session`, `get_session`, `delete_session`). Si cada llamada creara una nueva conexión TCP a Redis, el overhead de establecimiento de conexión dominaría la latencia de cada operación.

### Alternativas

1. **Crear una nueva conexión Redis por cada operación.** Sin estado compartido. El overhead de TCP handshake en cada operación es inaceptable bajo concurrencia.

2. **Singleton: una única instancia de `redis.Redis` reutilizada globalmente.** La función `get_redis()` retorna siempre la misma instancia. La librería `redis-py` maneja el pool de conexiones internamente. Un único punto de inicialización con la configuración de host/puerto.

### Criterios de Elección

- **Rendimiento:** eliminar overhead de conexión por operación.
- **Simplicidad** de implementación.

### Decisión

Se implementa el patrón Singleton mediante la función `get_redis()` en `src/modules/auth/redis_store.py`. La instancia se inicializa una sola vez y se reutiliza en todas las operaciones de sesión del módulo de autenticación.

### Sustento

`redis-py` implementa connection pooling internamente cuando se reutiliza la misma instancia; cada llamada obtiene una conexión del pool sin overhead de TCP handshake. El Singleton garantiza que el pool se configure una sola vez con los parámetros correctos. El mismo patrón se aplica en M2 para el WebSocket manager (ver [11.5](../../11/11.5/11.5.md)).

## ADR-AUTH-013 — Patrón Facade en el endpoint `/parse-data`

**Categoría:** Elección de Tecnología

### Contexto

El login del estudiante involucra tres subsistemas distintos: (1) parsing del HTML del ORCE para extraer datos del estudiante, (2) upsert en PostgreSQL (`estudiantes`), (3) creación de sesión en Redis. El cliente que llama a `POST /parse-data` no debe conocer ni coordinar estos tres subsistemas.

### Alternativas

1. **El cliente llama a tres endpoints separados.** El cliente gestiona el orden y manejo de errores de tres operaciones. Aumenta la complejidad del cliente y el riesgo de estado inconsistente si el cliente falla entre llamadas.

2. **Patrón Facade: un único endpoint orquesta los tres subsistemas internamente.** `POST /parse-data` es el punto de entrada único. El router llama a `parse_student_data()`, luego a `upsert_estudiante()`, luego a `create_session()`. El cliente recibe un único `sid` y los datos del estudiante.

### Criterios de Elección

- **Simplicidad del cliente:** una sola llamada para el flujo de login.
- **Consistencia:** los tres subsistemas se coordinan en el servidor, no en el cliente.
- **Extensibilidad:** agregar subsistemas al flujo de login no cambia la interfaz del cliente.

### Decisión

El endpoint `POST /parse-data` actúa como Facade: oculta la orquestación de parsing ORCE + upsert PostgreSQL + creación de sesión Redis detrás de una única interfaz HTTP. Esta es la decisión de diseño GoF documentada en [11.1](../../11/11.1/11.1.md).

### Sustento

La Facade es el patrón apropiado cuando se quiere proporcionar una interfaz simplificada a un conjunto de subsistemas complejos. El cliente de la app React Native solo necesita saber que `POST /parse-data` con los tres HTMLs devuelve un `sid` — no necesita conocer Redis, PostgreSQL ni la lógica de parsing. El trade-off aceptado es que la Facade concentra la lógica de coordinación en un único punto; si un subsistema falla, la operación completa falla (comportamiento deseable para garantizar consistencia del estado de sesión).

## ADR-AUTH-014 — Rate limiting en endpoints de autenticación

**Categoría:** Gestión de Recursos

### Contexto

Los endpoints `POST /parse-data` y `POST /verify-biometric` son los más costosos del sistema: el primero realiza parsing de HTML y upsert en DB; el segundo ejecuta comparación facial con CPU. Sin límite de tasa, un cliente malicioso podría saturar el servidor con solicitudes de verificación biométrica.

### Alternativas

1. **Sin rate limiting; confiar en la infraestructura.** Sin implementación adicional. Vulnerable a abuso o a bugs en el cliente que generen ciclos de re-login.

2. **Rate limiting por IP en middleware de FastAPI.** Configurable por endpoint con ventana de tiempo deslizante. No requiere infraestructura adicional. Puede afectar a usuarios legítimos detrás de NAT compartido del campus.

3. **Rate limiting por sid (por sesión activa).** Una sesión solo puede llamar a `verify-biometric` N veces. Más granular que por IP. Requiere contadores en Redis.

### Criterios de Elección

- **Protección** del endpoint de comparación biométrica (costoso en CPU).
- **Impacto mínimo** en usuarios legítimos.
- **Simplicidad** de implementación.

### Decisión

Se implementa rate limiting por IP en middleware de FastAPI: máximo 10 solicitudes por IP en ventana de 5 minutos para `POST /parse-data` y `POST /verify-biometric`.

### Sustento

Un estudiante legítimo no necesita más de 2-3 intentos de login por sesión de comedor. El límite de 10 en 5 minutos es generoso para uso legítimo pero bloquea uso automatizado. La protección por IP es suficiente para el contexto universitario donde el abuso sería puntual, no distribuido. El trade-off aceptado es que solicitudes rechazadas sí consumen recursos hasta ser rechazadas por el middleware.

## ADR-NOT-001 — Canal de entrega de notificaciones: Expo Push Notifications

**Categoría:** Elección de Tecnología

### Contexto

El módulo M4 debe notificar al estudiante cuando su turno es llamado (`turno.llamado`) o cancelado (`turno.cancelado`). Los estudiantes usan la app React Native (Expo). Se debe decidir el canal de entrega de notificaciones.

### Alternativas

1. **Server-Sent Events (SSE) o WebSocket.** Requiere que la app esté en primer plano y conectada. Si el estudiante minimiza la app o bloquea la pantalla, no recibe la notificación. No funciona cuando la app está en background.

2. **Expo Push Notifications (servicio de push de Expo/FCM/APNs).** Push notifications nativas del SO: llegan aunque la app esté en background o cerrada. El estudiante ve la notificación como alerta del sistema. Expo abstrae FCM (Android) y APNs (iOS) con una única API. Requiere que el estudiante haya registrado su push token.

3. **SMTP (email).** Alta latencia (segundos a minutos). El estudiante puede no tener el correo visible en tiempo real. No apropiado para la ventana de confirmación de turno (3 minutos).

### Criterios de Elección

- **Entrega garantizada aunque la app esté en background.**
- **Latencia:** la notificación de turno debe llegar en segundos.
- **Integración** con el stack React Native/Expo existente.

### Decisión

Se usa Expo Push Notifications como canal principal. El consumer de M4 llama a `send_push(token, title, body, data)` implementado en `src/shared/push.py`.

### Sustento

La app es React Native/Expo; el push service de Expo es la integración natural y proporciona entrega en background en iOS y Android sin gestionar FCM y APNs por separado. La latencia de entrega de push es de 1-3 segundos en condiciones normales, apropiada para el tiempo límite de confirmación. El trade-off aceptado es que el servicio de push de Expo es una dependencia externa; si el servicio no está disponible, las notificaciones no se entregan (se pierde el mensaje pero RabbitMQ ya procesó el ack).

## ADR-NOT-002 — Broker de mensajería: RabbitMQ con colas durables

**Categoría:** Elección de Tecnología

### Contexto

M4 debe recibir eventos de dominio generados por M3 (cuando se llama o cancela un turno). Se debe decidir el mecanismo de transporte entre M3 (productor) y M4 (consumidor).

### Alternativas

1. **Event bus en memoria (asyncio.Queue o EventEmitter).** Sin dependencias adicionales. Los eventos se pierden si el proceso se reinicia. No permite escalar el consumidor independientemente. No garantiza entrega si M4 está momentáneamente caído.

2. **Redis Pub/Sub.** Redis ya está en el stack. Pub/Sub es fire-and-forget: si el consumidor no está suscrito en el momento de la publicación, el mensaje se pierde. Sin durabilidad.

3. **RabbitMQ con colas durables.** Los mensajes se persisten en disco. Si M4 está caído, los mensajes se acumulan en la cola y se procesan al recuperarse. Soporte para routing por tipo de evento. Dead-letter queue para mensajes no procesables. Se despliega como contenedor estándar.

### Criterios de Elección

- **Durabilidad:** las notificaciones de turno llamado no deben perderse si el consumer está caído.
- **Desacoplamiento:** M3 no debe conocer la existencia de M4.
- **Routing:** diferentes tipos de evento deben poder enrutarse a diferentes consumidores.

### Decisión

Se adopta RabbitMQ como broker. M3 publica en un exchange con routing keys por tipo de evento. M4 consume de la cola `m4.notificaciones` vinculada a los eventos `turno.llamado` y `turno.cancelado`.

### Sustento

RabbitMQ garantiza que los eventos no se pierdan si M4 está temporalmente caído, a diferencia de un event bus en memoria o Redis Pub/Sub. Las colas durables persisten en disco y sobreviven reinicios del broker. Redis Streams sería también válido y reutilizaría infraestructura existente; se elige RabbitMQ porque el equipo ya lo conoce y tiene UI de administración integrada para monitorear colas. El trade-off aceptado es RabbitMQ como dependencia adicional; se despliega como contenedor estándar.

## ADR-NOT-003 — Push token del estudiante almacenado en la tabla `estudiantes`

**Categoría:** Modelo de Datos

### Contexto

Para enviar push notifications, M4 necesita el push token Expo del dispositivo del estudiante. El token se registra cuando el estudiante instala la app. Se debe decidir dónde almacenarlo.

### Alternativas

1. **Tabla separada `push_tokens` con relación a `estudiantes`.** Permite múltiples tokens por estudiante (varios dispositivos). Mayor complejidad de consultas.

2. **Columna `push_token` en la tabla `estudiantes`.** Un token por estudiante (un dispositivo activo). Consulta directa sin join adicional. El token se actualiza en el upsert de login o en el endpoint `POST /register-push-token`.

3. **Token en Redis junto con la sesión.** Solo disponible durante la sesión activa. Si el estudiante no tiene sesión activa cuando su turno es llamado, M4 no puede enviar el push.

### Criterios de Elección

- **Disponibilidad** del token incluso cuando el estudiante no tiene sesión activa.
- **Simplicidad** de consulta desde M4.

### Decisión

El push token se almacena en la columna `push_token` de la tabla `estudiantes`. El consumer de M4 recibe el token directamente en el payload del evento RabbitMQ (publicado por M3 con el token al registrar el turno).

### Sustento

Al incluir el push token en el payload del evento RabbitMQ, M4 no necesita consultar ninguna base de datos para obtenerlo — el token llega con el mensaje. Esto hace al consumer completamente stateless respecto a la DB. El token en `estudiantes` es la fuente de verdad; se replica en el payload del evento en el momento de publicación para eficiencia. El trade-off aceptado es que un token en el evento puede estar desactualizado si el estudiante cambió de dispositivo después de que el turno fue encolado; el push fallará silenciosamente y el estudiante puede seguir verificando en la app.

## ADR-NOT-004 — Responsabilidad de generación de eventos: M3 publica, M4 consume

**Categoría:** Asignación de Responsabilidades

### Contexto

Las notificaciones se originan cuando M3 cambia el estado de un turno. M4 debe actuar sobre esos cambios. Se debe definir quién publica los eventos y quién los consume.

### Alternativas

1. **M3 llama directamente a M4 (acoplamiento directo).** Simple pero acopla M3 a M4. Cambiar el canal de notificación requiere modificar M3.

2. **M3 publica eventos en RabbitMQ; M4 consume independientemente.** M3 solo sabe que hay un exchange de eventos. No sabe si M4 existe ni cuántos consumidores hay. M4 reacciona a los eventos de su interés. Cambiar o agregar consumidores no requiere modificar M3.

### Criterios de Elección

- **Desacoplamiento** entre módulos de negocio e infraestructura de notificación.
- **Extensibilidad:** agregar más consumidores (M5) sin modificar el productor.

### Decisión

M3 publica eventos en RabbitMQ. M4 tiene su propio consumidor independiente con cola `m4.notificaciones`. M5 tiene su propio consumidor con cola `m5.seguimiento`. El mismo evento puede ser consumido por múltiples módulos sin coordinación entre ellos.

### Sustento

El desacoplamiento via broker es la decisión más importante de la arquitectura del sistema: M3 no conoce a M4 ni a M5. Si M5 se agrega después, M3 no necesita modificarse. El patrón Observer a través de RabbitMQ es la implementación de este desacoplamiento (ver [11.5](../../11/11.5/11.5.md)). El trade-off aceptado es que introducir un nuevo tipo de evento requiere acordar el esquema del mensaje entre el productor y los consumidores.

## ADR-NOT-005 — Plantillas de mensajes definidas en código (no en base de datos)

**Categoría:** Tiempo de Enlace

### Contexto

Las notificaciones push tienen texto fijo por tipo de evento: `turno.llamado` siempre genera "¡Es tu turno!" y `turno.cancelado` siempre genera "Turno cancelado". Se debe decidir dónde y cuándo se resuelven estos textos.

### Alternativas

1. **Plantillas almacenadas en base de datos, configurables por el administrador en runtime.** Flexible: el administrador puede cambiar los textos sin redespliegue. Requiere una consulta a DB o caché por cada notificación despachada. Complejidad adicional para textos que rara vez cambian.

2. **Plantillas hardcodeadas en el código del consumer.** El diccionario `MENSAJES` en `consumer.py` mapea cada tipo de evento a `(title, body)`. Sin consultas adicionales. Cambiar el texto requiere redespliegue, pero esto es aceptable para la etapa actual.

### Criterios de Elección

- **Simplicidad** de implementación en la etapa actual.
- **Sin overhead** de consulta por cada notificación enviada.

### Decisión

Las plantillas se definen en el diccionario `MENSAJES` dentro del consumer de M4 (`src/modules/notifications/consumer.py`). Los valores dinámicos (número de turno) se interpolan al construir el body.

### Sustento

Para la implementación actual, los dos tipos de evento tienen textos fijos bien conocidos. Añadir un sistema de plantillas en DB agrega complejidad que no aporta valor en esta etapa. Si en el futuro el administrador necesita personalizar los mensajes, el diccionario puede migrarse a una tabla con caché en memoria sin cambiar la interfaz del consumer. El trade-off aceptado es que cambiar los textos requiere redespliegue; asumible dado que los textos son institucionales y cambian raramente.

## ADR-NOT-006 — Durabilidad de mensajes no entregados mediante colas durables de RabbitMQ

**Categoría:** Modelo de Coordinación

### Contexto

Si el consumer de M4 está momentáneamente caído (reinicio del proceso, error no capturado), los eventos `turno.llamado` publicados por M3 no deben perderse. El estudiante debe recibir la notificación cuando M4 se recupere.

### Alternativas

1. **Mensajes efímeros (fire-and-forget).** Si el consumer está caído, el mensaje se pierde. El estudiante no recibe la notificación de turno llamado.

2. **Colas durables en RabbitMQ.** Los mensajes se persisten en disco en el broker. Si M4 está caído, los mensajes se acumulan en la cola. Al recuperarse M4, los procesa en orden. El ack solo se envía después de procesar exitosamente el mensaje (`async with message.process()`).

### Criterios de Elección

- **Confiabilidad de entrega** ante caídas temporales del consumer.
- **Sin pérdida** de eventos de turno llamado.

### Decisión

Las colas de M4 son durables. El ack se envía solo después de que `send_push()` completa (exitosa o no), gestionado por el context manager `async with message.process()`.

### Sustento

RabbitMQ con colas durables garantiza que ningún evento de turno llamado se pierde, incluso si M4 reinicia durante el horario de comedor. `message.process()` de aio_pika hace ack automático al salir del context manager sin excepción, o nack si hay excepción no capturada. El trade-off aceptado es que si `send_push()` falla consistentemente (token inválido), el mensaje puede quedarse en la cola o ir a dead-letter; el try/except en `_handle` previene que errores de push bloqueen el consumer.

## ADR-NOT-007 — Despliegue del módulo de notificaciones: FastAPI modular en monolito

**Categoría:** Mapeo entre Elementos Arquitectónicos

### Contexto

El consumer de RabbitMQ de M4 debe correr junto al resto del backend. Se debe decidir si se despliega como proceso separado o dentro del monolito.

### Alternativas

1. **Proceso/contenedor independiente solo para el consumer de M4.** Escalable independientemente del resto. Mayor complejidad operativa. Para el volumen universitario, no justificado.

2. **Consumer de RabbitMQ corriendo dentro del proceso FastAPI.** El consumer se inicia con `asyncio` al arrancar la app. Comparte el mismo contenedor y red que el resto de los módulos. Sin overhead de comunicación entre procesos.

### Criterios de Elección

- **Complejidad operativa** acorde al equipo.
- **Facilidad** de inicio y monitoreo.

### Decisión

El consumer de M4 corre en el mismo proceso FastAPI, iniciado al arrancar la aplicación como tarea asyncio.

### Sustento

El consumer es un loop asyncio que no bloquea el event loop principal de FastAPI. Al estar en el mismo proceso, comparte la conexión Redis y el pool de DB sin overhead adicional. El trade-off aceptado es que un crash del consumer puede afectar al proceso principal; se mitiga con el manejo de excepciones en `_handle()` y la política de retry de RabbitMQ.

## ADR-NOT-008 — Eventos consumidos por M4: `turno.llamado` y `turno.cancelado`

**Categoría:** Modelo de Coordinación

### Contexto

M4 debe suscribirse a los eventos de dominio relevantes para notificaciones push. Se debe definir explícitamente qué eventos consume M4 y cuáles no.

### Alternativas

1. **M4 consume todos los eventos del exchange.** Consume eventos irrelevantes para notificaciones push. El consumer decide en runtime cuáles procesar con condicionales.

2. **M4 consume solo los eventos que requieren push notification.** La cola `m4.notificaciones` se vincula con routing keys específicas: `turno.llamado` y `turno.cancelado`. Mensajes de otros tipos no llegan a la cola de M4.

### Criterios de Elección

- **Eficiencia:** M4 no procesa mensajes que no le corresponden.
- **Claridad** del contrato entre módulos.

### Decisión

La cola `m4.notificaciones` está vinculada a los routing keys `["turno.llamado", "turno.cancelado"]`. M4 no recibe ni procesa eventos de encolamiento (`turno.encolado`) ni de atención (`turno.atendido`), que son responsabilidad de M5.

### Sustento

El routing por clave en RabbitMQ garantiza que M4 solo recibe los mensajes que necesita, sin filtrado en aplicación. `turno.llamado` activa la notificación de "confirma tu presencia" y `turno.cancelado` notifica que el turno fue cancelado por inactividad. Son los dos únicos eventos que requieren notificación push inmediata al estudiante. El trade-off aceptado es que agregar un nuevo tipo de evento de notificación requiere actualizar la configuración de la cola.

## ADR-NOT-009 — Manejo de errores en el consumer: ack implícito con `message.process()`

**Categoría:** Gestión de Recursos

### Contexto

Si `send_push()` falla (token inválido, servicio de Expo caído), se debe decidir qué hacer con el mensaje de RabbitMQ: volver a intentar (nack con requeue) o descartar (ack o nack sin requeue).

### Alternativas

1. **Nack con requeue ante cualquier error.** El mensaje vuelve a la cola indefinidamente si el error es permanente (token inválido). Puede generar ciclos de retry infinitos.

2. **Ack siempre, sin importar el resultado de send_push.** Los errores de push se loguean pero no bloquean. Un mensaje con token inválido no atasca la cola. El mensaje se pierde sin reintento.

3. **Ack en éxito y en errores de negocio esperados (token inválido); nack solo en errores transitorios.** Diferenciación por tipo de error. Mayor complejidad de clasificación de errores.

4. **Try/except que captura todos los errores; `message.process()` siempre hace ack.** El context manager `async with message.process()` hace ack al salir normalmente y nack al propagar una excepción. El try/except interno captura todos los errores de send_push, previendo que no lleguen al nivel del context manager. Efectivamente siempre hace ack.

### Criterios de Elección

- **Estabilidad del consumer:** errores en un mensaje no deben atascar el procesamiento de otros.
- **Simplicidad** de implementación.

### Decisión

El try/except en `_handle()` captura todas las excepciones de procesamiento. `message.process()` siempre hace ack. Los errores se loguean con `print(f"[M4] Error procesando mensaje: {e}")`.

### Sustento

Para el caso de uso actual, la mayoría de fallos de push son por tokens expirados o inválidos — errores permanentes que no se resuelven con retry. Hacer ack inmediato evita que la cola se atasque con mensajes irreintentables. El trade-off aceptado es que errores transitorios de Expo (servicio caído) también hacen ack y el mensaje se pierde; en producción esto se mitigaría con una dead-letter queue y política de retry configurable.

## ADR-NOT-010 — Patrón Observer vía RabbitMQ Pub/Sub entre M3 y M4

**Categoría:** Elección de Tecnología

### Contexto

M3 (Subject/Publisher) genera eventos de dominio cuando cambia el estado de turnos. M4 (Observer/Consumer) debe reaccionar a esos eventos enviando push notifications. Se debe decidir cómo implementar esta relación Observer.

### Alternativas

1. **Observer en memoria (callback directo entre módulos).** M3 mantiene una lista de observers y los notifica directamente. Acoplamiento en tiempo de compilación entre M3 y M4. Los observers se pierden si el proceso se reinicia.

2. **Observer vía RabbitMQ Pub/Sub.** M3 publica en el exchange sin conocer a M4. M4 se suscribe declarando su cola y bindings. La relación Observer está implementada en la infraestructura del broker, no en el código de la aplicación.

### Criterios de Elección

- **Desacoplamiento** entre Subject y Observer.
- **Durabilidad** de las notificaciones entre observers.
- **Extensibilidad:** agregar observers sin modificar el Subject.

### Decisión

Se implementa el patrón Observer mediante RabbitMQ Pub/Sub. M3 es el publisher (Subject), M4 y M5 son consumers (Observers) independientes. Esta es la decisión GoF documentada en [11.5](../../11/11.5/11.5.md).

### Sustento

RabbitMQ materializa el patrón Observer con durabilidad: los mensajes persisten hasta que todos los consumers los han procesado. M3 no tiene referencia en código a M4 ni a M5. Agregar un Observer nuevo (por ejemplo, un módulo de analytics) solo requiere declarar una nueva cola vinculada al mismo exchange, sin tocar M3. El trade-off aceptado es la dependencia de la infraestructura RabbitMQ para la coordinación entre módulos.

## ADR-SEG-001 — Motor de almacenamiento para historial: PostgreSQL con tablas de append

**Categoría:** Elección de Tecnología

### Contexto

M5 debe registrar dos tipos de eventos: encolamiento de estudiantes (`turno.encolado`) y atención efectiva (`turno.atendido`). Estos registros son de solo escritura (append-only) durante el horario de comedor. Se debe decidir dónde almacenarlos.

### Alternativas

1. **TimescaleDB (extensión de PostgreSQL para series temporales).** Optimizada para datos temporales con compresión y particionado automático. Requiere cambiar la imagen Docker de PostgreSQL. Agrega complejidad operativa que no está justificada para el volumen actual.

2. **PostgreSQL simple con tablas estándar.** Sin dependencias adicionales. El equipo ya conoce el motor. Las tablas tienen `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` que actúa como índice temporal. Para el volumen universitario (miles de registros diarios, no millones), el rendimiento es suficiente.

3. **Redis para el historial en tiempo real.** Alta velocidad de escritura. Sin persistencia garantizada ante reinicios. No apto para historial a largo plazo.

### Criterios de Elección

- **Simplicidad** de operación con el stack existente.
- **Rendimiento** suficiente para el volumen universitario.
- **Persistencia** garantizada del historial.

### Decisión

Los eventos de seguimiento se persisten en tablas PostgreSQL estándar (`historial_asistencia` e `historial_encolamiento`) sin extensiones adicionales.

### Sustento

Para el volumen de un comedor universitario (decenas a cientos de registros por turno de comedor), PostgreSQL estándar es completamente suficiente. Las consultas más frecuentes son por `estudiante_id` y `turno_dia_id`, ambos con índices implícitos (FK y UNIQUE). Si el volumen justifica TimescaleDB en el futuro, la migración es compatible (misma imagen, misma sintaxis SQL). El trade-off aceptado es que las consultas de rango temporal sobre semanas o meses pueden ser más lentas que en un motor especializado; asumible en la etapa actual.

## ADR-SEG-002 — Modelo de datos: `historial_asistencia` e `historial_encolamiento`

**Categoría:** Modelo de Datos

### Contexto

M5 registra dos eventos distintos: que un estudiante se encoló (turno creado en cola) y que fue atendido (turno confirmado y consumido). Se debe decidir si usar una tabla unificada de eventos o tablas separadas por tipo.

### Alternativas

1. **Una tabla `historial_eventos` con campo `tipo` (ENCOLADO/ATENDIDO).** Modelo unificado. Las consultas de conversión (encolado→atendido) requieren self-join con filtro de tipo.

2. **Dos tablas separadas: `historial_asistencia` (atendidos) e `historial_encolamiento` (encolados).** Cada tabla tiene solo los registros de su tipo. Las consultas de tasa de conversión usan JOIN entre las dos tablas. Más simple de leer e indexar.

### Criterios de Elección

- **Claridad del esquema** para el caso de uso principal (tasa de conversión encolado→atendido).
- **Simplicidad de inserción** en el consumer.

### Decisión

Se usan dos tablas separadas: `historial_asistencia` (evento `turno.atendido`) y `historial_encolamiento` (evento `turno.encolado`). Ambas tienen `UNIQUE (estudiante_id, turno_dia_id)` para garantizar un registro por estudiante por turno.

### Sustento

La separación en dos tablas hace que cada INSERT en el consumer sea semánticamente claro: `registrar_asistencia()` toca solo `historial_asistencia` y `registrar_encolamiento()` toca solo `historial_encolamiento`. El JOIN para calcular conversión es explícito y legible. El constraint UNIQUE garantiza que ningún estudiante pueda ser registrado dos veces en el mismo turno, lo que refuerza la idempotencia (ADR-SEG-005). El trade-off aceptado es la duplicación de estructura entre ambas tablas; esto es justificado por la claridad semántica.

## ADR-SEG-003 — Responsabilidad del registro: M5 consume eventos de RabbitMQ

**Categoría:** Asignación de Responsabilidades

### Contexto

Los eventos de seguimiento se originan en M3. Se debe definir qué módulo es responsable de escribir en `historial_asistencia` e `historial_encolamiento`.

### Alternativas

1. **M3 escribe directamente en las tablas de historial.** M3 conoce el estado de la cola y podría escribir en los historiales en la misma transacción. Acopla M3 al esquema de M5. Un cambio en el modelo de datos de seguimiento requiere modificar M3.

2. **M5 consume eventos de RabbitMQ y escribe en sus propias tablas.** M3 publica eventos; M5 es el único que escribe en sus tablas. M5 es completamente responsable de su modelo de datos. M3 no necesita conocer el esquema de M5.

### Criterios de Elección

- **Desacoplamiento** entre módulos.
- **Single Responsibility:** M5 es dueño de su modelo de datos.

### Decisión

M5 consume eventos de RabbitMQ y es el único responsable de escribir en `historial_asistencia` e `historial_encolamiento`. M3 nunca toca esas tablas directamente.

### Sustento

La responsabilidad de persistir el historial pertenece a M5, no a M3. Este principio de Single Responsibility garantiza que el esquema de seguimiento puede evolucionar (agregar columnas, nuevas tablas) sin afectar a M3. El consumer de M5 es el boundary explícito entre el modelo de dominio de cola (M3) y el modelo de historial (M5). El trade-off aceptado es la latencia entre el evento y el registro en historial (tiempo de procesamiento del consumer), que es de milisegundos y aceptable para el caso de uso.

## ADR-SEG-004 — Eventos consumidos por M5: `turno.atendido` y `turno.encolado`

**Categoría:** Modelo de Coordinación

### Contexto

M5 debe registrar cuándo un estudiante se encoló y cuándo fue efectivamente atendido. Los eventos disponibles en el exchange de RabbitMQ incluyen `turno.encolado`, `turno.atendido`, `turno.llamado` y `turno.cancelado`. M5 solo consume los que requiere para su historial.

### Alternativas

1. **M5 consume todos los eventos del exchange.** Filtra en runtime. M5 recibe mensajes irrelevantes para su función.

2. **M5 consume solo `turno.atendido` y `turno.encolado`.** La cola `m5.seguimiento` se vincula exclusivamente a esos routing keys. M5 no recibe ni procesa los otros tipos.

### Criterios de Elección

- **Eficiencia:** M5 no procesa mensajes que no necesita.
- **Claridad** del contrato con M3.

### Decisión

La cola `m5.seguimiento` está vinculada a `["turno.atendido", "turno.encolado"]`. M5 llama a `registrar_asistencia()` para `turno.atendido` y `registrar_encolamiento()` para `turno.encolado`.

### Sustento

`turno.encolado` se genera cuando un estudiante obtiene un turno en la cola — evento de seguimiento de demanda. `turno.atendido` se genera cuando el turno se confirma y el estudiante es atendido — evento de seguimiento de consumo efectivo. Estos dos eventos son suficientes para calcular la tasa de conversión y el historial de asistencia. `turno.cancelado` no se registra en el historial de M5 porque es una no-asistencia que puede analizarse como la diferencia entre encolados y atendidos.

## ADR-SEG-005 — Idempotencia en el registro: `ON CONFLICT DO NOTHING`

**Categoría:** Modelo de Coordinación

### Contexto

RabbitMQ puede entregar el mismo mensaje más de una vez si el consumer falla después de procesar pero antes de enviar el ack. Si M5 reintenta procesar un mensaje ya registrado, podría intentar insertar una fila duplicada en `historial_asistencia`.

### Alternativas

1. **Verificar antes de insertar (`SELECT ... INSERT`).** Condición de carrera en accesos concurrentes. Dos operaciones pueden pasar el SELECT y ambas intentar el INSERT.

2. **Restricción UNIQUE + `ON CONFLICT DO NOTHING`.** La restricción `UNIQUE (estudiante_id, turno_dia_id)` garantiza unicidad a nivel de base de datos. `ON CONFLICT DO NOTHING` hace que la segunda inserción del mismo evento falle silenciosamente sin error. La operación es idempotente.

### Criterios de Elección

- **Idempotencia** ante reintentos de RabbitMQ.
- **Simplicidad** de implementación.
- **Ausencia de condiciones de carrera.**

### Decisión

Ambas funciones de registro (`registrar_asistencia`, `registrar_encolamiento`) usan `INSERT ... ON CONFLICT DO NOTHING`. Las restricciones `UNIQUE (estudiante_id, turno_dia_id)` están definidas en el DDL.

### Sustento

`ON CONFLICT DO NOTHING` es la forma más simple y correcta de implementar idempotencia en PostgreSQL. La restricción UNIQUE en DDL garantiza que la base de datos nunca tendrá duplicados independientemente de la concurrencia. PostgreSQL maneja el conflicto atómicamente sin condición de carrera. El trade-off aceptado es que si el mismo evento legítimamente debería registrarse dos veces (por ejemplo, si se rediseña el modelo), la restricción UNIQUE debería eliminarse; esto es un cambio explícito de diseño que no ocurrirá accidentalmente.

## ADR-SEG-006 — Eventos enriquecidos publicados por M3: M5 no consulta a otros módulos

**Categoría:** Asignación de Responsabilidades

### Contexto

Para registrar el historial, M5 necesita: `estudiante_id`, `turno_dia_id`, `numero_turno` y `tipo_comida`. Estos datos están disponibles en M3 cuando publica el evento. Se debe decidir si M5 los obtiene del payload del evento o los consulta a M3 u otras tablas.

### Alternativas

1. **M5 recibe un evento mínimo y consulta las tablas de M3 para completar los datos.** M5 hace queries a `turnos`, `turno_dia` o `estudiantes` para enriquecer el registro. Acopla M5 al modelo de datos de M3. Introduce latencia y dependencia síncrona.

2. **M3 publica eventos enriquecidos con todos los datos que M5 necesita.** El payload del evento incluye `estudiante_id`, `turno_dia_id`, `numero_turno`, `tipo_comida`. M5 solo inserta lo que recibe; no consulta ninguna tabla externa.

### Criterios de Elección

- **Desacoplamiento:** M5 no debe depender del esquema de tablas de M3.
- **Rendimiento:** M5 no realiza consultas síncronas adicionales por cada evento.

### Decisión

M3 publica eventos enriquecidos. M5 extrae directamente los campos del payload (`payload.get("estudiante_id")`, etc.) y los inserta en las tablas de historial sin consultas adicionales.

### Sustento

El consumer de M5 es un consumer completamente pasivo: recibe el mensaje, extrae los campos, inserta en la tabla correspondiente. Cero queries adicionales por evento. El trade-off aceptado es que el payload del evento es más grande; para el volumen universitario, el tamaño adicional (unos pocos campos más) es negligible.

## ADR-SEG-007 — Despliegue del módulo de seguimiento: FastAPI modular en monolito

**Categoría:** Mapeo entre Elementos Arquitectónicos

### Contexto

El consumer de RabbitMQ de M5 debe correr junto al resto del backend. Se decide si se despliega como proceso separado o dentro del monolito.

### Alternativas

1. **Proceso independiente para el consumer de M5.** Escalable independientemente. Mayor complejidad operativa sin beneficio para el volumen actual.

2. **Consumer de M5 dentro del proceso FastAPI.** Corre como tarea asyncio junto al servidor FastAPI. Sin overhead de comunicación entre procesos. Comparte el pool de conexiones de PostgreSQL.

### Criterios de Elección

- **Simplicidad operativa** acorde al equipo.
- **Compartición** del pool de conexiones existente.

### Decisión

El consumer de M5 corre en el mismo proceso FastAPI, iniciado como tarea asyncio al arrancar la aplicación.

### Sustento

Igual que M4 (ADR-NOT-007), el consumer asyncio no bloquea el event loop principal. El pool de conexiones PostgreSQL ya está configurado para el monolito; M5 lo reutiliza. El trade-off aceptado es que un crash del consumer afecta al proceso principal; el manejo de excepciones en `_handle()` previene que errores de inserción propaguen fuera del consumer.

## ADR-SEG-008 — Alcance del módulo de seguimiento en la implementación actual

**Categoría:** Modelo de Datos

### Contexto

El diseño conceptual de M5 contemplaba funcionalidades adicionales: sistema de penalizaciones por inasistencia, dashboard de estadísticas en tiempo real, retención y limpieza de datos históricos. Se debe documentar explícitamente qué está implementado y qué no.

### Implementado en la versión actual

- Registro de encolamiento en `historial_encolamiento` via evento `turno.encolado`.
- Registro de asistencia en `historial_asistencia` via evento `turno.atendido`.
- Idempotencia con `ON CONFLICT DO NOTHING`.
- Consumer de RabbitMQ con manejo básico de errores.

### Fuera del alcance actual

- Sistema de penalizaciones (`inasistencias`, `penalizacion_activa`): no implementado. Las tablas no existen en el esquema actual.
- Dashboard de estadísticas en tiempo real: no implementado.
- Retención y limpieza de datos históricos: no implementado.
- Contadores en Redis para métricas en tiempo real: no implementado.

### Decisión

La implementación actual de M5 cubre exclusivamente el registro de historial mediante consumo de eventos RabbitMQ. Las funcionalidades adicionales son trabajo futuro.

### Sustento

El alcance acotado garantiza que lo que está implementado funciona correctamente y está alineado con el resto del sistema. El sistema de penalizaciones requiere decisiones de negocio (cuántas inasistencias activan penalización, duración) que no están definidas en los requerimientos actuales. El trade-off aceptado es que el módulo de seguimiento en su estado actual es un registrador pasivo sin capacidad analítica; esto es suficiente para la etapa de implementación del proyecto.

## ADR-SEG-009 — Manejo de errores en el consumer de seguimiento

**Categoría:** Gestión de Recursos

### Contexto

Si la inserción en PostgreSQL falla (error de conexión, violación de constraint inesperada), se debe decidir qué hacer con el mensaje de RabbitMQ.

### Alternativas

1. **Nack con requeue ante cualquier error de DB.** El mensaje vuelve a la cola. Si el error es transitorio (conexión caída), se resuelve al recuperarse. Si el error es permanente (constraint violation no esperada), ciclo infinito.

2. **Ack siempre, los errores se loguean.** Un error de inserción no atasca la cola. El registro se pierde pero el sistema sigue funcionando.

3. **Try/except que distingue errores transitorios de permanentes.** Mayor complejidad. Requiere clasificar cada tipo de excepción de PostgreSQL.

### Criterios de Elección

- **Estabilidad del consumer** ante errores individuales.
- **No pérdida** de mensajes por errores transitorios.
- **Simplicidad** de implementación.

### Decisión

El try/except en `_handle()` captura todas las excepciones. Los errores se loguean con `print(f"[M5] Error procesando mensaje: {e}")`. `message.process()` hace ack al salir del context manager sin excepción propagada. Efectivamente siempre hace ack.

### Sustento

Los errores más probables de inserción en M5 son: constraint UNIQUE (ya cubierto por `ON CONFLICT DO NOTHING`), FK violation (estudiante_id no existe, turno_dia_id no existe), o pérdida momentánea de conexión a DB. `ON CONFLICT DO NOTHING` previene el error de duplicado. Los otros errores son raros y loguearlos es suficiente para detectarlos sin bloquear el procesamiento. El trade-off aceptado es igual que en ADR-NOT-009: errores de DB transitorios también hacen ack y el registro se pierde; en producción se añadiría una dead-letter queue.

## ADR-SEG-010 — Patrón Observer vía RabbitMQ Pub/Sub entre M3 y M5

**Categoría:** Elección de Tecnología

### Contexto

M3 (Subject/Publisher) genera eventos de dominio. M5 (Observer/Consumer) debe reaccionar a los eventos de encolamiento y atención para registrarlos en el historial. La misma relación Observer que existe entre M3 y M4 (ADR-NOT-010) aplica aquí.

### Alternativas

1. **Observer en memoria entre M3 y M5.** Acoplamiento en código. Los eventos se pierden ante reinicios.

2. **Observer vía RabbitMQ Pub/Sub.** M3 no conoce a M5. M5 declara su cola y bindings independientemente. El broker gestiona la relación Observer.

### Criterios de Elección

- **Desacoplamiento** entre M3 y M5.
- **Independencia** entre los observers M4 y M5 (cada uno procesa a su propio ritmo).

### Decisión

Se implementa el patrón Observer mediante RabbitMQ Pub/Sub, igual que en ADR-NOT-010. M5 tiene su propia cola `m5.seguimiento` independiente de la cola de M4. Esta es la segunda instancia del patrón Observer documentada en [11.5](../../11/11.5/11.5.md).

### Sustento

La independencia de colas entre M4 y M5 garantiza que si M5 está caído, M4 sigue enviando push notifications sin verse afectado, y viceversa. Cada consumer procesa los mensajes a su propio ritmo. La semántica del patrón Observer se cumple: M3 notifica un cambio de estado sin conocer a sus observers; cada observer reacciona de forma independiente. El trade-off aceptado es que el mismo evento de RabbitMQ se almacena dos veces en el broker (en la cola de M4 y en la de M5), lo cual es el comportamiento esperado del fan-out en el exchange.
