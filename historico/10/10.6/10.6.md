# 10.6. Estrategia de Poblamiento de Datos

---

## Visión general

El sistema utiliza dos motores de persistencia: **PostgreSQL** para todos los datos de negocio y **Redis** para las sesiones activas. La estrategia de poblamiento se divide en dos capas:

| Capa | Mecanismo | Motor |
|---|---|---|
| Estructura + datos de configuración | Migración SQL ejecutada automáticamente al levantar Docker | PostgreSQL |
| Estudiantes de prueba | Script de seed en Python (`seed_estudiantes.py`) | PostgreSQL |
| Sesiones | Sin pre-poblamiento — se crean en tiempo de ejecución al iniciar sesión | Redis |

---

## 1. Mecanismo de reproducibilidad

El entorno completo se levanta con un único comando:

```bash
docker compose up --build
```

Docker Compose define tres servicios: `postgres`, `redis` y `rabbitmq`. El servicio `postgres` monta la migración directamente en la carpeta de inicialización del contenedor:

```yaml
volumes:
  - ./backend/migrations/001_init.sql:/docker-entrypoint-initdb.d/001_init.sql
```

PostgreSQL ejecuta automáticamente todos los archivos `.sql` que encuentre en `docker-entrypoint-initdb.d/` la primera vez que el contenedor se inicia con un volumen vacío. Esto garantiza que:

1. Las tablas se crean en el orden correcto (respetando claves foráneas).
2. Los datos de configuración se insertan en la misma ejecución, sin pasos manuales.
3. Al destruir y recrear el volumen (`docker compose down -v && docker compose up`) el entorno vuelve a su estado inicial limpio.

## 2. Datos sembrados por la migración (`001_init.sql`)

### 2.1 Configuración de servicios — `turnos_config`

La migración inserta los tres tipos de servicio que el sistema reconoce. Son la plantilla de la que heredan todas las instancias diarias:

| `id` | `tipo` | `hora_apertura` | `hora_inicio` | `hora_cierre` | `raciones_max` |
|---|---|---|---|---|---|
| 1 | `ALMUERZO` | 06:00 | 07:00 | 08:00 | 5 000 |
| 2 | `CENA` | 11:30 | 12:30 | 13:30 | 5 000 |
| 3 | `PRUEBA` | 00:00 | 00:10 | 23:59 | 10 |

El tipo `PRUEBA` tiene `hora_cierre = 23:59` para que permanezca siempre abierto durante el día y permita demostrar el flujo de encolamiento sin depender de un horario específico. Su `raciones_max = 10` produce grupos de llamado de 1 estudiante (`⌈10 / 10⌉ = 1`), lo que facilita la demostración del ciclo completo con pocos participantes.

```sql
INSERT INTO turnos_config (tipo, hora_apertura, hora_inicio, hora_cierre) VALUES
    ('ALMUERZO', '6:00',  '7:00',  '8:00'),
    ('CENA',     '11:30', '12:30', '13:30'),
    ('PRUEBA',   '00:00', '00:10', '23:59');
```

### 2.2 Instancias del día actual — `turno_dia`

La migración crea una instancia de cada servicio para `CURRENT_DATE`. Esto significa que cada vez que se recrea el contenedor, las instancias se generan para la fecha en que se ejecuta `docker compose up`:

| `config_id` | `fecha` | `raciones_max` |
|---|---|---|
| 1 (ALMUERZO) | hoy | 5 000 |
| 2 (CENA) | hoy | 5 000 |
| 3 (PRUEBA) | hoy | 10 |

```sql
INSERT INTO turno_dia (config_id, fecha, raciones_max) VALUES
    (1, CURRENT_DATE, 5000),
    (2, CURRENT_DATE, 5000),
    (3, CURRENT_DATE, 10);
```

### 2.3 Menú del día — `menu_dia` y `menu_platos`

La migración inserta el menú nutricional completo del día actual con sus tres comidas:

| Comida | Energía (kcal) | Proteínas (g) | Lípidos (g) | Carbohidratos (g) |
|---|---|---|---|---|
| DESAYUNO | 607,98 | 19,44 | 16,83 | 81,31 |
| ALMUERZO | 1 332,46 | 43,31 | 51,11 | 171,35 |
| CENA | 1 042,36 | 38,46 | 27,04 | 131,83 |

Los platos se insertan referenciando el `id` de cada comida:

- **DESAYUNO:** AVENA CON MEMBRILLO · PAN DE TOLETE CON QUESO · FRUTA
- **ALMUERZO:** SOPA DE FIDEOS · ARROZ CHAUFA DE CERDO · REFRESCO DE CHICHA MORADA · FRUTA
- **CENA:** AJÍ DE PAVITA PRESADO CON PAPAS · ARROZ · INFUSIÓN DE CEBADA · FRUTA

Los datos nutricionales son valores reales del comedor universitario, no generados sintéticamente, ya que no contienen información personal.

## 3. Script de seed de estudiantes

### Por qué es necesario un script separado

La tabla `estudiantes` no tiene datos en la migración por diseño: en producción, el registro de un estudiante ocurre la primera vez que inicia sesión con Google y el backend obtiene sus datos del sistema académico (ORCE/SGA). En un entorno de demostración sin acceso al SGA, se necesita un script que inserte estudiantes sintéticos directamente en PostgreSQL.

### Script propuesto: `seed_estudiantes.py`

El script genera estudiantes con datos sintéticos usando la librería `Faker` para evitar exponer información personal real. Los códigos siguen el formato real de la UNI (`20XXYYYY`).

```python
"""
seed_estudiantes.py
Pobla la tabla estudiantes con N registros sintéticos para entornos de demostración.
Uso: python seed_estudiantes.py [N]   (por defecto N=20)
"""
import sys
import asyncio
import asyncpg
from faker import Faker

DATABASE_URL = "postgresql://postgres:postgres@localhost:5433/comedor_uni"
fake = Faker("es_PE")   # localización peruana para nombres realistas
import random, string

async def seed(n: int = 20):
    conn = await asyncpg.connect(DATABASE_URL)
    for i in range(1, n + 1):
        letra     = random.choice(string.ascii_uppercase)
        codigo    = f"20{str(i).zfill(6)}{letra}"    # ej. 20000001A … 20000020Z
        segundo   = fake.first_name() if random.random() < 0.5 else ""
        nombres   = f"{fake.first_name()} {segundo}".strip()   # 1 o 2 nombres al azar
        ap_pat    = fake.last_name()
        ap_mat    = fake.last_name()
        email     = (
            f"{nombres.split()[0].lower()}"
            f".{ap_pat.lower()}"
            f".{ap_mat[0].lower()}"
            f"@uni.edu.pe"
        )  # ej. luis.garcia.m@uni.edu.pe
        await conn.execute(
            """
            INSERT INTO estudiantes (codigo, nombres, apellido_paterno, apellido_materno, email)
            VALUES ($1, $2, $3, $4, $5)
            ON CONFLICT (codigo) DO NOTHING
            """,
            codigo, nombres, ap_pat, ap_mat, email
        )
    await conn.close()
    print(f"{n} estudiantes insertados.")

if __name__ == "__main__":
    n = int(sys.argv[1]) if len(sys.argv) > 1 else 20
    asyncio.run(seed(n))
```

**Dependencias:**

```bash
pip install asyncpg faker
```

**Ejecución** (con el contenedor de PostgreSQL ya corriendo):

```bash
python seed_estudiantes.py 20
```

### Por qué `ON CONFLICT DO NOTHING`

La cláusula evita que una segunda ejecución del script falle por la restricción `UNIQUE(codigo)`. El script es **idempotente**: correrlo más de una vez deja la base en el mismo estado que correrlo una sola vez.

## 4. Redis — Sin pre-poblamiento

Redis almacena únicamente sesiones activas. Una sesión se crea cuando un estudiante inicia sesión y se destruye cuando cierra sesión o cuando su TTL de 8 horas vence. No hay datos que sembrar de antemano: al levantar el contenedor Redis comienza vacío y se puebla en tiempo de ejecución a medida que los estudiantes autentican.

Para verificar el estado de Redis durante una demostración:

```bash
# Conectar al CLI de Redis
docker exec -it comedor-redis redis-cli

# Listar todas las sesiones activas
KEYS session:*

# Ver el payload de una sesión
GET session:<sid>

# Ver cuánto tiempo le queda (TTL en segundos)
TTL session:<sid>

# Verificar que el índice usuario→sesión existe
GET user_session:<codigo>
```

## 5. Coherencia entre motores

La clave de coherencia entre PostgreSQL y Redis es el campo `codigo` del estudiante:

- En PostgreSQL: `estudiantes.codigo` (VARCHAR, UNIQUE).
- En Redis: la clave `user_session:{codigo}` apunta al `sid` de la sesión activa de ese estudiante.

Cuando el sistema autentica a un estudiante, el backend:
1. Lee el registro de `estudiantes` en PostgreSQL usando el código Google institucional.
2. Crea en Redis `session:{sid}` con el payload `{codigo, email, nombre, creditos}` y TTL de 8 horas.
3. Crea en Redis `user_session:{codigo}` apuntando al mismo `sid`.

No existe ningún identificador numérico (`id`) de PostgreSQL en las claves Redis — la coherencia se mantiene por el `codigo` institucional, que es estable e inmutable.

```
PostgreSQL                      Redis
────────────────────────        ──────────────────────────────────────
estudiantes.codigo = "20000001A" user_session:20000001A  → "abc123"
                                 session:abc123           → {"codigo":"20000001A",...}
```

Si Redis se vacía (reinicio del contenedor), ningún dato de negocio se pierde: los estudiantes, turnos y menús permanecen intactos en PostgreSQL. El único efecto es que los estudiantes con sesión activa deben volver a iniciar sesión.

## 6. Dataset de verificación

Una vez levantado el entorno y ejecutado el seed de estudiantes, los siguientes flujos permiten verificar que todos los datos son coherentes:

### Verificar configuración base

```sql
-- Debe retornar 3 filas: ALMUERZO, CENA, PRUEBA
SELECT tipo, hora_apertura, hora_cierre, raciones_max FROM turnos_config;

-- Debe retornar 3 filas para la fecha de hoy
SELECT td.id, tc.tipo, td.fecha, td.raciones_max, td.abierto
FROM turno_dia td JOIN turnos_config tc ON tc.id = td.config_id
WHERE td.fecha = CURRENT_DATE;
```

### Verificar estudiantes sembrados

```sql
-- Debe retornar N filas (20 por defecto)
SELECT id, codigo, nombres, apellido_paterno, email FROM estudiantes ORDER BY id;
```

### Simular encolamiento (M2)

```sql
-- Inscribir al estudiante 1 en el turno PRUEBA del día de hoy
INSERT INTO turnos (estudiante_id, turno_dia_id, numero_turno)
SELECT 1, td.id,
       COALESCE((SELECT MAX(numero_turno) FROM turnos WHERE turno_dia_id = td.id), 0) + 1
FROM turno_dia td JOIN turnos_config tc ON tc.id = td.config_id
WHERE tc.tipo = 'PRUEBA' AND td.fecha = CURRENT_DATE;

-- Verificar posición en cola
SELECT numero_turno, estado, ingresado_at FROM turnos
WHERE estudiante_id = 1 AND estado != 'CANCELADO';
```

### Simular llamado de grupo (M3)

```sql
-- Llamar al primer grupo del turno PRUEBA
UPDATE turnos SET estado = 'LLAMADO', llamado_at = NOW(), ultimo_ping = NOW()
WHERE turno_dia_id = (
    SELECT td.id FROM turno_dia td JOIN turnos_config tc ON tc.id = td.config_id
    WHERE tc.tipo = 'PRUEBA' AND td.fecha = CURRENT_DATE
)
AND numero_turno BETWEEN 1 AND 1   -- batch_size = ⌈10/10⌉ = 1
AND estado = 'ESPERANDO';

-- Verificar que el turno cambió de estado
SELECT id, numero_turno, estado, llamado_at FROM turnos WHERE estudiante_id = 1;
```

### Verificar menú del día

```sql
SELECT md.tipo_comida, md.energia_kcal, mp.nombre AS plato
FROM menu_dia md JOIN menu_platos mp ON mp.menu_dia_id = md.id
WHERE md.fecha = CURRENT_DATE
ORDER BY md.tipo_comida, mp.id;
```
