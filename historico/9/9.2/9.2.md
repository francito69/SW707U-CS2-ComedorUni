# 9.2. Módulo 2 / Integrante 2

# Decisiones de Modelo de Datos (Elección de Motores de Persistencia)

---

## 1. Módulo 2 – Gestión de Colas (M2)

### 1.1 Caso de uso
> *Mantener la cola virtual de estudiantes, permitir ingresos y salidas en tiempo real, y exponer la posición de cada estudiante a la UI.*

#### Atributos de calidad priorizados
| Calidad | Prioridad |
|---------|-----------|
| **Rendimiento** (latencia < 5 ms en operaciones de ingreso/consulta) | Alta |
| **Consistencia** (garantizar FIFO y evitar duplicados) | Alta |
| **Escalabilidad** (soportar picos de miles de solicitudes simultáneas) | Media |
| **Persistencia histórica** (auditar todas las entradas y salidas) | Media |
| **Disponibilidad** (operar aunque la base relacional sufra degradación) | Baja |

### 1.2 Comparativa de familias de motores (selección de al menos dos candidatas)
| Familia | Ventajas para el caso | Desventajas relevantes |
|---------|----------------------|------------------------|
| **Clave‑valor / In‑memory** – **Redis (Sorted Set, Hash, Counter)** | • Operaciones O(log N) / O(1) extremadamente rápidas, ideal para inserciones, extracción FIFO y consulta de posición (`ZRANK`).<br>• Soporta contadores atómicos y scripts Lua que garantizan atomicidad sin bloqueos externos.<br>• Persistencia opcional (AOF/RDB) permite recuperación rápida en caso de caída. | • No ofrece transacciones ACID multi‑tabla; la consistencia a largo plazo debe replicarse en otro motor.<br>• La pérdida parcial de datos es posible si la configuración de persistencia no está bien ajustada. |
| **Relacional (RDBMS)** – **PostgreSQL** | • ACID completo para auditoría, historial y consultas analíticas.<br>• Integridad referencial y constraints garantizan que no existan registros huérfanos.<br> • Permite exportar datos a reportes y cumplir con requisitos regulatorios. | • Latencia mucho mayor (ms‑tens) que Redis para operaciones de alta frecuencia.
| **Documental (MongoDB)** | • Modelo flexible para almacenar metadatos de la cola (por ejemplo, atributos de prioridad).| • Carece de transacciones multi‑documento robustas (solo en versiones recientes y con limitaciones), lo que complica la garantía de FIFO sin lógica adicional. |

### 1.3 Decisión (ADR‑9.2‑M2‑001)
> **ADR‑9.2‑M2‑001 – Motor de persistencia para la Gestión de Colas**
>
> **Elección:** *Modelo híbrido: Redis como fuente operativa (estado de la cola y contadores) y PostgreSQL como fuente de verdad histórica.*
>
> **Motivo:** Redis satisface los requisitos críticos de **rendimiento** y **escalabilidad** al manejar la cola en memoria y permitir consultas instantáneas de posición. PostgreSQL garantiza **consistencia** y **persistencia histórica** requerida por los ADR‑COL‑003 y ADR‑COL‑007 .
>
> **Trade‑offs aceptados:** Se sacrifica la simplicidad de una única base de datos a favor de una arquitectura políglota. El riesgo de pérdida de estado operativo se mitiga con AOF + replicación de Redis y con la sincronización periódica en PostgreSQL.

### 1.4 Persistencia políglota
- **Redis** (clave‑valor, estructuras en memoria) → *fuente operativa* para la cola, contadores de disponibilidad y timers de expiración.
- **PostgreSQL** (relacional) → *fuente de verdad* para el historial de la cola, auditoría y generación de reportes.
- **Convivencia:** Cada operación de ingreso/expulsión escribe primero en Redis (latencia mínima). Un proceso de *sync* asíncrono (worker) persiste la transacción en PostgreSQL y, en caso de error, genera una compensación que vuelve a colocar el elemento en Redis.

## 2. Módulo 3 – Gestión de Turnos (M3)

### 2.1 Caso de uso
> *Crear, actualizar y seguir el ciclo de vida de los turnos asignados a los estudiantes, incluida la confirmación, expiración y reasignación automática.*

#### Atributos de calidad priorizados
| Calidad | Prioridad |
|---------|-----------|
| **Consistencia fuerte** (estado único y válido en todo momento) | Alta |
| **Auditoría** (trazabilidad de cambios y responsables) | Alta |
| **Rendimiento** en consultas de estado activo (ej. verificar si un turno está confirmado) | Media |
| **Escalabilidad** (soportar miles de turnos simultáneos) | Media |
| **Disponibilidad** del historial de turnos para reporting | Baja |

### 2.2 Comparativa de familias de motores
| Familia | Ventajas para el caso | Desventajas relevantes |
|---------|----------------------|------------------------|
| **Relacional (RDBMS)** – **PostgreSQL** | • Transacciones ACID garantizan la integridad del ciclo de vida del turno.<br>• ENUM y constraints facilitan la implementación de la máquina de estados (ADR‑TUR‑002).<br>• Soporta historial versionado y auditoría con *temporal tables* o triggers.<br>• Fácil de integrar con los eventos de dominio ya publicados por la cola. | • Lecturas muy frecuentes pueden impactar la latencia si se acceden directamente; mitigado con caché de lectura. |
| **Clave‑valor / In‑memory** – **Redis (TTL + Key‑Space Notifications)** | • Permite timers ultra‑rápidos para expiración de confirmación (ADR‑TUR‑004, ADR‑TUR‑005).| • No ofrece consultas complejas ni relaciones, por lo que el modelo de datos completo debe residir en PostgreSQL. |
| **Orientado a grafos (Neo4j)** | • Modelaría relaciones de dependencia entre turnos y estudiantes de forma natural (cadenas de reasignación).| • Overkill para el dominio actual y añade complejidad operativa sin beneficios claros. |

### 2.3 Decisión (ADR‑9.2‑M3‑001)
> **ADR‑9.2‑M3‑001 – Motor de persistencia para la Gestión de Turnos**
>
> **Elección:** *PostgreSQL como fuente de verdad para todos los turnos y su historial; Redis como caché de lectura y gestor de timers.*
>
> **Motivo:** La **consistencia** y la **auditoría** demandan un motor relacional con soporte de transacciones. Redis complementa al proporcionar **baja latencia** para operaciones de expiración y para lecturas frecuentes del estado activo, alineándose con los ADR‑TUR‑004 y ADR‑TUR‑005.
>
> **Trade‑offs aceptados:** Introducimos una capa de caché que requiere invalidación coherente (evento `turno_actualizado` → purge Redis). El beneficio es una reducción significativa de la carga sobre PostgreSQL en lecturas de alta frecuencia.

### 2.4 Persistencia políglota
- **PostgreSQL** → almacena la tabla `turnos` con columnas `id`, `estado` (ENUM), `ulid`, `fecha_creacion`, etc.; guarda histórico mediante *temporal tables* o triggers.
- **Redis** → cachea el estado `activo`/`confirmado` de los turnos y gestiona **TTL** para los temporizadores de confirmación.
- **Convivencia:** Al crear o actualizar un turno, el servicio escribe en PostgreSQL y, a continuación, actualiza/invalidates la entrada correspondiente en Redis. Los workers que escuchan eventos (`turno_actualizado`) garantizan la coherencia eventual.
