# 9.1. Módulo 1 / Integrante 1

**Módulos cubiertos:** M1 – Autenticación · M4 – Notificaciones · M5 – Seguimiento

---

## Persistencia políglota adoptada

**Persistencia políglota** significa usar más de un motor de base de datos en el mismo sistema, eligiendo el más adecuado para cada tipo de dato en lugar de forzar todo en un único motor.

En este sistema se usan dos motores:

| Motor | Familia | Qué almacena |
|---|---|---|
| **PostgreSQL** | Relacional | Perfiles de estudiantes, historial de notificaciones, turnos, eventos |
| **Redis** | Clave/Valor | Sesiones activas (solo M1); cada sesión incluye la foto vigente del estudiante obtenida de ORCE |

M4 y M5 usan únicamente PostgreSQL. Redis solo interviene en M1 para la gestión de sesiones. Las razones se detallan en cada ADR a continuación.

---

## M1 — Autenticación

### Caso de uso y atributos de calidad

El caso de uso central es **CU01 – Autenticar estudiante**: el sistema valida credenciales Google institucionales, verifica que el estudiante sea activo, crea una sesión personal e intransferible y registra el evento para auditoría. El caso de uso secundario es **CU02 – Cerrar sesión**: la sesión debe invalidarse de forma instantánea.

| Atributo | Medida clave |
|---|---|
| Seguridad | 0 sesiones inválidas reutilizadas; tokens revocados inaccesibles en < 1s |
| Rendimiento | Autenticación < 2s; verificación de sesión < 50ms en cada operación del estudiante |
| Disponibilidad | ≥ 99.5%; el sistema no puede quedar inaccesible por un fallo en la capa de sesiones |

---

### ADR-9.1-M1-001 / ADR-9.1-M1-002: Motor de persistencia para perfil de estudiante y sesiones

**Decisión:** PostgreSQL para el perfil del estudiante + Redis para las sesiones activas y la lista de tokens revocados.

---

**Contexto:**

El módulo gestiona dos tipos de dato con naturalezas completamente distintas:

1. **Perfil del estudiante:** dato permanente. Se crea una vez (cuando el estudiante se registra) y se lee en cada autenticación. Es información estructurada y fija: código, nombre, email, foto, token de notificaciones. Requiere que no existan dos registros con el mismo código institucional.

2. **Sesión activa:** dato temporal. Una sesión solo existe mientras el estudiante está usando la app. Cuando cierra sesión —o cuando pasa cierto tiempo sin actividad— debe desaparecer automáticamente. Técnicamente, cada sesión es identificada por un `sid` (identificador de sesión) y necesita expirar con un **TTL** (*Time To Live*: tiempo de vida máximo que se le asigna a un dato; cuando ese tiempo se cumple, el dato se elimina automáticamente sin intervención de la aplicación). La sesión almacena además la **foto de perfil del estudiante obtenida de ORCE** durante el scraping del login: al no guardarla en PostgreSQL, se garantiza que cada nuevo inicio de sesión siempre compara la selfie contra la foto institucional vigente, no contra una versión anterior que el estudiante pudo haber actualizado.

---

**Alternativas evaluadas:**

**Alternativa A — Motor relacional (PostgreSQL) para todo**

Tanto el perfil como las sesiones se guardan en tablas de PostgreSQL. Las sesiones expiradas se eliminan mediante un proceso programado que borra registros con fecha de expiración pasada.

- Es la solución más simple: un solo motor.
- La verificación de sesión en cada operación del estudiante implica una consulta a disco. Aceptable en volumen universitario, pero añade latencia innecesaria cuando el estudiante interactúa con el sistema.
- La expiración automática de sesiones depende de un proceso externo que debe ejecutarse periódicamente. Si ese proceso falla, las sesiones expiradas permanecen en la tabla indefinidamente, acumulando registros inútiles.
- La lista de tokens revocados crece sin límite hasta que el proceso de limpieza la depura.

**Alternativa B — Motor clave/valor en memoria (Redis) para sesiones + Relacional para perfil *(solución adoptada)***

Redis almacena las sesiones activas y la lista de tokens revocados. PostgreSQL almacena el perfil.

Redis es una base de datos que vive completamente en la memoria RAM del servidor, en lugar de en disco. Esto lo hace extremadamente rápido para operaciones simples de "guarda este valor bajo esta clave" y "dame el valor de esta clave". La diferencia con PostgreSQL es que Redis no está pensado para consultas complejas ni para datos que deben vivir para siempre, sino para datos de acceso frecuente y vida corta.

- La verificación de sesión es una lectura directa en memoria: se le da el `sid` al motor y devuelve si existe o no, sin consultar disco.
- Redis tiene soporte nativo para TTL: al guardar una sesión se le indica cuánto tiempo puede vivir y Redis la elimina solo cuando ese tiempo vence. No se necesita ningún proceso de limpieza externo.
- La lista de tokens revocados también usa TTL: cuando un token expira por su propio tiempo de vida, su entrada en la lista se borra automáticamente.
- El perfil del estudiante permanece en PostgreSQL, que garantiza que no puedan existir dos registros con el mismo código (restricción de unicidad) y permite consultas relacionales para reportes administrativos.

**Trade-off aceptado:** si el servidor Redis se reinicia de forma inesperada, las sesiones activas en ese momento se pierden y los estudiantes deben autenticarse de nuevo. Para el contexto universitario, donde las sesiones duran horas y los reinicios planeados se hacen fuera del horario de comedor, este riesgo es aceptable.

**Alternativa C — Motor documental (MongoDB) para el perfil**

El perfil del estudiante se guarda como un documento JSON sin esquema fijo, lo que permite agregar o quitar campos sin migrar la base de datos.

- El perfil del estudiante tiene campos completamente fijos (definidos por la Intranet UNI). La flexibilidad de esquema que ofrece MongoDB no tiene utilidad aquí.
- Se pierde la garantía de unicidad nativa del código institucional.
- Se añade un tercer motor al sistema sin ningún beneficio concreto para este caso de uso.

---

**Decisión adoptada:** Alternativa B.

**Trade-offs aceptados:**

| Trade-off | Descripción |
|---|---|
| Pérdida de sesiones ante reinicio inesperado de Redis | Los estudiantes deben volver a autenticarse. Aceptable: las sesiones son cortas y el sistema puede configurar Redis para persistir snapshots periódicos en disco como respaldo. |
| Dos motores en lugar de uno | La reducción de latencia en la verificación de sesión —operación que ocurre en cada acción del estudiante— justifica la complejidad adicional de gestionar un segundo motor. |
| Riesgo en el cierre de sesión si Redis cae | Si Redis no responde en el momento del logout, el token permanece técnicamente válido hasta que su TTL natural venza. Mitigado configurando un TTL corto (menos de 1 hora). |

## M4 — Notificaciones

### Caso de uso y atributos de calidad

Los casos de uso centrales son **CU01 – Notificar asignación de turno** y **CU02 – Notificar confirmación requerida**. El sistema debe registrar cada notificación enviada con su estado de entrega para auditoría (RF-M4-08). Las notificaciones de confirmación son críticas: si llegan tarde, el estudiante pierde su turno.

| Atributo | Medida clave |
|---|---|
| Rendimiento | Notificación emitida < 2s tras el evento; tasa de entrega ≥ 99% |
| Disponibilidad | 0 pérdida de registros; historial siempre consultable |
| Seguridad | Cada notificación enviada debe quedar registrada con su estado; auditoría completa |

---

### ADR-9.1-M4-001: Motor de persistencia para historial de notificaciones

**Decisión:** PostgreSQL para el historial de notificaciones y las preferencias del estudiante.

---

**Contexto:**

El módulo persiste dos tipos de dato:

1. **Historial de notificaciones:** registro de cada notificación enviada. Incluye tipo, mensaje, fecha y hora de envío, estado de entrega (`PENDIENTE / ENTREGADO / EXPIRADO`) y referencia al turno y al estudiante involucrado. Es un dato de auditoría: solo se escribe, nunca se modifica, y debe poder consultarse para demostrar que el sistema cumplió con la obligación de avisar al estudiante.

2. **Preferencias de notificación:** qué canales prefiere cada estudiante para recibir avisos. Dato con poca frecuencia de cambio.

---

**Alternativas evaluadas:**

**Alternativa A — Motor documental (MongoDB)**

Cada notificación se guarda como un documento JSON independiente, sin columnas predefinidas. Las preferencias del estudiante se guardan como parte de su documento.

MongoDB es un motor que no exige definir un esquema fijo: cada registro puede tener campos distintos. Esto lo hace conveniente cuando el formato de los datos varía mucho de un registro a otro.

- El contenido de una notificación varía según su tipo (una notificación de turno llamado incluye datos distintos a una de cancelación). Podría parecer que la flexibilidad de MongoDB es útil aquí.
- Sin embargo, para consultar el historial se necesita filtrar por estudiante, por turno y por tipo de notificación simultáneamente, y combinar esos datos con información de la tabla de turnos para enriquecer reportes. MongoDB no tiene un mecanismo equivalente al `JOIN` de SQL: para lograr lo mismo requiere duplicar datos o escribir agregaciones complejas.
- Las preferencias del estudiante están relacionadas con su perfil, que ya vive en PostgreSQL. Mantenerlas en MongoDB generaría una separación artificial entre datos relacionados, sin ninguna ventaja.

**Alternativa B — Motor columnar (Cassandra)**

El historial de notificaciones como una tabla orientada al tiempo, organizada por estudiante y ordenada cronológicamente.

Cassandra es un motor diseñado para escribir enormes volúmenes de datos a alta velocidad, distribuidos entre múltiples servidores. Es la elección habitual en sistemas que reciben millones de eventos por segundo.

- En el contexto universitario el volumen de notificaciones es de miles por hora (la UNI tiene aproximadamente 12 000 estudiantes de pregrado), no millones. La complejidad operativa de administrar un clúster Cassandra (varios servidores coordinados, configuración de replicación, compactaciones periódicas de datos) no se justifica para ese volumen.
- Las consultas de auditoría que filtran por tipo de notificación o por rangos de fechas son costosas en Cassandra si esas columnas no forman parte de la clave de partición.
- Cassandra no tiene mecanismo de integridad referencial: la referencia al turno o al estudiante en el historial debe validarse en la aplicación, no en el motor.

**Alternativa C — Motor relacional (PostgreSQL) *(solución adoptada)***

El historial de notificaciones como una tabla con columnas fijas: `estudiante_id`, `turno_id`, `tipo`, `mensaje`, `estado`, `enviada_at`. Las preferencias como una tabla relacionada por `estudiante_id`.

- Las consultas de auditoría y reportes se escriben en SQL estándar.
- La relación entre la notificación, el estudiante y el turno está garantizada por **claves foráneas** (*foreign keys*: restricciones que el motor impone para asegurar que un registro no pueda referenciar a un estudiante o turno que no existe).
- El campo de contenido variable por tipo de notificación se almacena como JSONB, un tipo de PostgreSQL que guarda JSON pero permite indexarlo y consultarlo sin perder las garantías del motor relacional.
- El volumen esperado (miles de registros diarios) no requiere ninguna técnica especial de escalado.
- Coexiste con el resto del esquema ya en PostgreSQL sin añadir complejidad operativa.

---

**Decisión adoptada:** Alternativa C.

**Trade-offs aceptados:**

| Trade-off | Descripción |
|---|---|
| Payload variable en JSONB | Los campos específicos por tipo de notificación se guardan en una columna JSONB. PostgreSQL los indexa eficientemente; no se pierde capacidad de consulta. |
| Crecimiento de la tabla a largo plazo | Para el volumen universitario no se necesita particionar. Si el sistema crece, se puede aplicar particionamiento mensual en PostgreSQL sin cambiar el motor. |

## M5 — Seguimiento

### Caso de uso y atributos de calidad

Los casos de uso centrales son **CU01 – Consultar estado del turno**, **CU02 – Consultar posición en cola** y **CU03 – Consultar historial de turnos**. El caso **CU04 – Registrar evento para auditoría** exige que todos los cambios de estado queden trazados (RF-M5-04, RF-M5-05). Las actualizaciones en tiempo real se entregan al estudiante por WebSocket.

| Atributo | Medida clave |
|---|---|
| Disponibilidad | 0 pérdida de historial; el historial debe ser consultable aunque el WebSocket esté caído |
| Rendimiento | Consulta de estado < 2s; posición en cola < 2s |
| Seguridad | 100% de acciones auditables; un estudiante no puede consultar el historial de otro |

---

### ADR-9.1-M5-001: Motor de persistencia para historial de eventos y estado del turno

**Decisión:** PostgreSQL como único motor de persistencia. El estado en tiempo real se entrega por WebSocket, no por un motor adicional.

---

**Contexto:**

M5 no tiene escrituras propias: consume los datos que ya generan M2 y M3. La tabla `turnos` registra todas las transiciones de estado con sus timestamps (`ingresado_at`, `llamado_at`, `confirmado_at`, `cancelado_at`). El módulo expone esa información al estudiante de dos formas:

- **Consulta bajo demanda:** el estudiante abre la pantalla de ticket y ve su estado actual; el backend consulta PostgreSQL.
- **Actualización en tiempo real:** cuando el estado cambia (por ejemplo, el turno pasa a LLAMADO), el backend notifica al frontend a través de una conexión WebSocket que ya está establecida; no se necesita un motor adicional para esto.

---

**Alternativas evaluadas:**

**Alternativa A — Motor clave/valor (Redis) para el estado en tiempo real**

El estado actual del turno de cada estudiante se guarda en Redis para servirlo con latencia mínima. Cuando el estado cambia, se actualiza en Redis además de en PostgreSQL.

Redis vive en memoria RAM y devuelve cualquier valor en tiempo constante, sin importar cuántos registros tenga. Esto lo hace ideal para cachés de alta frecuencia.

- Añadiría un segundo motor cuyo único beneficio sería reducir la latencia de la consulta de estado de ~20ms (PostgreSQL indexado) a ~1ms (Redis). Para una pantalla de ticket en una app móvil universitaria, esa diferencia no es perceptible para el usuario.
- Introduciría el problema de sincronización: habría dos fuentes de verdad (PostgreSQL y Redis) que podrían desincronizarse si una escritura falla a mitad del camino.
- Las actualizaciones en tiempo real ya se resuelven con WebSocket, que empuja el cambio al frontend en el instante en que ocurre. Redis no aporta nada a este mecanismo.

**Alternativa B — Motor columnar (Cassandra) para el historial de eventos**

El historial de transiciones de estado como una tabla cronológica, particionada por `turno_id`.

Cassandra organiza los datos en particiones que se distribuyen entre varios nodos. Es eficiente para leer todos los eventos de un `turno_id` en orden cronológico.

- El volumen de eventos de turno en un comedor universitario de ~12 000 estudiantes de pregrado (decenas de miles de eventos por día como máximo) no justifica un clúster distribuido con toda su complejidad de administración.
- Las consultas de auditoría que cruzan múltiples turnos o múltiples estudiantes son costosas en Cassandra.
- El historial ya está implícito en la tabla `turnos` mediante los campos de timestamp: `ingresado_at`, `llamado_at`, `confirmado_at`, `cancelado_at`. No se necesita una tabla de eventos separada ni un motor distinto.

**Alternativa C — Motor relacional (PostgreSQL) *(solución adoptada)***

Todo el historial de M5 se deriva de la tabla `turnos`, que ya existe en PostgreSQL. El estado en tiempo real se entrega por WebSocket sin ningún motor adicional.

- El historial de cada turno está completamente representado por los timestamps que `turnos` ya almacena: cuándo entró a la cola, cuándo fue llamado, cuándo confirmó, cuándo fue cancelado.
- Las consultas de posición en cola (`COUNT(*) WHERE estado = 'ESPERANDO' AND numero_turno < X`) son simples y están cubiertas con el índice `idx_turnos_dia` definido en la migración.
- No se introduce ningún motor adicional: M5 es un módulo de lectura pura sobre datos que ya persiste M3.

---

**Decisión adoptada:** Alternativa C.

**Trade-offs aceptados:**

| Trade-off | Descripción |
|---|---|
| Dependencia del WebSocket para tiempo real | Si la conexión WebSocket se interrumpe, el estudiante no recibe actualizaciones automáticas. La pantalla de ticket tiene un mecanismo de reconexión automática y puede refrescarse manualmente consultando PostgreSQL directamente. |
| Sin caché para la posición en cola | La posición se calcula en cada consulta con un `COUNT` en PostgreSQL. Para el volumen universitario esto es instantáneo; si el sistema escalara a decenas de miles de estudiantes simultáneos, se podría agregar un contador en Redis sin cambiar la arquitectura del módulo. |

---

## Convivencia de motores

El sistema adopta persistencia políglota con una regla simple:

- **PostgreSQL** es la fuente de verdad de todos los módulos. Ningún dato de negocio vive exclusivamente fuera de PostgreSQL.
- **Redis** es auxiliar y exclusivo de M1. Almacena sesiones activas y tokens revocados con TTL automático. Si Redis pierde su contenido, el único efecto es que los estudiantes deben iniciar sesión de nuevo; no se pierde ningún dato de negocio.
- M4 y M5 usan únicamente PostgreSQL.
