## M2 — Gestión de Colas

### Contexto del módulo

El módulo de Gestión de Colas es responsable de administrar de forma estructurada las colas virtuales, organizando el ingreso de los estudiantes, respetando las políticas de estricto orden de llegada (FIFO), controlando la capacidad máxima dispuesta y actualizando la disponibilidad de cupos en tiempo real para todos los estudiantes solicitantes. La demanda de este módulo se caracteriza por picos de extrema concurrencia durante los periodos de habilitación del servicio de comedor, demandando una estructura capaz de evitar condiciones de carrera, sobresuscripción y cuellos de botella sin interrumpir el funcionamiento fluido de la API.

**Atributos de calidad prioritarios:**

| Atributo | Medida clave |
|---|---|
| Escalabilidad | Soporte de alta concurrencia sin pérdida de solicitudes; degradación < 5% en hora pico. |
| Rendimiento | Respuesta de registro en cola < 2s; Actualización de disponibilidad en tiempo real (< 1s). |
| Confiabilidad | 0% duplicidad; preservación del orden FIFO estricto; prevención de errores y caída del estado. |
| Seguridad | Validar 100% que las solicitudes pertenezcan a sesiones validadas (vía M1). |

**Volumen y concurrencia esperados:** Alta avalancha de peticiones HTTP concurrentes durante las horas programadas para solicitar turnos de almuerzo y cena; requerimiento de actualizaciones atómicas ultra rápidas y respuestas rápidas.

---

### Patrones aplicables

#### Categoría de Módulo: Capas (Layered)

El módulo M2 se organiza internamente dividiendo sus responsabilidades en cuatro capas lógicas específicas:

- **Capa de API:** Proporciona los endpoints REST en FastAPI a través de los cuales la aplicación móvil realiza la petición de registro, consultas de estado en la cola o disponibilidad de cupos. 
- **Capa de Lógica de Cola:** Ejecuta la lógica de dominio. Concentra al Validador de Restricciones (ej. evitar múltiples registros o turno activo previo), la validación de capacidad del comedor y la instrumentación para encolar al usuario de acuerdo al orden FIFO.
- **Capa de Integración de Redis:** Contiene la gestión específica de estructuras atómicas de muy baja latencia, incluyendo el Redis Sorted Set para el mantenimiento del orden de llegada (Score = Time) y la ejecución segura de scripts de Lua.
- **Capa de Persistencia:** Accede de forma delegada a PostgreSQL para la salvaguarda de históricos, estado auditable y registro persistente del ingreso.

**Justificación:**
Dado que este módulo prioriza altamente la *Confiabilidad* y la *Escalabilidad*, segmentar en capas asegura que la lógica crítica de negocio (como asegurar que no haya duplicidad ni sobresuscripción) esté disociada de las estructuras específicas de datos o red. Si en un futuro es imperativo reemplazar Redis por otra solución in-memory, la Capa de Lógica de Cola queda absolutamente intacta. Esto favorece fuertemente la mantenibilidad del módulo.

---

#### Categoría de Componente y Conector: Cliente-Servidor

La forma en que las interacciones ocurren con M2 está fuertemente basada en un esquema clásico Request-Response entre un cliente y un recurso centralizado.

- La App Móvil (Estudiante) funge como cliente que emite una solicitud síncrona HTTP hacia el API de colas para solicitar el registro.
- El servidor ejecuta la validación, ingresa al usuario, resta un cupo y responde confirmando o rechazando la operación.

**Justificación:**
La operación de solicitud de acceso a una cola virtual requiere retroalimentación directa y aseguramiento transaccional de cara al usuario. Un estudiante debe saber de forma inequívoca en su dispositivo móvil si pudo acceder o no. Este requerimiento cancela de facto patrones asíncronos o descentralizados como Pub/Sub y P2P para la interacción inicial. Se requiere el patrón Cliente-Servidor. *(No se elabora un ADR ya que no existe una alternativa real al manejo asíncrono para este flujo primario de registro).*

---

#### Categoría de Asignación: Multi-Tier

El módulo se ajusta a una segmentación en tres tiers físicos bien delimitados:

- **Tier de Presentación:** El dispositivo móvil donde corre la app de React Native y la infraestructura de proxy/balanceo HTTP.
- **Tier de Aplicación:** El contenedor corriendo el proceso FastAPI y sus workers para procesar las validaciones.
- **Tier de Datos:** A su vez segmentado en un almacén de in-memory rápido para estados operativos transitorios (Redis) y un RDBMS persistente (PostgreSQL) para datos finales y consistencia.

**Justificación:**
El atributo de Seguridad requiere que los motores donde se dictamina el acceso y persistencia estén aislados del mundo externo, comunicándose estrictamente a través del Tier de Aplicación validado y autenticado. Por otro lado, la segmentación Tier de Datos mejora sustancialmente el rendimiento ya que posibilita optimizar Redis independientemente de PostgreSQL.

---

### Combinación de patrones (M2)

```
Multi-Tier (asignación)
  └── Capas (organización interna)
        └── Cliente-Servidor (interacción síncrona para ingreso/lectura)
```

## M3 — Gestión de Turnos

### Contexto del módulo

El módulo Gestión de Turnos toma control del estudiante una vez validado dentro de la cola virtual. Es el cerebro detrás del ciclo de vida de un turno. Sus responsabilidades son generar la asignación en bloques de horario, marcar los turnos como activos, posibilitar la confirmación manual de la asistencia, y, en caso el tiempo venza, registrar la expiración para liberar el cupo. Conlleva la pesada tarea de ser fuente de la verdad para M4 (Notificaciones), M5 (Seguimiento) y M6 (Reasignación).

**Atributos de calidad prioritarios:**

| Atributo | Medida clave |
|---|---|
| Confiabilidad | 0% inconsistencia en estados, trazabilidad y manejo impecable del ciclo de vida (turnos asignados vs. expirados). |
| Rendimiento | < 2s de respuesta para generación, < 3s para actualizaciones y confirmaciones. |
| Escalabilidad | Mantener consistencia concurrente sin duplicar información bajo picos de carga. |
| Seguridad | Certeza y encriptación en las validaciones, previniendo que estudiantes confirmen turnos ajenos. |

**Volumen y concurrencia esperados:** Alta intensidad en generación inicial de turnos seguido de intervalos masivos de confirmación por horario, donde cientos de estudiantes reaccionarán a la activación de su turno.

---

### Patrones aplicables

#### Categoría de Módulo: Capas (Layered)

La estructura interna de M3 cuenta con las siguientes capas:

- **Capa de API:** Expone los controladores para invocar generación y permitir las confirmaciones de asistencia del cliente.
- **Capa de Lógica de Turnos:** Concentra las reglas y el núcleo de transición de estados de la Máquina de Estados del turno, garantizando que el flujo ASIGNADO → ACTIVO → CONFIRMADO (o NO_CONFIRMADO) no se violente.
- **Capa de Coordinación de Eventos:** Encargada de acoplar y enviar información de estos cambios de estado hacia las colas MQ, disociando las dependencias. 
- **Capa de Persistencia:** Maneja sentencias ACID con PostgreSQL para asegurar que las mutaciones de estados no se corrompan y la persistencia de timers efímeros en Redis.

**Justificación:**
Disociar la máquina de estados de negocio (Lógica de Turnos) del cómo se alerta al mundo exterior (Capa de Coordinación) es clave para cumplir con la *Confiabilidad*. Si la conectividad hacia RabbitMQ sufre intermitencia, el corazón que garantiza que un turno cambie correctamente de estado debe mantener su cohesión y operación normal sin emborronar el código.

---

#### Categoría de Componente y Conector: Pub/Sub y Cliente-Servidor

El M3 requiere emplear dos patrones paralelos debido a la naturaleza mixta de su dominio:
1. **Cliente-Servidor:** Para las respuestas directas a las acciones del estudiante, fundamentalmente la "Confirmación de asistencia", que requiere respuesta síncrona en el dispositivo móvil indicando el éxito.
2. **Pub/Sub:** Para advertir al resto del ecosistema que algo del turno varió (Activación, Asignación, Expiración).

**(Ver ADR a continuación para el sustento de la elección de coordinación)**.

---

#### Categoría de Asignación: Multi-Tier

Idéntico y unificado al módulo M2; se aloja como parte del monolito centralizado en el Tier de Aplicación de FastAPI. La unificación con M2 brinda el atributo de *Rendimiento*, ya que el M2 invoca a la generación en M3 mediante una llamada local que se apoya en el mismo Tier de Datos sin incurrir en peticiones costosas por red intra-cluster.

---

### ADR: Patrón de comunicación para el ciclo de vida del turno

**Categoría de decisión:** Modelo de Coordinación — elección de patrón de Componente y Conector.

**Contexto:**
El M3 regula estados que impactan a casi toda la aplicación. Cuando M3 marca un turno como `ACTIVO`, el M4 debe notificar y el M5 debe actualizar el seguimiento. Cuando el turno de un usuario es marcado `NO_CONFIRMADO`, M2 debe reponer el cupo y M6 debe ofrecerlo a otro alumno en cola. ¿De qué forma orquesta el M3 la comunicación masiva y multiradial de su estado a todos estos subsistemas dependientes sin ahogarse bajo la presión en una hora pico?

**Alternativas:**
1. **Cliente-Servidor Síncrono Directo:** M3, tras cambiar su estado, llama mediante librerías/requests HTTP internos al servicio/módulo M4, a M5, M6 y a M2.  
   - *Ventajas:* Simple y permite tener certeza (tracing simple) si todos los módulos tomaron la instrucción.
   - *Desventajas:* Acoplamiento extremo y fragilidad. Si el M4 está en proceso de reinicio o saturado, M3 experimentará timeouts o tardanza, perjudicando la liberación real del cupo o fallando el API request general. 
2. **Publicar-Suscribir (Pub/Sub) con RabbitMQ:** M3 actúa meramente como Productor. Publica eventos abstractos del dominio (`turn_assigned`, `turn_active`, `confirm_required`, `turn_expired`). Los módulos interesados (M4, M5, M6, M2) se suscriben de manera independiente a las colas MQ vinculadas y consumen a su propio ritmo.

**Criterios de Elección:**
- **Desacoplamiento:** M3 no debería estar enterado de la existencia de sistemas de notificación o rastreo.
- **Resiliencia (Disponibilidad):** M3 no puede degradar o tirar abajo el ciclo de turno por problemas en servicios satélite.
- **Extensibilidad:** Agregar un módulo estadístico en el futuro no debe obligar a recompilar o alterar M3.

**Decisión:**
Se utiliza un modelo de **Publicar-Suscribir (Pub/Sub) asíncrono** usando RabbitMQ para la coordinación del ciclo de vida del turno hacia el resto del sistema, mientras las entradas manuales de usuario utilizan el formato síncrono.

**Sustento:**
El Pub/Sub erradica el acoplamiento temporal y lógico. M3 cumple eficientemente con ejecutar la transición del turno en la BD Principal y simplemente despacha el anuncio a la red de mensajes. Al poseer RabbitMQ como un componente de middleware ya incorporado al stack tecnológico general, abrazar el patrón para eventos mutables del turno aporta garantías inmensas para los escenarios de alto rendimiento y robustez de todo el proyecto, facilitando en iteraciones posteriores el desarrollo o mantenimiento del módulo M6 Reasignación de manera cien por cien aislada.

---

### Combinación de patrones (M3)

```
Multi-Tier (asignación)
  └── Capas (organización interna)
        ├── Cliente-Servidor (respuesta a confirmaciones del usuario)
        └── Pub/Sub (coordinación reactiva del ciclo de vida con otros módulos)
```
