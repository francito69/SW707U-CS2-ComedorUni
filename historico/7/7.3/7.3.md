# 7.3. Módulo 3 / Integrante 3

## Módulos asignados:

- Módulo de reasignación
- Módulo de configuración

---

## Modulo de Reasignación (M6)

El proceso comienza cuando los módulos de origen (como el API de Turnos) generan eventos de liberación de cupos, publicando mensajes como `CupoLiberado` o `TurnoExpirado` en el **Message Broker** (RabbitMQ o Kafka). Con esta implementación, la lógica pesada de buscar estudiantes en espera y reasignar cupos no bloquea la API principal: el **Worker de Reasignación** procesa estos eventos en segundo plano de forma sistemática y asíncrona.

Luego, el Worker de Reasignación ejecuta la validación y selección del candidato elegible respetando estrictamente el orden FIFO de la cola. Para esto, interactúa directamente con la **BD Reasignación y Cola** (PostgreSQL) aplicando un bloqueo transaccional excluyente sobre las filas involucradas, asegurando que un mismo cupo no pueda ser asignado a dos estudiantes concurrentemente. En caso de fallas transitorias o indisponibilidad de datos, el worker no pierde la petición, sino que deriva los mensajes a una **Dead Letter Queue (DLQ)** para aplicar políticas de reintento idempotente con seguridad.

Una vez que la asignación se completa con éxito y se commitea en la base de datos, el Worker reacciona publicando un evento `TurnoReasignadoExitamente` de vuelta al broker. Este evento es consumido pasivamente por módulos satélites, como el Módulo de Notificaciones, para despachar el aviso final al estudiante celular.

En comparación con un esquema de reasignación síncrona monolítica alojada en el mismo hilo HTTP, los cambios más relevantes son: la separación de responsabilidades hacia workers dedicados en background, la coordinación mediante mensajería (protegiendo a la API de cuellos de botella) y la resiliencia contra colisiones de concurrencia mediante bloqueos transaccionales aislados. Esto refleja de forma directa nuestras decisiones de diseño y el patrón de comunicación **Publicar-Suscribir (Pub/Sub)** combinado con arquitectura **Multi-Tier**, garantizando la altísima disponibilidad y escalabilidad que se requiere para los picos de demanda.

## Modulo de Configuración (M7)

El proceso comienza cuando el Administrador accede a la **Web App Administrativa** (React/TypeScript) para modificar parámetros críticos del sistema, como los aforos máximos del comedor o los tiempos límite por bloque horario. El cliente web envía la nueva solicitud de configuración mediante llamadas HTTP síncronas hacia la **API de Configuración**, actuando como el portón blindado y exclusivo para estas autorizaciones.

Luego, la API de Configuración asume la validación de coherencia de las reglas y verifica los perfiles de acceso. Al validarse, la regla se persiste en la **Base de Datos de Configuración** (PostgreSQL) implementando un modelo que guarda historiales de vigencia y de auditoría (quién hizo qué y en qué momento), erigiéndose como la única "fuente de la verdad". De inmediato, surge el desafío de rendimiento: para evitar que otros módulos saturen esta BD con lecturas en cada transacción de turno, la API publica un aviso estratégico llamado `ConfiguracionModificada` en el **Message Broker**.

Este evento de invalidación viaja por el bus de forma instantánea hacia los módulos satélites (p. ej., el de Turnos), instruyéndolos a purgar o actualizar de inmediato sus *cachés locales de lectura* y así empezar a procesar a los estudiantes bajo las nuevas normas operativas.

En comparación con un esquema de configuración dispersa en archivos o uno de evaluación en tiempo real (que ahogaría por latencia a todos los microservicios), los cambios más relevantes son: el aislamiento seguro de la edición en capas exclusivas, la auditoría del ciclo de vida del dato y la propagación optimizada para coordinar las memorias caché sin acoplamiento duro. Esto refleja de forma directa las decisiones de diseño del módulo usando los patrones **Cliente-Servidor** y **Capas** para la administración de seguridad estricta, complementado transversalmente con **Publicar-Suscribir (Pub/Sub)** para garantizar lecturas rápidas sin sacrificar la consistencia global del comedor universitario.
