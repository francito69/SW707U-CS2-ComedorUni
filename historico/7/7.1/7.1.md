# 7.1. Módulo 1 / Integrante 1

## Módulos asignados:

- Módulo de autenticación
- Módulo de notificaciones
- Módulo de seguimiento

---

## Modulo de Autenticación (M1)

El proceso comienza cuando el Estudiante accede a la App Móvil (React Native) e inicia el flujo de autenticación enviando la solicitud al login de Google. Con esta implementación, la autenticación no depende de un sistema de credenciales propio: el API Backend (FastAPI, Python) recibe la solicitud y coordina la ejecución completa del módulo de forma síncrona.
Luego, el API Backend delega la validación y gestión de identidad al Servicio de Autenticación, que opera en dos frentes de forma paralela. Por un lado, consulta al Servicio de Scraping para obtener los datos personales oficiales del estudiante desde el portal Intranet UNI; el scraping retorna esos datos al Servicio de Autenticación, que los usa para buscar, crear o actualizar el perfil del usuario en la Base de Datos Principal (PostgreSQL). Por otro lado, el Servicio de Autenticación coordina con el Servicio de Biometría: le envía tanto la foto oficial obtenida del scraping como la foto capturada por el usuario, y el Servicio de Biometría realiza la comparación de rostros para confirmar que la identidad declarada corresponde al estudiante físico que está autenticándose.
Una vez validada la identidad, el Gestor de Tokens JWT genera el access token y el refresh token. El refresh token se persiste en Redis Sesiones para su gestión, y Redis también es consultado para verificar la blacklist antes de validar cualquier token activo. Ante una solicitud de logout, el API Backend instruye al Gestor de Tokens JWT a invalidar el token correspondiente. Finalmente, la App Móvil recibe los tokens y los almacena de forma segura en el dispositivo.
En comparación con un esquema de autenticación tradicional por usuario y contraseña, los cambios más relevantes son: delegación de la verificación de identidad al proveedor institucional (Google + Intranet UNI), incorporación de validación biométrica como capa adicional de seguridad, y separación explícita de responsabilidades entre el Servicio de Autenticación, el Servicio de Biometría y el Gestor de Tokens JWT. Esto refleja de forma directa las decisiones de diseño del módulo y el patrón Cliente-Servidor con organización interna en Capas, que implementa la verificación síncrona a través del middleware del API Backend dentro del monolito.

## Modulo de Notificaciones (M4)

El proceso comienza cuando los módulos productores generan eventos en la **Cola RabbitMQ**: el **M3 Gestor de Estado de Turno** publica los eventos `turn_assigned` y `confirm_required`, mientras que el **M6 Orquestador de Reasignación** publica los eventos `user_removed` y `turn_reassigned`. Con esta implementación, el despacho de notificaciones ya no depende de un flujo síncrono bloqueante: el **M4 Orquestador de Notificaciones** consume los eventos de forma asíncrona desde RabbitMQ y coordina la ejecución completa del módulo.

Luego, el orquestador consulta al **M4 Gestor de Preferencias** para conocer los canales y configuraciones de notificación del estudiante, y envía el payload de notificación al **M4 Despachador de Notificaciones**, que también recibe los datos de preferencia directamente desde el Gestor de Preferencias. Con ambas entradas, el Despachador determina el canal de entrega apropiado y envía la notificación al **Servicio Push Notifications** (OneSignal), que se encarga de entregar la notificación al dispositivo del estudiante a través de la **App Móvil** (React Native).

Además del despacho, el Despachador envía el registro de envío con su estado al **M4 Registro de Notificaciones**, que persiste los logs de notificaciones en la **Base de Datos Principal** (PostgreSQL), reforzando la trazabilidad y el historial operativo del módulo. Las preferencias del estudiante también quedan persistidas en la misma base de datos y son consultadas por el Gestor de Preferencias en cada despacho.

En comparación con una arquitectura de notificación síncrona directa, los cambios más relevantes son: coordinación por eventos mediante un broker (RabbitMQ), separación explícita de responsabilidades entre el Orquestador, el Gestor de Preferencias, el Despachador y el Registro, y mayor trazabilidad operativa mediante el log de estado de cada envío. Esto refleja de forma directa las decisiones de diseño del módulo y el patrón **Publicar-Suscribir** documentado en la actividad de patrones de arquitectura, que implementa la coordinación asíncrona mediante RabbitMQ como broker de mensajes.

## Módulo de Seguimiento (M5)

El proceso comienza cuando el **Estudiante** usa la **App Móvil** (React Native) para consultar el estado de su turno. El flujo opera en dos modalidades complementarias: consulta bajo demanda y actualización en tiempo real.

Para la **consulta bajo demanda**, la App Móvil envía un `request estado` al **API Backend** (FastAPI, Python), que delega la consulta al **Servicio Seguimiento**. Este servicio lee el estado actualizado de la cola desde **Redis Cola** y, una vez obtenida la información, guarda los cambios relevantes en la **Base de Datos Principal** (PostgreSQL), desde donde también puede leer el historial completo de eventos del turno. El API Backend responde con un `push update` a la App Móvil con el estado actual.

Para las **actualizaciones en tiempo real**, la App Móvil establece una conexión WebSocket con el API Backend. El **RealTime Channel** se suscribe a este WebSocket y recibe eventos en tiempo real emitidos por el **Servicio Seguimiento**. A su vez, Redis Cola alimenta al RealTime Channel con el estado más reciente de la cola, permitiendo que cualquier cambio relevante se propague de forma inmediata al dispositivo del estudiante sin necesidad de que este realice una nueva consulta.

Además, el módulo también actúa como consumidor de eventos externos: el **M3 Gestor de Estado de Turno** publica eventos de turno en la **Cola RabbitMQ**, y el **Servicio Seguimiento** publica y consume esos eventos para mantener su estado interno sincronizado con el resto del sistema, garantizando consistencia entre lo que el estudiante ve y lo que ocurre en los módulos transaccionales.

En comparación con un esquema de consulta puramente por polling, los cambios más relevantes son: incorporación de un canal en tiempo real mediante WebSocket, separación entre el estado operativo en Redis y el historial persistente en PostgreSQL, y sincronización asíncrona con módulos externos a través de RabbitMQ. Esto refleja de forma directa las decisiones de diseño del módulo y la combinación de patrones **MVC** para la interfaz de consulta y **Publicar-Suscribir** para la ingesta de eventos, documentados en la actividad de patrones de arquitectura.
