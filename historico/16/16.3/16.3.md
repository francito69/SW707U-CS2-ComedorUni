# 16.3. Módulo 3 / Integrante 3

**Módulos cubiertos:** M6 – Reasignación de Turnos · M7 – Configuración Operativa

**Transacción principal elegida:** *Actualizar la configuración operativa de un turno* (M7) — `PUT /config/turnos/{tipo}`, implementada de extremo a extremo. Se complementa con el registro de menú (`POST /config/menu`) y se describe el flujo interno de M6 (reasignación), ejercido a través de M3.

---

## Funcionalidad incluida

### Flujo principal — Actualizar configuración de turno (M7)

El administrador modifica los parámetros operativos de un turno (`ALMUERZO` o `CENA`): horarios y aforo. El cambio se valida y persiste en la fuente de verdad (`turnos_config`), que es leída por M2/M3 para abrir cola y generar turnos.

**Entradas:**
- Path: `tipo` (`ALMUERZO` | `CENA`).
- Body JSON (parcial): `hora_apertura`, `hora_inicio`, `hora_cierre`, `raciones_max`, `activo`.

**Salida:**
- `200` con la plantilla resultante (`TurnoConfigResponse`).
- Errores: `400` (tipo no configurable, horas incoherentes o `raciones_max <= 0`), `404` (tipo inexistente).

**Componentes C4 que participan** (ver [15.3](../../15/15.3/15.3.md)):

| Componente C4 | Rol en la transacción |
|---|---|
| Web App Administrativa | Origen de la petición del admin |
| API Backend → `config.router` | Expone `PUT /config/turnos/{tipo}` |
| `config.service` | Valida (whitelist de tipo, `apertura <= inicio <= cierre`, `raciones_max > 0`) y persiste con rollback ante error |
| PostgreSQL (`turnos_config`) | Fuente de verdad; constraints como última línea de validación |

Código: [config/router.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/config/router.py) · [config/service.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/config/service.py) · [config/schemas.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/config/schemas.py).

### Flujo complementario — Registro de menú (M7)

`POST /config/menu` registra el almuerzo/cena con sus platos en `menu_dia`/`menu_platos`, reutilizando el service del módulo de menú (M3). Lo registrado aquí lo consultan los estudiantes vía `GET /menu`.

### Flujo interno — Reasignación (M6)

M6 no expone endpoints: `llamar_siguiente(turno_dia_id)` ([reassignment/service.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/reassignment/service.py)) llama al siguiente grupo de turnos. Se dispara automáticamente cuando un estudiante es atendido (desde `queues/router.py` y `queues/worker.py`), por lo que se demuestra ejecutando el flujo de cola de M2/M3 (`/queue/confirm`).

---

## Criterios de elección

| Criterio | Justificación |
|---|---|
| Valor para el negocio | La configuración operativa (aforo y horarios) determina cuántos estudiantes atiende el comedor y cuándo; sin ella M2/M3 no pueden operar. |
| Cobertura de escenarios de calidad | Ejercita las tácticas de la Sección 2.3: validación de entrada, whitelist de tipo y constraints (ver [14.3](../../14/14.3/14.3.md)). |
| Dependencia de otros módulos | M2 (apertura de cola) y M3 (generación de turnos) **dependen** de `turnos_config`; es la entrada de todo el flujo de turnos. |
| Riesgo técnico acotado | Es síncrona y autocontenida (no requiere broker ni biometría), por lo que es plenamente demostrable en la sustentación. |
| Estado de implementación | Es el flujo de M6/M7 efectivamente implementado y probado en s111 (M6 es interno; la reasignación se demuestra vía M3). |

## Instrucciones de ejecución

### Dependencias

- Docker (para PostgreSQL/Redis/RabbitMQ) y Python 3.11+.
- Backend en [s111-actividad-bosquejo-implementacion/backend](../../s111-actividad-bosquejo-implementacion/backend).

### 1. Levantar infraestructura y backend

```bash
# Desde s111-actividad-bosquejo-implementacion/
docker compose up -d            # postgres (5433), redis (6379), rabbitmq (5672)

# Desde s111-actividad-bosquejo-implementacion/backend/
pip install -r requirements.txt
python run.py                   # uvicorn en http://localhost:8000 (.env fija DB_PORT=5433)
```

La migración [001_init.sql](../../s111-actividad-bosquejo-implementacion/backend/migrations/001_init.sql) siembra `turnos_config` con `ALMUERZO`, `CENA` y `PRUEBA`, y un menú del día — son los **datos de prueba** del flujo.

### 2. Ejecutar la transacción principal

```bash
# Consultar configuración vigente
curl http://localhost:8000/config/turnos

# Actualizar el turno ALMUERZO (transacción principal)
curl -X PUT http://localhost:8000/config/turnos/ALMUERZO \
  -H "Content-Type: application/json" \
  -d '{"hora_cierre": "08:30:00", "raciones_max": 4500, "activo": true}'

# Verificar el cambio persistido
curl http://localhost:8000/config/turnos/ALMUERZO
```

Casos de error demostrables:

```bash
# 400 - horas incoherentes
curl -X PUT http://localhost:8000/config/turnos/ALMUERZO \
  -H "Content-Type: application/json" -d '{"hora_apertura":"09:00:00","hora_cierre":"08:00:00"}'

# 400 - tipo no configurable
curl -X PUT http://localhost:8000/config/turnos/PRUEBA \
  -H "Content-Type: application/json" -d '{"raciones_max": 10}'
```

### 3. Flujo complementario (menú) y verificación del estudiante

```bash
# Registrar menú del día
curl -X POST http://localhost:8000/config/menu \
  -H "Content-Type: application/json" \
  -d '{"fecha":"2026-06-29","comidas":[{"tipo_comida":"ALMUERZO","energia_kcal":1332,"platos":[{"nombre":"ARROZ CHAUFA"}]}]}'

# Lo que ve el estudiante
curl "http://localhost:8000/menu?fecha=2026-06-29"
```

Documentación interactiva disponible en `http://localhost:8000/docs` (Swagger UI).

## Alcance y límites

**Dentro del prototipo:**
- M7: CRUD de plantillas `ALMUERZO`/`CENA` (lectura, lectura por tipo, actualización parcial) con validación completa, y registro/edición/consulta de menú.
- M6: lógica de reasignación (`llamar_siguiente`) operativa e idempotente, ejercida por el flujo de cola.
- Persistencia directa en PostgreSQL (fuente de verdad).

**Fuera del prototipo (diseño, ver [15.3](../../15/15.3/15.3.md)):**
- Autenticación/autorización de administrador (hoy los endpoints de M7 se exponen sin auth — ver [13.3](../../13/13.3/13.3.md)).
- Caché Redis (Cache-Aside) de `turnos_config` e invalidación dirigida.
- DLQ y reintentos del worker de reasignación; `FOR UPDATE SKIP LOCKED`.
- Réplicas, balanceador, réplica standby de PostgreSQL y gateway TLS.

Estos quedaron fuera por ser optimizaciones de rendimiento/HA y controles de seguridad cuyo valor se demuestra en el diseño, no en el flujo funcional mínimo.
