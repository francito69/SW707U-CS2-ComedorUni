# 16.2. Módulo 2 / Integrante 2

**Módulos cubiertos:** M2 – Gestión de Colas · M3 – Gestión de Turnos

**Transacción principal elegida:** *Encolarse en el turno activo* (M2) — `POST /queue/join`, implementada de extremo a extremo. Encadena con M3 (generación del turno) y con la consulta de estado (`GET /queue/status`) y la confirmación (`POST /queue/confirm`).

---

## Funcionalidad incluida

### Flujo principal — Encolarse en el turno activo (M2/M3)

El estudiante autenticado solicita un turno: el sistema valida su sesión y elegibilidad, verifica el aforo disponible, lo inserta en la cola en orden FIFO y genera su turno (M3).

**Entradas:**
- `POST /queue/join`: `sid`.

**Salida:**
- `200` con `numero_turno`, `tipo`, `posicion`, `raciones_restantes`, `mensaje`.
- Errores: `400` (no hay turno activo / aforo agotado), `401` (sid inválido), `404` (estudiante no registrado), `409` (ya tiene turno activo hoy), `503` (turno no habilitado por el admin).

**Componentes C4 que participan** (ver [15.2](../../15/15.2/15.2.md)):

| Componente C4 | Rol en la transacción |
|---|---|
| App Móvil | Origen de la solicitud de ingreso |
| API Backend → `queue.router` | Expone `/queue/join`, `/status`, `/confirm`, `/leave` |
| Validador de Restricciones → Redis (sesión) | Valida `sid` y elegibilidad (sin turno activo) |
| Control de Capacidad | Verifica aforo disponible del `turno_dia` |
| Gestor FIFO / Generador de Turno (M3) | Asigna `numero_turno` y crea el turno |
| PostgreSQL (`turnos`, `turno_dia`) | Persiste el turno; índice único `idx_turnos_activo` impide duplicados |

Código: [queues/router.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/router.py) · [queues/service.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/service.py) · [queues/worker.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/worker.py).

### Flujos encadenados — M3

- **Estado:** `GET /queue/status?sid=...` devuelve posición, turno actual y estado.
- **Confirmación:** `POST /queue/confirm` pasa el turno a `ATENDIDO` y dispara la reasignación del siguiente grupo (M6).
- **Inactividad:** el worker cancela turnos `LLAMADO` sin ping en 3 min (heartbeat `ultimo_ping`).

## Criterios de elección

| Criterio | Justificación |
|---|---|
| Valor para el negocio | Encolarse es la función central del comedor: ordena la atención de miles de estudiantes. |
| Frecuencia de uso | Es la operación más frecuente del sistema en hora punta. |
| Cobertura de escenarios de calidad | Ejercita consistencia (FIFO, sin duplicados), atomicidad y aforo de la Sección 2. |
| Dependencia de otros módulos | Consume la sesión de M1 y la configuración de M7; alimenta a M4/M5/M6 vía eventos. |
| Riesgo técnico | Concentra la lógica de concurrencia y de integridad de la cola; demostrarla valida el núcleo del diseño. |

## Instrucciones de ejecución

### Dependencias

- Docker (PostgreSQL/Redis/RabbitMQ) y Python 3.11+.
- Backend en [s111-actividad-bosquejo-implementacion/backend](../../s111-actividad-bosquejo-implementacion/backend).

### 1. Levantar infraestructura y backend

```bash
# Desde s111-actividad-bosquejo-implementacion/
docker compose up -d            # postgres (5433), redis (6379), rabbitmq (5672)

# Desde s111-actividad-bosquejo-implementacion/backend/
pip install -r requirements.txt
python run.py                   # uvicorn en http://localhost:8000 (.env fija DB_PORT=5433)
```

La migración [001_init.sql](../../s111-actividad-bosquejo-implementacion/backend/migrations/001_init.sql) siembra `turnos_config` y crea el `turno_dia` del día (incluido el turno `PRUEBA`, siempre abierto, ideal para demostrar el flujo).

### 2. Ejecutar la transacción principal

```bash
# Verificar que hay un turno activo
curl http://localhost:8000/queue/active-service

# Encolarse (requiere un sid valido obtenido del login de M1)
curl -X POST http://localhost:8000/queue/join \
  -H "Content-Type: application/json" -d '{"sid":"<sid>"}'

# Consultar posicion y estado
curl "http://localhost:8000/queue/status?sid=<sid>"

# Confirmar presencia (dispara reasignacion del siguiente grupo)
curl -X POST http://localhost:8000/queue/confirm \
  -H "Content-Type: application/json" -d '{"sid":"<sid>"}'
```

> **Datos de prueba:** el `sid` se obtiene del login de M1 ([16.1](../16.1/16.1.md)); el turno `PRUEBA` sembrado permite encolar a cualquier hora. El WebSocket de tiempo real está en `ws://localhost:8000/queue/ws/{sid}`. Documentación interactiva en `http://localhost:8000/docs`.

## Alcance y límites

**Dentro del prototipo:**
- M2: validación de sesión/elegibilidad, control de aforo, encolado FIFO, salida de cola.
- M3: generación de turno, máquina de estados (`ESPERANDO/LLAMADO/ATENDIDO/CANCELADO`), confirmación, worker de inactividad y publicación de eventos `turno.*`.

**Fuera del prototipo (diseño, ver [15.2](../../15/15.2/15.2.md)):**
- Cola en Redis Sorted Set + contadores atómicos (hoy la cola se resuelve sobre PostgreSQL).
- Sync con compensación Redis→PostgreSQL y caché de estado de turno.
- Réplicas con afinidad WebSocket, réplica standby de PostgreSQL y worker con líder único.

Quedaron fuera por ser optimizaciones de rendimiento/HA cuyo valor se demuestra en el diseño, no en el flujo funcional mínimo.
