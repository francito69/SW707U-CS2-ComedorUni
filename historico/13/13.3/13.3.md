# 13.3. Módulo 3 / Integrante 3

**Módulos cubiertos:** M6 – Reasignación de Turnos · M7 – Configuración Operativa

---

## Estado de implementación

**M7 está implementado** en el backend s111. El módulo [`config/`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/config/) tiene router, service y schemas, y está registrado en [`src/main.py`](../../s111-actividad-bosquejo-implementacion/backend/src/main.py); sus endpoints ya figuran en el [`openapi.yaml`](../../s111-actividad-bosquejo-implementacion/backend/openapi.yaml).

**M6 no expone API HTTP propia**: su lógica de reasignación (`llamar_siguiente`) vive en el módulo [`reassignment/`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/reassignment/) pero **se ejecuta de forma automática** desde M2/M3 (la cola), no por un endpoint de administración. Ver detalle abajo.

---

## Endpoints de M7 — Configuración Operativa

M7 expone endpoints HTTP para que el administrador gestione la configuración operativa del comedor. Cubre dos áreas:

1. **Plantillas de turno** (`turnos_config`): horarios y aforo de los turnos `ALMUERZO` y `CENA`. El tipo `PRUEBA` queda fuera (es solo para testing) y no es configurable por estos endpoints.
2. **Menú del día** (`menu_dia` / `menu_platos`): registro del almuerzo/cena con sus platos. Reutiliza el service del módulo de menú (M3) — misma tabla, una sola fuente de verdad —, de modo que lo que el administrador registra aquí lo ven los alumnos vía `GET /menu`.

**Autenticación:** en la implementación actual estos endpoints **no exigen autenticación**, igual que los endpoints de escritura de menú (`POST/PUT /menu`). La estrategia de autorización de administrador (token, rol en sesión) se definirá en la actividad posterior — ver [sección de Autenticación y autorización](#autenticación-y-autorización).

**Persistencia:** la lectura/escritura va directo a PostgreSQL. La capa de caché Redis (Cache-Aside / Proxy — ver [11.3](../../11/11.3/11.3.md)) se incorporará más adelante; aún no está activa en esta versión.

| Método | Ruta | Propósito | Auth |
|---|---|---|---|
| `GET` | `/config/turnos` | Lista las plantillas configurables (ALMUERZO, CENA) | No* |
| `GET` | `/config/turnos/{tipo}` | Consulta la plantilla de un turno | No* |
| `PUT` | `/config/turnos/{tipo}` | Actualiza horarios, aforo y/o estado de un turno (parcial) | No* |
| `GET` | `/config/menu` | Consulta el menú de una fecha (por defecto, hoy en hora Perú) | No* |
| `POST` | `/config/menu` | Registra el menú de una fecha (comidas con sus platos) | No* |
| `PUT` | `/config/menu` | Edita el menú ya registrado de una fecha | No* |

> *Sin auth en esta versión; pasará a `Admin` cuando se defina la autorización.

### Esquemas de request / response

**`GET /config/turnos`**

```json
// Response 200
[
  {
    "id":            1,
    "tipo":          "ALMUERZO",
    "hora_apertura": "06:00:00",
    "hora_inicio":   "07:00:00",
    "hora_cierre":   "08:00:00",
    "raciones_max":  5000,
    "activo":        true
  },
  {
    "id":            2,
    "tipo":          "CENA",
    "hora_apertura": "11:30:00",
    "hora_inicio":   "12:30:00",
    "hora_cierre":   "13:30:00",
    "raciones_max":  5000,
    "activo":        true
  }
]
```

**`PUT /config/turnos/{tipo}`** — actualización parcial; solo se modifican los campos enviados.

```json
// Request — ejemplo: PUT /config/turnos/ALMUERZO
{
  "hora_cierre":  "08:30:00",
  "raciones_max": 4500,
  "activo":       true
}

// Response 200 — plantilla resultante
{
  "id":            1,
  "tipo":          "ALMUERZO",
  "hora_apertura": "06:00:00",
  "hora_inicio":   "07:00:00",
  "hora_cierre":   "08:30:00",
  "raciones_max":  4500,
  "activo":        true
}
```

> Validaciones: el tipo debe ser `ALMUERZO` o `CENA`; las horas deben cumplir `hora_apertura <= hora_inicio <= hora_cierre`; `raciones_max` debe ser mayor a 0.

**`POST /config/menu`**

```json
// Request
{
  "fecha": "2025-06-15",
  "comidas": [
    {
      "tipo_comida":     "ALMUERZO",
      "energia_kcal":    1332.46,
      "lipidos_g":       51.11,
      "proteinas_g":     43.31,
      "carbohidratos_g": 171.35,
      "platos": [
        { "nombre": "SOPA DE FIDEOS" },
        { "nombre": "ARROZ CHAUFA DE CERDO" }
      ]
    }
  ]
}

// Response 201
{
  "fecha": "2025-06-15",
  "comidas": [
    {
      "id":              10,
      "tipo_comida":     "ALMUERZO",
      "energia_kcal":    1332.46,
      "lipidos_g":       51.11,
      "proteinas_g":     43.31,
      "carbohidratos_g": 171.35,
      "platos": [
        { "id": 31, "nombre": "SOPA DE FIDEOS" },
        { "id": 32, "nombre": "ARROZ CHAUFA DE CERDO" }
      ]
    }
  ]
}
```

**`PUT /config/menu?fecha=<fecha>`** — reemplaza las comidas registradas de esa fecha. Mismo cuerpo que `POST` pero sin el campo `fecha` (va en query) y devuelve `200`.

### Códigos de estado por endpoint

| Endpoint | Código | Situación |
|---|---|---|
| `GET /config/turnos` | `200` | Lista de plantillas devuelta |
| `GET /config/turnos/{tipo}` | `200` | Plantilla devuelta |
| `GET /config/turnos/{tipo}` | `400` | Tipo no configurable (solo ALMUERZO/CENA) |
| `GET /config/turnos/{tipo}` | `404` | No existe configuración para el tipo |
| `PUT /config/turnos/{tipo}` | `200` | Actualización exitosa |
| `PUT /config/turnos/{tipo}` | `400` | Tipo no configurable, horas inconsistentes o `raciones_max` <= 0 |
| `PUT /config/turnos/{tipo}` | `404` | No existe configuración para el tipo |
| `GET /config/menu` | `200` | Menú devuelto (comidas vacías si no hay registro) |
| `POST /config/menu` | `201` | Menú registrado |
| `POST /config/menu` | `400` | Comida inválida (tipo no permitido o lista vacía) |
| `POST /config/menu` | `409` | Ya existe un menú para esa fecha |
| `PUT /config/menu` | `200` | Menú actualizado |
| `PUT /config/menu` | `400` | Comida inválida |
| `PUT /config/menu` | `404` | No existe un menú para esa fecha |

## M6 — Reasignación de Turnos (módulo de funciones, sin API)

M6 es un **módulo de funciones internas**: no tiene router ni endpoints, solo expone lógica que otros módulos importan. Por eso no aparece en el `openapi.yaml`.

Su función principal es `llamar_siguiente(turno_dia_id)` en [`reassignment/service.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/reassignment/service.py), que llama al siguiente *grupo* de turnos. La invoca el módulo de cola (M2/M3) de forma automática cuando un alumno es atendido.

**Lógica de batching:** el tamaño de grupo se deriva del aforo, `batch_size = ceil(raciones_max / 10)`. Un "grupo" es el rango de posiciones `[ (grupo-1)*batch_size + 1 , grupo*batch_size ]`. `llamar_siguiente` solo actúa si no hay nadie en `LLAMADO`: toma la posición mínima en `ESPERANDO`, calcula su grupo y pasa todo ese rango a `LLAMADO`.

## Autenticación y autorización

Conceptualmente, los endpoints de M7 son exclusivos del **administrador del comedor** (M6 no expone endpoints). La estrategia de autorización definitiva (token de admin, rol en sesión, etc.) se definirá en la actividad posterior; en el DEMO, M7 verifica el header `x-consumer-username` inyectado por el API Gateway.

En la implementación actual de s111 los endpoints de M7 **aún no aplican esa restricción**: se exponen sin autenticación, siguiendo el mismo patrón que los endpoints de escritura de menú (`POST/PUT /menu`). El control de acceso de administrador se añadirá junto con la estrategia de autorización.
