# 14.5.1. Continuidad y Recuperación

Esta subsección consolida, a nivel de sistema, las decisiones de **continuidad** de todos los módulos (M1–M7) documentadas individualmente en [14.1](../../14.1/14.1.md), [14.2](../../14.2/14.2.md) y [14.3](../../14.3/14.3.md). El objetivo común es que ningún fallo parcial (caída de Redis, del broker, de un worker o del WebSocket) provoque **pérdida de datos de negocio** ni deje el sistema en un estado inconsistente.

## Principio rector

**PostgreSQL es la única fuente de verdad de todo el sistema** (ver [9.1](../../../9/9.1/9.1.md), [9.2](../../../9/9.2/9.2.md), [9.3](../../../9/9.3/9.3.md)). Redis y los canales en tiempo real son capas auxiliares: su pérdida degrada el rendimiento o el tiempo real, pero **nunca** la integridad del dato. Esta regla unifica la estrategia de continuidad de los siete módulos.

## Tácticas transversales de continuidad

| Táctica (Bass et al.) | Dónde se aplica | Estructura C4 | Criterio verificable |
|---|---|---|---|
| **Fuente de verdad persistente + datos auxiliares con TTL** | M1 (sesiones), M2 (estado de cola), M7 (caché config) | `Redis` ⇢ `PostgreSQL` | Detener Redis: 0 datos de negocio perdidos; solo se re-autentica / se lee de PostgreSQL |
| **Degradación elegante (fallback / exception handling)** | M5 (WebSocket → consulta), M7 (Redis → PostgreSQL) | `WebSocket`/`Caché Redis` ⇢ `PostgreSQL` | Cortar la capa auxiliar: la funcionalidad sigue respondiendo `200` desde PostgreSQL |
| **Reintento / clasificación de error (fault recovery)** | M4, M5 (consumers), M6 (worker de reasignación) | `RabbitMQ` + `DLQ` → consumers/worker | Error transitorio → reencolado y reprocesado sin duplicar; mensaje malformado → descartado |
| **Prevención de inconsistencia (ACID + constraints)** | M2/M3 (turnos), M6 (reasignación), M7 (config) | `PostgreSQL` (`idx_turnos_activo`, `FOR UPDATE SKIP LOCKED`, CHECK) | Doble turno activo / doble asignación / config incoherente: rechazados por la BD |
| **Monitoreo por heartbeat (fault detection)** | M3 (worker de inactividad) | `M3 Scheduler` → `PostgreSQL` (`ultimo_ping`) | Turno `LLAMADO` sin ping > 3 min → `CANCELADO` y cupo liberado |
| **Auditoría / recuperación de estado** | M4 (historial notif.), M3/M6 (historial turnos), M7 (versionado config) | `PostgreSQL` (tablas de historial) | Todo cambio crítico es reconstruible a partir de la traza persistida |

## Mapa de continuidad por módulo

| Módulo | Riesgo principal | Respuesta de continuidad | Detalle |
|---|---|---|---|
| M1 – Autenticación | Reinicio de Redis | Re-autenticación; perfil intacto en PostgreSQL; AOF como respaldo | [14.1](../../14.1/14.1.md) |
| M2 – Colas | Falla de sync Redis→PostgreSQL | Compensación / rollback sin pérdida ni duplicado | [14.2](../../14.2/14.2.md) |
| M3 – Turnos | Estado inconsistente / turno abandonado | ACID + máquina de estados + heartbeat | [14.2](../../14.2/14.2.md) |
| M4 – Notificaciones | Push/BD caída | Reintento con clasificación de error; 0 registros perdidos | [14.1](../../14.1/14.1.md) |
| M5 – Seguimiento | WebSocket caído | Fallback a consulta + reconexión automática | [14.1](../../14.1/14.1.md) |
| M6 – Reasignación | Worker cae / concurrencia | DLQ + reintento idempotente; `FOR UPDATE SKIP LOCKED` | [14.3](../../14.3/14.3.md) |
| M7 – Configuración | Corrupción / Redis caído | Persistencia fuerte ACID; degradación a PostgreSQL; versionado | [14.3](../../14.3/14.3.md) |

## Estado de implementación

Implementado en s111: fuente de verdad en PostgreSQL para todos los módulos, sesiones en Redis (M1), worker de inactividad con heartbeat (M3) y publicación de eventos a RabbitMQ. **Pendientes de diseño:** DLQ + reintentos con backoff, snapshots AOF, fallback de caché Redis (M7) y tablas de historial/auditoría dedicadas. Ver notas de "Estado" en cada sección por integrante.
