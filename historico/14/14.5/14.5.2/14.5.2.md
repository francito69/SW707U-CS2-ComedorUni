# 14.5.2. Escalabilidad, Rendimiento y Coordinación

Esta subsección consolida las decisiones de **escalabilidad, rendimiento y coordinación** de los módulos M1–M7 documentadas en [14.1](../../14.1/14.1.md), [14.2](../../14.2/14.2.md) y [14.3](../../14.3/14.3.md). El reto común es sostener los picos de demanda de la apertura de almuerzo/cena (miles de estudiantes concurrentes) sin degradar la latencia ni acoplar los módulos entre sí.

## Principio rector

El sistema separa el **camino caliente** (operaciones de alta frecuencia que deben responder en milisegundos) del **camino frío** (persistencia, auditoría, reasignación). El camino caliente se sirve desde memoria (Redis) y respuestas directas; el camino frío se procesa de forma **asíncrona** mediante el broker (RabbitMQ), de modo que la lógica pesada nunca bloquea la API. Esto materializa el patrón **Publicar-Suscribir** de forma transversal.

## Tácticas transversales de escalabilidad/rendimiento

| Táctica (Bass et al.) | Dónde se aplica | Estructura C4 | Criterio verificable |
|---|---|---|---|
| **Estructuras en memoria / caché de lectura (reduce overhead)** | M1 (sesiones), M2 (Sorted Set + contadores), M5/M7 (caché de estado/config) | `Redis` | Verificación de sesión p95 < 50 ms; ingreso/posición de cola < 5 ms |
| **Desacople asíncrono (Pub-Sub, increase concurrency)** | M3→M4/M6 (eventos `turno.*`), M7→M2/M3 (config) | `RabbitMQ` | El productor no se bloquea; consumo en background; notif < 2 s tras el evento |
| **Procesamiento en background (schedule resources)** | M6 (workers de reasignación), M3 (worker de inactividad) | `Worker de Reasignación` / `M3 Scheduler` | La reasignación e inactividad corren fuera del hilo HTTP; p95 de la API estable |
| **Paralelismo sin contención (`FOR UPDATE SKIP LOCKED`)** | M6 (reasignación con réplicas) | `PostgreSQL` (`turnos`) | K workers escalan ~linealmente; sin esperas por lock mutuo |
| **Push por eventos vs polling (reduce demand)** | M5 (tiempo real) | `RealTime Channel (WebSocket)` | Cambios propagados sin polling; consulta de estado < 2 s |
| **Coordinación de caché (invalidación dirigida)** | M7 → M2/M3 | `Caché Redis` + `RabbitMQ` (`ConfiguracionModificada`) | Tras un cambio de aforo, M2/M3 aplican el nuevo valor sin reinicio; ventana ≤ TTL |

## Mapa de rendimiento por módulo

| Módulo | Escenario de carga | Táctica principal | Umbral objetivo |
|---|---|---|---|
| M1 | Validación de sesión en cada operación | Lectura en memoria (Redis) | p95 < 50 ms |
| M2 | Picos de ingreso/consulta de posición | Redis Sorted Set + contadores atómicos | < 5 ms |
| M3 | Notificar cambios a M4/M6 | Pub-Sub asíncrono | Transacción no bloqueada por el publish |
| M4 | Ráfagas de eventos de turno | Consumo asíncrono desde RabbitMQ | Emisión < 2 s; entrega ≥ 99 % |
| M5 | Muchos estudiantes observando estado | Push por WebSocket | Estado/posición < 2 s |
| M6 | Múltiples expiraciones simultáneas | Workers en background + `SKIP LOCKED` | Throughput ~lineal; API estable |
| M7 | Lectura masiva de configuración | Cache-Aside (Redis, TTL 180 s) | Cache hit sin tocar PostgreSQL |

## Coordinación entre módulos

El flujo de coordinación es uniforme: **M7** define los parámetros operativos y los propaga por evento; **M2/M3** los consumen para abrir cola y generar turnos; **M3** publica los eventos de ciclo de vida que **M4** (notifica), **M5** (sigue) y **M6** (reasigna) consumen. Ningún módulo llama síncronamente a otro para estas tareas: todo se coordina por el broker, lo que permite escalar cada consumidor de forma independiente.

## Estado de implementación

Implementado: WebSocket de tiempo real (M5), verificación de sesión en Redis (M1), publicación de eventos `turno.*` a RabbitMQ (M3) y derivación de `batch_size` (M6). **Pendientes de diseño:** cola en Redis Sorted Set + contadores atómicos (M2), Cache-Aside de configuración (M7), réplicas de workers con `SKIP LOCKED` (M6) y la medición formal de los umbrales p95/latencia.
