# 11.2. Módulo 2 / Integrante 2

**Módulos cubiertos:** M2 – Gestión de Colas · M3 – Gestión de Turnos

---

## Patrón 1 — Singleton *(Creacional)*

### Problema concreto

El `QueueConnectionManager` mantiene el mapa de conexiones WebSocket activas (`codigo → WebSocket`). Para que el sistema funcione, el router (que registra las conexiones cuando el estudiante abre el WebSocket) y el worker (que envía notificaciones cada 60 segundos) deben operar sobre **el mismo mapa**. Si cada módulo instanciara su propio `QueueConnectionManager`, el worker tendría un diccionario vacío y nunca podría notificar a nadie.

### Ubicación en el código

[`src/modules/queues/manager.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/manager.py) — línea final `manager = QueueConnectionManager()`.

Importado por [`src/modules/queues/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/router.py) y [`src/modules/queues/worker.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/worker.py).

### Implementación

```python
# src/modules/queues/manager.py

class QueueConnectionManager:
    def __init__(self):
        self._connections: dict[str, WebSocket] = {}   # estado compartido

    async def connect(self, codigo: str, ws: WebSocket) -> None: ...
    def disconnect(self, codigo: str) -> None: ...
    def is_connected(self, codigo: str) -> bool: ...
    async def send(self, codigo: str, message: dict) -> None: ...

manager = QueueConnectionManager()   # única instancia a nivel de módulo
```

```python
# router.py — registra conexiones
from .manager import manager
await manager.connect(codigo, ws)    # subscribe

# worker.py — notifica a través de la misma instancia
from .manager import manager
await manager.send(codigo, {...})    # notify
```

Python garantiza que la importación de un módulo ocurre una sola vez por proceso; `manager` es resuelto al mismo objeto en ambos archivos.

### Trade-offs aceptados

| Trade-off | Descripción |
|---|---|
| Estado global de proceso | `_connections` vive en memoria del proceso FastAPI. Si el servidor se reinicia, todas las conexiones WebSocket se pierden y los estudiantes reconectan automáticamente al detectar el cierre. Aceptable: la reconexión es inmediata y no implica pérdida de datos (el turno vive en PostgreSQL). |
| No escala a múltiples workers | Si se levantaran varias réplicas del proceso, cada una tendría su propio `manager`. Para el entorno universitario con un único proceso es suficiente. |

## Patrón 2 — Observer *(De comportamiento)*

### Problema concreto

Cuando el worker detecta que es momento de llamar a un grupo de turnos, o cuando un estudiante confirma su turno y el sistema debe avisar al siguiente, es necesario notificar a cada estudiante afectado en tiempo real. El sistema no debe conocer de antemano cuántos estudiantes están conectados ni depender de que estén conectados; la notificación es opcional (si el estudiante no tiene WebSocket abierto, el push de M4 lo cubre).

### Ubicación en el código

- **Subject:** [`src/modules/queues/manager.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/manager.py) — clase `QueueConnectionManager`
- **Registro de observer:** [`src/modules/queues/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/router.py) — endpoint `GET /ws/{sid}`
- **Notificación:** [`src/modules/queues/worker.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/worker.py) y [`router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/router.py) — `manager.send()`

### Implementación

```python
# manager.py — Subject con registro y notificación dirigida
class QueueConnectionManager:
    def __init__(self):
        self._connections: dict[str, WebSocket] = {}

    async def connect(self, codigo: str, ws: WebSocket) -> None:
        await ws.accept()
        self._connections[codigo] = ws      # attach(observer)

    def disconnect(self, codigo: str) -> None:
        self._connections.pop(codigo, None) # detach(observer)

    async def send(self, codigo: str, message: dict) -> None:
        ws = self._connections.get(codigo)
        if ws:
            try:
                await ws.send_json(message) # notify(observer)
            except Exception:
                self.disconnect(codigo)     # auto-detach si la conexión cayó
```

```python
# router.py — suscripción (WebSocket abierto por el estudiante)
@router.websocket("/ws/{sid}")
async def queue_websocket(ws: WebSocket, sid: str):
    codigo = session["codigo"]
    await manager.connect(codigo, ws)       # attach
    try:
        while True:
            msg = await ws.receive_json()
            ...
    except WebSocketDisconnect:
        manager.disconnect(codigo)          # detach

# worker.py — notificación (llamado de turno)
for llamado in llamar_siguiente(turno_dia_id):
    if manager.is_connected(llamado["codigo"]):
        await manager.send(llamado["codigo"], {"type": "llamado", ...})
```

Este Observer es **unicast** (notifica a un destinatario específico por `codigo`) a diferencia del Observer de M4/M5 vía RabbitMQ que es **multicast** (todos los suscriptores a un routing key reciben el mensaje). Ambos implementan el mismo principio de desacoplamiento pero para canales distintos: WebSocket para respuesta inmediata en pantalla, RabbitMQ para entrega garantizada fuera de la app.

### Trade-offs aceptados

| Trade-off | Descripción |
|---|---|
| Notificación no garantizada | Si el estudiante no tiene WebSocket abierto, `manager.send()` no hace nada. Por eso cada `manager.send()` en el worker va acompañado de un `publish("turno.llamado", ...)` a RabbitMQ que dispara el push de M4. Los dos canales son complementarios. |
| Auto-desconexión silenciosa | Si `send()` lanza una excepción (conexión caída sin `WebSocketDisconnect` limpio), el manager ejecuta `disconnect()` internamente. El estudiante no recibe mensaje de error pero reconecta al abrir la app. |
