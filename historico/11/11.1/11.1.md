# 11.1. Módulo 1 / Integrante 1

**Módulos cubiertos:** M1 – Autenticación · M4 – Notificaciones · M5 – Seguimiento

---

## Patrón 1 — Singleton *(Creacional)*

### Problema concreto

M1 necesita un cliente Redis para leer y escribir sesiones en cada request autenticado del sistema. Crear una nueva conexión TCP a Redis en cada llamada es costoso: implica negociación de socket, autenticación y asignación de recursos en el servidor Redis. El cliente debe existir una única vez durante el ciclo de vida del proceso y ser reutilizado por todas las operaciones.

### Ubicación en el código

[`src/modules/auth/redis_store.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/redis_store.py) — función `get_redis()` y variable de módulo `_client`.

### Implementación

```python
# src/modules/auth/redis_store.py

_client: redis.Redis | None = None          # única instancia; None hasta el primer uso

def get_redis() -> redis.Redis:
    global _client
    if _client is None:                     # primera llamada: crea la conexión
        _client = redis.Redis(
            host=os.getenv("REDIS_HOST", "localhost"),
            port=int(os.getenv("REDIS_PORT", "6379")),
            decode_responses=True,
        )
    return _client                          # llamadas siguientes: devuelve la misma instancia
```

El mismo patrón aparece en [`src/shared/rabbitmq.py`](../../s111-actividad-bosquejo-implementacion/backend/src/shared/rabbitmq.py) con `_connection` para la conexión a RabbitMQ.

### Trade-offs aceptados

| Trade-off | Descripción |
|---|---|
| Estado global de módulo | Python no tiene `private` de clase; la variable `_client` es técnicamente accesible desde fuera del módulo. Aceptable porque el módulo es cohesivo y no expone `_client` en su interfaz pública. |
| No es thread-safe en sentido estricto | Si dos hilos evaluaran `_client is None` simultáneamente en el arranque, podrían crear dos conexiones. En la práctica FastAPI usa un único proceso asyncio, por lo que la condición de carrera (race condition) no ocurre. |
| Dificultad para pruebas unitarias | El Singleton hace difícil sustituir el cliente por un mock. Se mitiga inyectando la URL desde variables de entorno, lo que permite apuntar a un Redis de prueba. |

## Patrón 2 — Facade *(Estructural)*

### Problema concreto

El flujo de login involucra tres subsistemas independientes: (1) el parser de HTML que extrae datos del scraping de la Intranet UNI, (2) el repositorio que persiste el perfil del estudiante en PostgreSQL, y (3) el store que crea la sesión en Redis con la foto de ORCE. El cliente (la app React Native) no debe conocer ni depender de cada subsistema por separado; solo necesita enviar el HTML y recibir un `sid` de sesión.

### Ubicación en el código

[`src/modules/auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) — endpoint `POST /parse-data`.

### Implementación

```python
# src/modules/auth/router.py

@router.post("/parse-data", response_model=ParseDataResponse)
def parse_data(data: ParseDataRequest = Body(...)):

    # Subsistema 1: parsing del HTML de ORCE
    result = parse_student_data(data.home_html, data.cursos_html, data.datos_html)

    # Subsistema 2: persistencia del perfil en PostgreSQL (obligatorio — sin esto el encolamiento falla por FK)
    upsert_estudiante(
        codigo=result["codigo"],
        nombres=result["nombres"],
        apellido_paterno=result["apellido_paterno"],
        apellido_materno=result["apellido_materno"],
        email=result["email"],
    )

    # Subsistema 3: creación de sesión en Redis (incluye foto vigente de ORCE)
    sid = str(uuid.uuid4())
    create_session(
        sid=sid,
        codigo=result["codigo"],
        email=result["email"],
        nombre=result["nombre"],
        creditos=result["creditos_llevados"],
        foto_base64=result["foto_base64"],
    )

    return ParseDataResponse(sid=sid, ...)
```

### Trade-offs aceptados

| Trade-off | Descripción |
|---|---|
| El endpoint mezcla orquestación con transporte HTTP | El router hace de coordinador, lo que en arquitecturas más estrictas correspondería a un servicio de aplicación separado. Para el tamaño del proyecto actual es suficiente y evita una capa adicional. |
| Fallo atómico: DB caída impide el login | Si `upsert_estudiante` falla (PostgreSQL no disponible), la excepción propaga y el endpoint devuelve 500. No se crea sesión Redis. Esto es correcto: sin registro en `estudiantes`, cualquier intento de encolamiento fallaría igualmente por violación de clave foránea (`turnos.estudiante_id`). El Facade garantiza que el cliente solo recibe un `sid` cuando todos los subsistemas completaron sin error. |

## Patrón 3 — Observer *(De comportamiento)*

### Problema concreto

Cuando M3 cambia el estado de un turno (`LLAMADO`, `CANCELADO`, `ATENDIDO`), otros dos módulos deben reaccionar:
- **M4** debe enviar una notificación push al estudiante.
- **M5** debe registrar el evento en el historial.

Si M3 invocara directamente a M4 y M5, los tres módulos quedarían acoplados: cualquier cambio en M4 o M5 afectaría a M3. El sistema necesita que M3 emita eventos sin saber quién los consume.

### Ubicación en el código

- **Publicación (sujeto):** [`src/modules/queues/worker.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/worker.py) — `inactivity_worker()` vía [`shared/rabbitmq.py`](../../s111-actividad-bosquejo-implementacion/backend/src/shared/rabbitmq.py) `publish()`
- **Suscriptor M4:** [`src/modules/notifications/consumer.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/notifications/consumer.py) — `_handle()` sobre cola `m4.notificaciones`
- **Suscriptor M5:** [`src/modules/tracking/consumer.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/tracking/consumer.py) — `_handle()` sobre cola `m5.seguimiento`

### Implementación

```python
# src/shared/rabbitmq.py — publicación de evento (rol de Subject)
async def publish(routing_key: str, payload: dict) -> None:
    exchange = await channel.declare_exchange("comedor", ExchangeType.TOPIC, durable=True)
    await exchange.publish(Message(body=json.dumps(payload).encode()), routing_key=routing_key)

# src/modules/queues/worker.py — M3 emite evento sin conocer a M4 ni M5
await publish("turno.llamado", {
    "evento": "turno.llamado",
    "push_token": push_token,
    "numero_turno": numero,
    ...
})

# src/modules/notifications/consumer.py — Observer M4: reacciona enviando push
ROUTING_KEYS = ["turno.llamado", "turno.cancelado"]

async def _handle(message: aio_pika.IncomingMessage) -> None:
    payload = json.loads(message.body)
    title, body = MENSAJES.get(payload["evento"], ...)
    await send_push(token=payload["push_token"], title=title, body=body, ...)

# src/modules/tracking/consumer.py — Observer M5: reacciona registrando historial
ROUTING_KEYS = ["turno.atendido", "turno.encolado"]

async def _handle(message: aio_pika.IncomingMessage) -> None:
    if payload["evento"] == "turno.atendido":
        registrar_asistencia(est_id, td_id, numero_turno, tipo_comida)
    elif payload["evento"] == "turno.encolado":
        registrar_encolamiento(est_id, td_id, numero_turno, tipo_comida)
```

**Relación con GoF:** El patrón GoF original define un vínculo directo Subject→Observer. Aquí RabbitMQ actúa como broker intermediario, lo que es la variante *Publish-Subscribe* del Observer: el Subject no conoce a sus observadores (solo conoce el `routing_key`) y los observadores se suscriben a colas sin conocer al Subject. La intención del patrón —desacoplamiento entre emisor y receptores— se cumple de forma más robusta que en la variante GoF pura: si M4 cae, los mensajes se acumulan en la cola durable y se procesan cuando M4 vuelva.

### Trade-offs aceptados

| Trade-off | Descripción |
|---|---|
| Consistencia eventual | M4 y M5 procesan el evento de forma asíncrona. Hay una ventana breve entre el momento en que M3 cambia el estado y el momento en que M4 envía el push. Para notificaciones de turno llamado (urgentes) esto es aceptable porque RabbitMQ entrega el mensaje en milisegundos bajo carga normal. |
| Infraestructura adicional | El patrón requiere un broker RabbitMQ en ejecución. Si RabbitMQ cae, los eventos no se entregan. Mitigado con colas `durable=True` y `DeliveryMode.PERSISTENT`: los mensajes sobreviven a un reinicio del broker. |
| Dificultad para rastrear el flujo | El control no pasa de M3 a M4/M5 de forma directa, lo que hace más difícil seguir el flujo en depuración. Se mitiga con los logs `[M4]` y `[M5]` en cada consumer. |
