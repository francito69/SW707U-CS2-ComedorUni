# 11.5. Listado Consolidado de Patrones GoF

---

## Tabla consolidada

| Patrón | Categoría | Módulo(s) | Problema resuelto | Ubicación en el código |
|---|---|---|---|---|
| Singleton | Creacional | M1 | Una única conexión Redis reutilizada por todos los requests de autenticación | [`src/modules/auth/redis_store.py`](../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/redis_store.py) — `get_redis()` |
| Singleton | Creacional | M2 | El mapa de conexiones WebSocket debe ser el mismo objeto en el router y en el worker | [`src/modules/queues/manager.py`](../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/manager.py) — `manager = QueueConnectionManager()` |
| Facade | Estructural | M1 | Ocultar al cliente la orquestación de tres subsistemas (parser ORCE, PostgreSQL, Redis) detrás de un único endpoint de login | [`src/modules/auth/router.py`](../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) — `POST /parse-data` |
| Observer (RabbitMQ Pub/Sub) | De comportamiento | M3 → M4, M5 | M3 emite eventos de turno sin conocer a M4 ni M5; cada módulo reacciona de forma independiente | Publisher: [`src/modules/queues/worker.py`](../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/worker.py) · Consumers: [`notifications/consumer.py`](../s111-actividad-bosquejo-implementacion/backend/src/modules/notifications/consumer.py), [`tracking/consumer.py`](../s111-actividad-bosquejo-implementacion/backend/src/modules/tracking/consumer.py) |
| Observer (WebSocket in-process) | De comportamiento | M2, M3 | Notificar en tiempo real a estudiantes conectados cuando su turno es llamado o cancelado | [`src/modules/queues/manager.py`](../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/manager.py) — `QueueConnectionManager` como Subject |
| Proxy (Cache-Aside) | Estructural | M7 | Evitar consultas repetidas a PostgreSQL para la configuración operativa que cambia raramente | Propuesto sobre [`migrations/001_init.sql`](../s111-actividad-bosquejo-implementacion/backend/migrations/001_init.sql) — tabla `turnos_config`; referencia: [`DEMO/main.py`](../0/0.5/0.5.3/0.5.3.3/DEMO/main.py) |
| Template Method | De comportamiento | M6 | Definir el esqueleto fijo del flujo de reasignación (seleccionar → marcar → notificar) dejando el paso de selección de candidato abierto a variaciones por tipo de turno | Propuesto en `src/modules/reassignment/` — `ReasignacionBase` / `ReasignacionFIFO` |

## Distribución por categoría

| Categoría | Patrones |
|---|---|
| Creacional | Singleton ×2 |
| Estructural | Facade, Proxy |
| De comportamiento | Observer ×2, Template Method |

## Distribución por módulo

| Módulo | Patrones aplicados |
|---|---|
| M1 – Autenticación | Singleton (Redis), Facade (login) |
| M2 – Gestión de Colas | Singleton (WebSocket manager), Observer (WebSocket) |
| M3 – Gestión de Turnos | Observer (RabbitMQ publisher), Observer (WebSocket notifier) |
| M4 – Notificaciones | Observer (RabbitMQ consumer) |
| M5 – Seguimiento | Observer (RabbitMQ consumer) |
| M6 – Reasignación | Strategy (selección de candidato) |
| M7 – Configuración | Proxy (Cache-Aside sobre `turnos_config`) |
