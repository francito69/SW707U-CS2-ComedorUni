# 11.3. Módulo 3 / Integrante 3

**Módulos cubiertos:** M6 – Reasignación de Turnos · M7 – Configuración Operativa

> M7 cuenta con una implementación de demostración en [`DEMO/main.py`](../../0/0.5/0.5.3/0.5.3.3/DEMO/main.py). M6 está en etapa de diseño; su patrón se documenta a partir del esquema definido en [`10.3`](../../10/10.3/10.3.md).

## Patrón 1 — Proxy *(Estructural)*

### Problema concreto

M7 almacena la configuración operativa del comedor (aforo, tiempos de confirmación, bloques horarios) en PostgreSQL. Esta configuración es **leída con alta frecuencia** por todos los módulos que necesitan saber los parámetros vigentes (M2 para apertura de cola, M3 para calcular expiración de turnos), pero **se modifica rara vez** (solo cuando un administrador cambia una regla). Consultar PostgreSQL en cada request innecesariamente añade latencia y carga a la base de datos.

### Ubicación en el código

- **Real Subject:** tabla `turnos_config` en PostgreSQL — [`migrations/001_init.sql`](../../s111-actividad-bosquejo-implementacion/backend/migrations/001_init.sql)
- **Proxy:** clave `turnos_config:cache` en Redis con TTL de 180 s
- **Patrón de referencia:** [`DEMO/main.py`](../../0/0.5/0.5.3/0.5.3.3/DEMO/main.py) implementa el mismo Cache-Aside sobre la tabla `configuracion` de la demo

### Implementación propuesta

```python
# Proxy de lectura — Cache-Aside sobre turnos_config

def get_turnos_config():
    # 1. Consultar el Proxy (Redis)
    raw = redis_client.get("turnos_config:cache")
    if raw:
        return json.loads(raw)              # cache hit: no toca PostgreSQL

    # 2. Cache miss → consultar el Real Subject (PostgreSQL)
    cur.execute("SELECT * FROM turnos_config WHERE activo = TRUE")
    configs = cur.fetchall()

    # 3. Rellenar el Proxy para próximas lecturas (TTL 180 s)
    redis_client.setex("turnos_config:cache", 180, json.dumps(configs))
    return configs


# Escritura + invalidación del Proxy al modificar configuración
def update_turnos_config(tipo: str, nuevos_params: dict):
    cur.execute(
        "UPDATE turnos_config SET raciones_max=%s, activo=%s WHERE tipo=%s",
        (nuevos_params["raciones_max"], nuevos_params["activo"], tipo)
    )
    conn.commit()
    redis_client.delete("turnos_config:cache")  # invalida el Proxy
```

A diferencia de un Proxy de seguridad o de virtualización, este es un **Proxy de caché**: evita consultas repetidas a PostgreSQL para datos que cambian raramente (horarios y capacidad del comedor). Combina TTL (caducidad automática en 180 s) con invalidación dirigida al escribir, garantizando que nunca se sirva una configuración desactualizada más allá del margen del TTL.

### Trade-offs aceptados

| Trade-off | Descripción |
|---|---|
| Ventana de inconsistencia durante la invalidación | Entre el momento en que se escribe la nueva versión en PostgreSQL y el momento en que `redis_client.delete()` se ejecuta, existe una ventana mínima donde otros procesos podrían leer la versión anterior del caché. Se mitiga ejecutando ambas operaciones en la misma transacción de aplicación. |
| Redis como dependencia adicional | Si Redis no está disponible, `get_config_activa()` debe degradarse consultando PostgreSQL directamente. El Proxy debe manejar esta situación con un `try/except` en la lectura de Redis. |

## Patrón 2 — Template Method *(De comportamiento)*

### Problema concreto

Cuando un turno queda libre, M6 ejecuta siempre el mismo flujo: (1) buscar al siguiente candidato en `cola_virtual`, (2) actualizarle el estado a `LLAMADO`, (3) notificarle por WebSocket y RabbitMQ. Este esqueleto no varía. Lo que sí puede variar es el paso 1 — almuerzo y cena tienen colas separadas (cada `turno_dia_id` es una instancia independiente en `cola_virtual`), pero hoy usan el mismo criterio de selección FIFO. En el futuro podrían necesitar criterios distintos (ventana de confirmación diferente, restricción de horario de corte), y el Template Method permite sobrescribir solo ese paso sin tocar el flujo completo. Si ese paso estuviera hardcodeado en la clase principal, cada variación obligaría a tocar el flujo completo.

### Ubicación en el diseño

- **Clase abstracta:** `ReasignacionBase` — define el esqueleto (`ejecutar`) con el paso variable como método abstracto
- **Paso concreto variable:** `seleccionar_candidato()` — diferente por tipo de turno
- **Pasos concretos fijos:** `marcar_llamado()` y `notificar()` — iguales para cualquier tipo
- **Campo de datos:** tabla [`cola_virtual`](../../10/10.3/10.3.md) en PostgreSQL

### Implementación propuesta

```python
# Clase abstracta — define el esqueleto del algoritmo
class ReasignacionBase:
    def ejecutar(self, turno_dia_id: int) -> dict | None:
        # Paso 1: variable según subclase
        candidato = self.seleccionar_candidato(turno_dia_id)
        if not candidato:
            return None

        # Paso 2: fijo — marcar en DB
        self.marcar_llamado(candidato["id"])

        # Paso 3: fijo — notificar
        self.notificar(candidato)

        return candidato

    def seleccionar_candidato(self, turno_dia_id: int) -> dict | None:
        raise NotImplementedError

    def marcar_llamado(self, turno_id: int) -> None:
        db.execute(
            "UPDATE cola_virtual SET estado = 'LLAMADO', llamado_at = NOW() WHERE id = %s",
            (turno_id,)
        )

    def notificar(self, candidato: dict) -> None:
        if manager.is_connected(candidato["codigo"]):
            manager.send(candidato["codigo"], {
                "type":    "llamado",
                "turno":   candidato["numero_turno"],
                "mensaje": "¡Es tu turno! Confirma en los próximos 3 minutos.",
            })
        publish("turno.llamado", {
            "evento":       "turno.llamado",
            "codigo":       candidato["codigo"],
            "numero_turno": candidato["numero_turno"],
            "push_token":   candidato["push_token"],
        })


# Subclase concreta — selección FIFO estricta (almuerzo y cena)
class ReasignacionFIFO(ReasignacionBase):
    def seleccionar_candidato(self, turno_dia_id: int) -> dict | None:
        return db.query("""
            SELECT * FROM cola_virtual
            WHERE turno_dia_id = %s
              AND estado = 'ESPERANDO'
            ORDER BY posicion ASC
            LIMIT 1
            FOR UPDATE SKIP LOCKED
        """, (turno_dia_id,))
```

El método `ejecutar()` en la clase base es el **template**: define el orden fijo de los pasos y delega solo `seleccionar_candidato()` a la subclase. `FOR UPDATE SKIP LOCKED` garantiza que si dos procesos de reasignación corren en paralelo, cada uno tome un candidato distinto sin bloqueo mutuo.

### Trade-offs aceptados

| Trade-off | Descripción |
|---|---|
| Herencia sobre composición | Template Method usa herencia, que acopla la subclase a la clase base. Para los tipos de turno actuales (almuerzo y cena con el mismo criterio FIFO) una sola subclase `ReasignacionFIFO` es suficiente. Si los criterios divergieran mucho, composición (Strategy) sería preferible. |
| Pasos fijos no son extensibles sin tocar la base | Si se necesita añadir un paso nuevo al flujo (ej. registrar en historial antes de notificar), hay que modificar `ReasignacionBase.ejecutar()`. Es el trade-off conocido del patrón: el esqueleto es rígido por diseño. |
