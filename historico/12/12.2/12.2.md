# 12.2. Módulo 2 / Integrante 2

**Módulos cubiertos:** M2 – Gestión de Colas · M3 – Gestión de Turnos

---

## Preocupaciones transversales identificadas

| Módulo(s) afectado(s) | Aspecto (concern transversal) | Punto de corte (pointcut) | Advice (tipo + descripción) |
|---|---|---|---|
| M2, M3 | Logging de operaciones | Toda función de servicio en `queues/router.py` y toda iteración del `inactivity_worker()` | **around** — registra la entrada (endpoint o ciclo del worker), parámetros clave y resultado o excepción al terminar |
| M2, M3 | Validación de sesión | Todo endpoint de M2/M3 que recibe `sid` (`join`, `status`, `confirm`, `leave`, `register-push-token`) | **before** — extrae el `sid`, lo valida contra Redis y lanza `HTTPException 401` si es inválido, antes de cualquier lógica de cola |
| M3 | Publicación de eventos de auditoría | Toda operación que cambia el estado de un turno (`join`, `confirm`, `inactivity_worker`) | **after-returning** — tras completar exitosamente la operación, publica el evento RabbitMQ correspondiente (`turno.encolado`, `turno.atendido`, `turno.llamado`, `turno.cancelado`) |

---

## Descripción de cada aspecto

### Aspecto 1 — Logging de operaciones

**Módulos afectados:** M2, M3

**Situación actual:** los `print()` de M2/M3 están dispersos en dos archivos. En [`queues/worker.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/worker.py):

```python
print(f"[Queue] Turno cancelado por inactividad: {codigo}")
print(f"[Queue] Llamando turno #{numero} — alumno {codigo}")
print(f"[Queue] Error en worker: {e}")
```

En [`queues/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/router.py) no hay logs explícitos fuera del worker — los errores de negocio se delegan directamente a `HTTPException` sin dejar rastro en el log del servidor.

**Por qué conviene tratarlo como aspecto:** el worker y el router son el núcleo de M2/M3; mezclar logging con lógica de cola dificulta añadir trazabilidad estructurada (ej. correlación de requests con `turno_dia_id`). Un aspecto `around` centraliza el formato y puede añadir contexto (turno, estudiante, duración) sin modificar la lógica de cada operación.

**Pointcut:** toda función handler de `queues/router.py` y cada ciclo del loop `inactivity_worker()`.

**Advice (`around`):**
```python
async def logging_advice(joinpoint):
    context = joinpoint.context.get("turno_dia_id", "–")
    logger.info(f"[M2/M3] → {joinpoint.function} turno_dia={context}")
    start = time.monotonic()
    try:
        result = await joinpoint.proceed()
        logger.info(f"[M2/M3] ✓ {joinpoint.function} ({time.monotonic()-start:.2f}s)")
        return result
    except Exception as e:
        logger.error(f"[M2/M3] ✗ {joinpoint.function} — {type(e).__name__}: {e}")
        raise
```

### Aspecto 2 — Validación de sesión

**Módulos afectados:** M2, M3

**Situación actual:** en [`queues/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/router.py) se extrajo la validación a un helper:

```python
def _require_session(sid: str) -> dict:
    session = get_session(sid)
    if not session:
        raise HTTPException(status_code=401, detail="Sesión inválida o expirada")
    return session
```

Y se llama manualmente al inicio de cada endpoint:

```python
session = _require_session(data.sid)   # en join_queue
session = _require_session(data.sid)   # en register_push_token
session = _require_session(sid)        # en queue_status
session = _require_session(data.sid)   # en confirm_presence
session = _require_session(data.sid)   # en leave_queue
```

Esto ya redujo la duplicación, pero la llamada sigue siendo responsabilidad de cada endpoint. Si un endpoint nuevo omite `_require_session`, el bug no se detecta hasta runtime.

**Por qué conviene tratarlo como aspecto:** un aspecto `before` hace que la validación sea automática para cualquier endpoint marcado; un endpoint nuevo no puede "olvidarse" de validar. Además unifica la lógica de sesión en un solo lugar con M1 (ver [12.1 — Aspecto 2](../12.1/12.1.md)).

**Pointcut:** todo endpoint de M2/M3 que recibe `sid` como parámetro (body o query).

**Advice (`before`):**
```python
def session_guard_advice(joinpoint):
    sid = joinpoint.extract_param("sid")
    session = get_session(sid)
    if not session:
        raise HTTPException(status_code=401, detail="Sesión inválida o expirada")
    joinpoint.context["session"] = session
    joinpoint.proceed()
```

### Aspecto 3 — Publicación de eventos de auditoría

**Módulos afectados:** M3

**Situación actual:** las llamadas a `publish()` están intercaladas con la lógica de negocio en [`queues/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/router.py) y [`queues/worker.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/worker.py):

```python
# En join_queue — router.py
crear_turno(estudiante_id, turno_dia_id, numero)
await publish("turno.encolado", {...})   # ← mezclado con lógica de negocio

# En confirm_presence — router.py
nuevo_estado = confirmar_turno(turno["id"], turno["estado"])
if nuevo_estado == "ATENDIDO":
    await publish("turno.atendido", {...})   # ← condicional dentro del handler
    for sig in llamar_siguiente(...):
        await publish("turno.llamado", {...})

# En inactivity_worker — worker.py
cancelar_inactivos()
await publish("turno.cancelado", {...})   # ← en el loop del worker
```

Cada operación de negocio conoce el sistema de mensajería y construye el payload manualmente.

**Por qué conviene tratarlo como aspecto:** la publicación de eventos es una responsabilidad de observabilidad/auditoría, no de la lógica de cola. Si el sistema de mensajería cambia (de RabbitMQ a Kafka, por ejemplo), habría que editar cada operación individualmente. Un aspecto `after-returning` reacciona al éxito de la operación y emite el evento sin que la lógica de negocio lo sepa.

**Pointcut:** toda función que modifica el estado de un turno: `crear_turno()`, `confirmar_turno()`, `cancelar_inactivos()`.

**Advice (`after-returning`):**
```python
async def audit_event_advice(joinpoint, result):
    funcion = joinpoint.function
    ctx     = joinpoint.context

    if funcion == "crear_turno":
        await publish("turno.encolado", {
            "evento": "turno.encolado", **ctx
        })
    elif funcion == "confirmar_turno" and result == "ATENDIDO":
        await publish("turno.atendido", {
            "evento": "turno.atendido", **ctx
        })
    elif funcion == "cancelar_inactivos":
        for cancelado in result:
            await publish("turno.cancelado", {
                "evento": "turno.cancelado", **cancelado
            })
```
