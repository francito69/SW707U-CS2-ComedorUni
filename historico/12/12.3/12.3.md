# 12.3. Módulo 3 / Integrante 3

**Módulos cubiertos:** M6 – Reasignación de Turnos · M7 – Configuración Operativa

---

## Preocupaciones transversales identificadas

| Módulo(s) afectado(s) | Aspecto (concern transversal) | Punto de corte (pointcut) | Advice (tipo + descripción) |
|---|---|---|---|
| M6, M7 | Logging de operaciones | Toda función de servicio de M6 y M7 (reasignación, lectura y escritura de configuración) | **around** — registra entrada, parámetros clave y resultado o excepción al terminar, incluyendo si el dato vino de Redis o PostgreSQL |
| M6, M7 | Autorización de administrador | Todo endpoint HTTP de M6 y M7 | **before** — verifica que el request proviene de un administrador autorizado antes de ejecutar la lógica; lanza `403` si no lo es |
| M7 | Invalidación de caché Redis | Toda operación de escritura sobre `turnos_config` en PostgreSQL | **after-returning** — tras confirmar el commit en PostgreSQL, elimina la clave `turnos_config:cache` en Redis para que el Proxy (ver [11.3](../../11/11.3/11.3.md)) sirva datos frescos en la próxima lectura |

---

## Descripción de cada aspecto

### Aspecto 1 — Logging de operaciones

**Módulos afectados:** M6, M7

**Situación actual:** M6 y M7 están en etapa de diseño (solo `__init__.py` en `src/modules/reassignment/` y `src/modules/config/`). El aspecto se especifica de forma preventiva para que, cuando se implemente el código, no se repita el patrón de `print()` dispersos observado en M1–M5.

**Por qué conviene tratarlo como aspecto:** M7 tiene una característica especial: cada lectura puede resolverse desde Redis (cache hit) o desde PostgreSQL (cache miss). El log debe registrar la fuente del dato para diagnosticar problemas de caché. Incluir esa decisión en la lógica de negocio mezcla responsabilidades; el aspecto puede inspeccionarlo sin modificar `get_turnos_config()`.

**Pointcut:** toda función de servicio de M6 (`seleccionar_candidato`, `reasignar_turno`) y M7 (`get_turnos_config`, `update_turnos_config`).

**Advice (`around`):**
```python
async def logging_advice(joinpoint):
    logger.info(f"[{joinpoint.module}] → {joinpoint.function}")
    start = time.monotonic()
    try:
        result = await joinpoint.proceed()
        fuente = "redis" if joinpoint.context.get("cache_hit") else "postgres"
        logger.info(
            f"[{joinpoint.module}] ✓ {joinpoint.function} "
            f"fuente={fuente} ({time.monotonic()-start:.2f}s)"
        )
        return result
    except Exception as e:
        logger.error(f"[{joinpoint.module}] ✗ {joinpoint.function} — {type(e).__name__}: {e}")
        raise
```

### Aspecto 2 — Autorización de administrador

**Módulos afectados:** M6, M7

**Situación actual:** M6 y M7 están en diseño. En el DEMO de M7 ([`DEMO/main.py`](../../0/0.5/0.5.3/0.5.3.3/DEMO/main.py)), la autorización se hace verificando el header `x-consumer-username` inyectado por el API Gateway:

```python
# DEMO/main.py
def update_configuracion(body: dict, x_consumer_username: str = Header(None)):
    if not x_consumer_username:
        raise HTTPException(status_code=403, detail="Acceso denegado")
```

Esta verificación tendrá que repetirse en cada endpoint de M6 y M7 cuando se implementen, con el riesgo de omitirla en alguno.

**Por qué conviene tratarlo como aspecto:** todos los endpoints de M6 y M7 son exclusivos del administrador — ninguno es público ni requiere sesión de estudiante. La política de acceso es uniforme para todos. Un aspecto `before` la aplica automáticamente a cualquier endpoint nuevo de estos módulos, sin que el desarrollador tenga que recordarla.

**Pointcut:** todo endpoint HTTP registrado bajo los prefijos `/config/` y `/reassignment/`.

**Advice (`before`):**
```python
def admin_auth_advice(joinpoint):
    # En la implementación definitiva: verificar rol de admin en el token de sesión
    # En la versión DEMO: verificar header inyectado por el API Gateway
    admin_user = joinpoint.request.headers.get("x-consumer-username")
    if not admin_user:
        raise HTTPException(
            status_code=403,
            detail="Acceso denegado: se requieren permisos de administrador"
        )
    joinpoint.context["admin_user"] = admin_user
    joinpoint.proceed()
```

### Aspecto 3 — Invalidación de caché Redis

**Módulos afectados:** M7

**Situación actual:** en el Proxy de M7 (ver [11.3 — Patrón 1](../../11/11.3/11.3.md)), la invalidación del caché se hace explícitamente dentro de `update_turnos_config()`:

```python
def update_turnos_config(tipo: str, nuevos_params: dict):
    cur.execute("UPDATE turnos_config SET ...")
    conn.commit()
    redis_client.delete("turnos_config:cache")   # ← mezclado con la lógica de escritura
```

Si en el futuro se añade otro método que escribe en `turnos_config` (por ejemplo, `desactivar_turno()` o `crear_turno_tipo()`), debe recordarse añadir la invalidación manualmente.

**Por qué conviene tratarlo como aspecto:** la invalidación del caché es una consecuencia de cualquier escritura en `turnos_config`, no una responsabilidad del método que escribe. Tratarla como aspecto garantiza que nunca se sirva configuración obsoleta, independientemente de cuántos métodos de escritura se añadan.

**Pointcut:** toda función que ejecuta un `UPDATE`, `INSERT` o `DELETE` sobre la tabla `turnos_config`.

**Advice (`after-returning`):**
```python
async def cache_invalidation_advice(joinpoint, result):
    # Solo se ejecuta si la escritura en PostgreSQL completó sin error
    redis_client.delete("turnos_config:cache")
    logger.info(
        f"[M7] Caché Redis invalidada tras {joinpoint.function} "
        f"(operador: {joinpoint.context.get('admin_user', '?')})"
    )
```
