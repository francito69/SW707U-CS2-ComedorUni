## ADR-COL-001 — Estructura de la cola virtual: tabla `turnos` en PostgreSQL

**Categoría:** Elección de Tecnología

### Contexto

El RF04 exige mantener el orden de llegada (FIFO) de los estudiantes en la cola virtual. Se debe decidir dónde y cómo se almacena el estado de la cola durante la operación del comedor.

### Alternativas

1. **Redis Sorted Set (ZSET) con timestamp como score.** Alta velocidad en memoria. Estado de la cola efímero: si Redis se reinicia, se pierde quién estaba en cola. Requiere sincronización adicional con PostgreSQL para persistencia histórica.

2. **Tabla `turnos` en PostgreSQL con `numero_turno` correlativo como orden.** La posición en la cola se determina por `numero_turno` en `estado = 'ESPERANDO'`. Las operaciones de escritura son atómicas con el resto del modelo relacional. El historial y el estado operativo viven en el mismo motor. La posición se consulta con `COUNT(*) WHERE numero_turno < :n AND estado = 'ESPERANDO'`.

3. **Hybrid: Redis para posición en tiempo real, PostgreSQL para persistencia.** Complejidad operativa adicional sin ganancia significativa para el volumen universitario esperado.

### Criterios de Elección

- **Consistencia:** el estado de la cola debe sobrevivir reinicios del proceso.
- **Simplicidad:** no añadir motores de datos adicionales si PostgreSQL es suficiente.
- **Integridad referencial** con `estudiantes` y `turno_dia`.

### Decisión

La cola virtual se implementa sobre la tabla `turnos` en PostgreSQL (`src/modules/queues/service.py`). El orden FIFO se mantiene mediante el campo `numero_turno` (INTEGER, correlativo por `turno_dia_id`). La posición se calcula con `posicion_en_cola(turno_dia_id, numero_turno)`.

### Sustento

PostgreSQL con transacciones ACID garantiza que ningún estudiante quede en un estado inconsistente (dos turnos activos, posición incorrecta) sin necesidad de sincronización adicional. Para el volumen universitario esperado (decenas a cientos de estudiantes por turno), el overhead de consultar posición con `COUNT(*)` es negligible. Redis se usa para sesiones (M1) y configuración (M7), pero la cola en sí es más segura en un motor con persistencia garantizada. El trade-off aceptado es que consultar la posición requiere un SELECT, no una operación O(1) como en Redis ZSET; asumible dado el volumen.

## ADR-COL-002 — Validación de duplicidad: restricción UNIQUE parcial en PostgreSQL

**Categoría:** Asignación de Responsabilidades

### Contexto

El RF03 exige que un estudiante no tenga más de un turno activo para el mismo `turno_dia_id`. Ante solicitudes concurrentes del mismo estudiante (error de red, doble tap), la validación debe garantizar unicidad sin condición de carrera.

### Alternativas

1. **Validación en la capa de aplicación (`SELECT` antes del `INSERT`).** Riesgo de condición de carrera: dos requests pueden pasar el SELECT simultáneamente y ambos llegar al INSERT.

2. **Restricción `UNIQUE` parcial en PostgreSQL sobre `(estudiante_id, turno_dia_id)` excluyendo `estado = 'CANCELADO'`.** La base de datos garantiza la unicidad a nivel DDL. El segundo INSERT para el mismo par falla con `UniqueViolation`. La lógica de aplicación usa `turno_existente()` para devolver un mensaje descriptivo antes del INSERT.

### Criterios de Elección

- **Prevención de duplicados** ante requests concurrentes.
- **Sin condición de carrera** en la validación.
- **Reutilizar la infraestructura existente** (PostgreSQL).

### Decisión

Se define `CREATE UNIQUE INDEX idx_turnos_activo ON turnos (estudiante_id, turno_dia_id) WHERE estado != 'CANCELADO'` en la migración. La capa de aplicación verifica con `turno_existente()` antes del `crear_turno()` para devolver un HTTP 409 descriptivo.

### Sustento

Delegar la garantía de unicidad al motor de base de datos elimina condiciones de carrera que existirían con solo validación en aplicación. Un turno cancelado no bloquea al estudiante de reingresar a la cola (el índice parcial excluye `CANCELADO`), lo cual es el comportamiento deseado. El trade-off aceptado es que la excepción de unicidad de PostgreSQL debe manejarse explícitamente en la capa de servicio si el check previo falla por concurrencia.

## ADR-COL-003 — Modelo de datos: estados ESPERANDO / LLAMADO / ATENDIDO / CANCELADO

**Categoría:** Modelo de Datos

### Contexto

Cada turno atraviesa un ciclo de vida: se crea, espera su turno, es llamado para confirmar, es atendido o cancelado. El modelo de datos debe reflejar estos estados de forma que sean válidos, consultables y auditables.

### Alternativas

1. **Múltiples columnas booleanas (`is_active`, `is_called`, `is_attended`).** Propenso a estados inválidos: `is_active=true` e `is_attended=true` simultáneamente.

2. **Campo `estado VARCHAR(20)` con CHECK constraint.** Un único campo enum-like con validación en la base de datos. Los estados son mutuamente excluyentes por definición. Los timestamps de cada transición (`llamado_at`, `confirmado_at`, `cancelado_at`) registran cuándo ocurrió cada cambio.

### Criterios de Elección

- **Integridad:** imposible registrar un estado inválido.
- **Trazabilidad:** registrar cuándo ocurrió cada transición.
- **Simplicidad de consulta:** filtrar por estado es un WHERE simple.

### Decisión

La tabla `turnos` tiene el campo `estado VARCHAR(20)` con `CHECK (estado IN ('ESPERANDO', 'LLAMADO', 'ATENDIDO', 'CANCELADO'))` y timestamps individuales: `ingresado_at`, `llamado_at`, `confirmado_at`, `cancelado_at`. La columna `ultimo_ping` registra la última actividad del estudiante para detección de inactividad.

### Sustento

El CHECK constraint de PostgreSQL garantiza que ningún estado inválido se almacene nunca. Los timestamps individuales permiten auditar la duración de cada fase (tiempo en cola, tiempo de confirmación) sin joins adicionales. La columna `ultimo_ping` es el mecanismo de detección de inactividad del worker (ver ADR-TUR-004). El trade-off aceptado es que las transiciones de estado se validan solo en la capa de aplicación (no hay FK entre estados); esto es suficiente dado que el código de servicio es el único punto de modificación de `estado`.

## ADR-COL-004 — Concurrencia en ingreso a cola: `FOR UPDATE SKIP LOCKED`

**Categoría:** Gestión de Recursos

### Contexto

Cuando se habilita la cola, múltiples estudiantes intentan ingresar simultáneamente. Las operaciones de validación de cupo (`raciones_usadas`) y asignación de `numero_turno` deben ser atómicas para evitar sobresuscripción o número de turno duplicado.

### Alternativas

1. **Scripts Lua en Redis.** Atómica y de alta velocidad en Redis. Pero si la cola está en PostgreSQL (ADR-COL-001), Lua en Redis no protege las escrituras en la tabla `turnos`.

2. **`SELECT FOR UPDATE` en PostgreSQL.** Bloquea la fila de `turno_dia` durante la transacción. Garantiza que solo un proceso a la vez lee el estado y lo modifica. Compatible con la decisión de cola en PostgreSQL.

3. **`SELECT ... FOR UPDATE SKIP LOCKED` en PostgreSQL.** Igual que FOR UPDATE pero un proceso que no puede obtener el lock pasa al siguiente registro en lugar de esperar. Usado específicamente para seleccionar el siguiente candidato sin bloqueo mutuo entre workers.

### Criterios de Elección

- **Atomicidad** entre leer el estado y modificarlo.
- **Sin bloqueo mutuo** entre requests concurrentes.
- **Consistente** con el motor elegido (PostgreSQL).

### Decisión

Las operaciones críticas de la cola usan transacciones PostgreSQL. La selección del siguiente candidato (usada en M6 para reasignación) usa `FOR UPDATE SKIP LOCKED` para evitar que dos procesos seleccionen el mismo estudiante simultáneamente.

### Sustento

`FOR UPDATE SKIP LOCKED` es la primitiva de PostgreSQL diseñada exactamente para el caso de "workers concurrentes que procesan una cola". Cada worker obtiene un candidato diferente sin esperar el lock del otro. Las operaciones de `crear_turno` y `siguiente_numero` corren dentro de la misma conexión con commit explícito. El trade-off aceptado es que las transacciones de PostgreSQL son más lentas que operaciones en Redis; para el volumen universitario (decenas de inserciones concurrentes, no millones), esto es completamente manejable.

## ADR-COL-005 — Parámetros de capacidad leídos desde `turno_dia` y `turnos_config`

**Categoría:** Tiempo de Enlace

### Contexto

La capacidad máxima de cada turno (`raciones_max`) y los horarios de apertura/cierre determinan si un estudiante puede ingresar a la cola. Estos parámetros son configurables por el administrador (M7) y se aplican por instancia diaria del turno (`turno_dia`).

### Alternativas

1. **Hardcodeados en variables de entorno o código.** Cambiar la capacidad requiere redespliegue. No apto para operación dinámica.

2. **Leídos directamente de PostgreSQL en cada request.** Sin caché. Para el volumen esperado, una consulta a PostgreSQL por request es aceptable. La tabla `turno_dia` ya tiene la capacidad del día actual.

3. **Leídos de Redis (caché de M7).** Mayor velocidad. Requiere que M7 mantenga `turnos_config:cache` actualizado. Para la capacidad de `turno_dia` (específica de hoy), el caché de M7 es de configuración base, no de instancias diarias.

### Criterios de Elección

- **Actualidad:** los parámetros deben reflejar el estado actual del día.
- **Simplicidad:** no añadir capas si PostgreSQL es suficiente para el volumen.

### Decisión

`get_turno_dia_activo()` consulta la tabla `turno_dia` en PostgreSQL para obtener `config_id`, `raciones_max` y horarios del turno activo hoy. `get_raciones_max_turno_dia()` consulta `turno_dia.raciones_max` por `turno_dia_id`. La configuración base (`hora_apertura`, `hora_inicio`, etc.) vive en `turnos_config` y puede ser cacheada por M7 (ver [11.3](../../11/11.3/11.3.md)).

### Sustento

La separación entre `turnos_config` (configuración base reutilizable) y `turno_dia` (instancia del día con posibles overrides) permite que el administrador ajuste la capacidad de un día específico sin tocar la configuración base. La consulta directa a PostgreSQL es suficiente para el volumen esperado; si la latencia fuera un problema, `turno_dia` puede cachearse en Redis con TTL de 1 hora. El trade-off aceptado es que cada verificación de turno activo hace una consulta a PostgreSQL; dado que `turno_dia` tiene pocos registros (uno por tipo por día), la consulta es extremadamente rápida.

## ADR-COL-006 — Despliegue del módulo de gestión de colas: FastAPI modular en monolito

**Categoría:** Mapeo entre Elementos Arquitectónicos

### Contexto

M2 es el módulo de mayor carga durante la apertura del turno. Se debe decidir si se despliega como microservicio independiente o dentro del monolito FastAPI.

### Alternativas

1. **Microservicio independiente.** Escalable de forma aislada. Para el volumen universitario esperado, agrega complejidad operativa sin beneficio real. Las llamadas a M3 para generar el turno requerirían HTTP inter-servicio con latencia adicional.

2. **Módulo dentro del monolito FastAPI.** El router de colas (`src/modules/queues/router.py`) se monta bajo el prefijo `/queue`. Las llamadas a funciones de M3 (servicio) son llamadas locales sin red. El WebSocket manager (`manager`) es una instancia global compartida por router y worker en el mismo proceso.

### Criterios de Elección

- **Latencia** en el join a cola: la generación del turno debe ser síncrona y rápida.
- **Simplicidad operativa** para el equipo académico.
- **Singleton compartido** del WebSocket manager.

### Decisión

M2 se despliega como router FastAPI dentro del monolito, montado bajo `/queue`. El `QueueConnectionManager` singleton (`manager = QueueConnectionManager()` en `manager.py`) es accesible desde el router y el worker en el mismo proceso.

### Sustento

Al estar en el mismo proceso, el router y el worker de inactividad comparten la misma instancia de `QueueConnectionManager`, lo que garantiza que las notificaciones WebSocket del worker llegan a los mismos clientes que se conectaron vía el router. Esto sería imposible de lograr de forma simple con microservicios separados. El trade-off aceptado es que escalar M2 implica escalar todo el monolito; asumible para el volumen universitario.

## ADR-COL-007 — Coordinación entre cola y turnos: llamadas directas + WebSocket

**Categoría:** Modelo de Coordinación

### Contexto

Cuando un estudiante ingresa a la cola (`POST /queue/join`), el sistema debe: (1) crear el turno en PostgreSQL, (2) responder al cliente con número y posición, y (3) notificar en tiempo real a otros clientes si corresponde. Se debe definir cómo M2 y M3 coordinan estas operaciones.

### Alternativas

1. **Totalmente asíncrono vía RabbitMQ.** M2 publica el evento y M3 crea el turno más tarde. El cliente no recibe su número de turno en la respuesta del join — debe esperar una notificación. Mala experiencia de usuario.

2. **Síncrono en el mismo request: llamadas directas entre servicios del mismo proceso.** `join_queue` llama a `crear_turno()`, `posicion_en_cola()` y devuelve todo en el response HTTP. Posterior al commit, publica el evento `turno.encolado` en RabbitMQ para M5.

3. **WebSocket para actualizaciones en tiempo real.** Complementario a la respuesta HTTP: el worker de inactividad y la confirmación de turno usan el WebSocket para notificar al cliente sin que este haga polling.

### Criterios de Elección

- **UX:** el estudiante recibe su número de turno inmediatamente al hacer join.
- **Desacoplamiento** de M4 y M5 vía eventos asíncronos.
- **Tiempo real** para actualizaciones de estado posteriores.

### Decisión

La creación del turno es síncrona (llamada directa en el mismo proceso). El evento `turno.encolado` se publica a RabbitMQ de forma asíncrona al final del request. Las notificaciones de llamado y cancelación se entregan vía WebSocket en tiempo real, complementadas por RabbitMQ para M4 y M5.

### Sustento

La respuesta síncrona garantiza que el estudiante sepa su número de turno en la misma petición HTTP (`JoinQueueResponse`). El WebSocket permite actualizaciones push sin polling: cuando el worker llama al siguiente turno, envía `{"type": "llamado"}` directamente al cliente conectado. RabbitMQ desacopla M4 (notificaciones push) y M5 (seguimiento) del flujo principal. El trade-off aceptado es que si el WebSocket se desconecta momentáneamente, el estudiante puede perder una notificación de llamado; esto se mitiga con la push notification de M4 que llega aunque la app esté en background.

## ADR-TUR-001 — Identificador de turno: número correlativo entero (`numero_turno`)

**Categoría:** Elección de Tecnología

### Contexto

Cada turno necesita un identificador que sea único dentro de un `turno_dia_id`, visible para el estudiante (le dice "eres el turno #47") y que establezca el orden FIFO de la cola.

### Alternativas

1. **ULID (Universally Unique Lexicographically Sortable Identifier).** Globalmente único y ordenable. Para el caso de uso (mostrar al estudiante su número de turno), un ULID de 26 caracteres es innecesariamente largo e ilegible.

2. **UUID v4.** Globalmente único pero no ordenable y no legible para el usuario.

3. **Número correlativo entero (`numero_turno` INTEGER).** Simple, legible ("Turno #47"), único dentro del `turno_dia_id` y establece el orden FIFO directamente. Se asigna con `MAX(numero_turno) + 1` dentro de la transacción de creación.

### Criterios de Elección

- **Legibilidad:** el estudiante ve su número en la app.
- **Orden FIFO:** el número establece la posición en la cola.
- **Simplicidad** de implementación.

### Decisión

El campo `numero_turno INTEGER` en la tabla `turnos` es el identificador visible del turno, correlativo dentro de `turno_dia_id`. La función `siguiente_numero(turno_dia_id, raciones_max)` calcula el siguiente número disponible con `MAX(numero_turno) + 1`.

### Sustento

El número correlativo es exactamente lo que el usuario necesita ver: "Turno #12 — estás en la posición 3". No hay necesidad de un identificador globalmente único para un dato que solo tiene sentido dentro del contexto de un turno del día. La clave primaria global de la fila sigue siendo `id SERIAL PRIMARY KEY` para referencias de FK. El trade-off aceptado es que `MAX(numero_turno) + 1` debe ejecutarse dentro de una transacción protegida contra concurrencia; esto se garantiza con las transacciones de PostgreSQL.

## ADR-TUR-002 — Ciclo de vida del turno: máquina de estados con CHECK constraint en PostgreSQL

**Categoría:** Modelo de Datos

### Contexto

El turno atraviesa estados bien definidos desde que el estudiante ingresa a la cola hasta que es atendido o cancelado. Se debe modelar este ciclo de forma que los estados inválidos sean imposibles y las transiciones sean auditables.

### Alternativas

1. **Campos booleanos dispersos.** `is_waiting`, `is_called`, `is_attended`. Estados inválidos posibles (`is_waiting=true` e `is_attended=true`).

2. **Campo `estado` con CHECK constraint y timestamps de transición.** Un único campo `estado VARCHAR(20)` con `CHECK (estado IN ('ESPERANDO', 'LLAMADO', 'ATENDIDO', 'CANCELADO'))`. Timestamps individuales (`llamado_at`, `confirmado_at`, `cancelado_at`) para auditar cuándo ocurrió cada transición.

### Criterios de Elección

- **Integridad:** estados inválidos imposibles a nivel de BD.
- **Trazabilidad:** auditar el tiempo en cada estado.
- **Claridad** del modelo de negocio.

### Decisión

La tabla `turnos` usa `estado VARCHAR(20)` con CHECK constraint y cuatro timestamps de transición. Las transiciones válidas son: `ESPERANDO → LLAMADO` (el worker o confirm llama al siguiente), `LLAMADO → ATENDIDO` (el estudiante confirma), `ESPERANDO → CANCELADO` (worker de inactividad), `LLAMADO → CANCELADO` (timeout de confirmación). La función `confirmar_turno(id, estado_actual)` gestiona las transiciones.

### Sustento

La máquina de estados en la capa de servicio impide transiciones inválidas (por ejemplo, no se puede pasar de ATENDIDO a ESPERANDO). El CHECK constraint de PostgreSQL es la red de seguridad de última instancia. Los timestamps de transición (`llamado_at`, `cancelado_at`) permiten calcular métricas operacionales: cuánto tardó el estudiante en confirmar, cuántos turnos fueron cancelados por inactividad. El trade-off aceptado es que las transiciones se validan en código de aplicación, no en FK entre estados; esto es suficiente con un único punto de modificación del estado.

## ADR-TUR-003 — Detección de inactividad: worker asyncio con loop periódico

**Categoría:** Asignación de Responsabilidades

### Contexto

Los turnos en estado `ESPERANDO` o `LLAMADO` que no han tenido actividad reciente deben cancelarse automáticamente para liberar el cupo. Se debe decidir qué componente detecta y ejecuta esta cancelación.

### Alternativas

1. **APScheduler o Celery (scheduler externo).** Dependencia adicional. La lógica de negocio queda en un proceso diferente al de la API. Complejidad de despliegue adicional.

2. **Redis TTL + Keyspace Notifications.** Cuando un turno expira su TTL en Redis, Redis dispara un evento. Requiere que el estado del turno esté en Redis, no en PostgreSQL (contradice ADR-COL-001). Alta complejidad de configuración.

3. **Worker asyncio con `asyncio.sleep(INTERVAL_SECONDS)` dentro del proceso FastAPI.** Un loop infinito que duerme 60 segundos, luego consulta la base de datos y cancela inactivos. Sin dependencias adicionales. Corre en el mismo event loop que el servidor FastAPI.

### Criterios de Elección

- **Cohesión:** la lógica de cancelación debe estar en el mismo módulo que gestiona la cola.
- **Sin dependencias adicionales** para el volumen universitario.
- **Precisión** suficiente (cancelar cada ~60 segundos).

### Decisión

`inactivity_worker()` en `src/modules/queues/worker.py` es un coroutine asyncio que corre en loop cada `INTERVAL_SECONDS = 60`. Se inicia como tarea asyncio al arrancar la aplicación FastAPI.

### Sustento

El worker asyncio no bloquea el event loop principal de FastAPI — `asyncio.sleep(60)` cede el control al event loop durante el intervalo. La lógica de detección de inactividad (`cancelar_inactivos()`, `get_turnos_a_notificar()`) está en el mismo módulo que el router, con acceso al mismo `manager` de WebSocket y al mismo pool de conexiones DB. El trade-off aceptado es que la cancelación no es instantánea — puede tardar hasta 60 segundos. Esto es aceptable: la ventana de inactividad está definida en minutos, no en segundos.

## ADR-TUR-004 — Mecanismo de inactividad: columna `ultimo_ping` actualizada por pings WebSocket

**Categoría:** Modelo de Coordinación

### Contexto

El sistema debe distinguir entre un estudiante que está esperando activamente (app abierta) y uno que cerró la app o perdió conexión. Se debe decidir cómo detectar esta inactividad.

### Alternativas

1. **Solo basarse en el estado de la conexión WebSocket.** Si el WebSocket está desconectado, el estudiante está inactivo. Frágil: la desconexión puede ser momentánea (lock de pantalla, red intermitente) sin que el estudiante abandone la cola.

2. **Columna `ultimo_ping` en la tabla `turnos`, actualizada por pings activos del cliente.** El cliente envía `{"type": "ping"}` periódicamente vía WebSocket. El servidor actualiza `ultimo_ping = NOW()` al recibir el ping. El worker cancela turnos donde `ultimo_ping < NOW() - umbral` Y el estado es `ESPERANDO`.

### Criterios de Elección

- **Tolerancia** a desconexiones momentáneas sin cancelar el turno.
- **Detección real** de estudiantes que abandonaron la cola.
- **Sin polling del cliente** contra la API REST.

### Decisión

La tabla `turnos` tiene `ultimo_ping TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`. El WebSocket maneja el mensaje `{"type": "ping"}` actualizando `ultimo_ping` en la DB y respondiendo `{"type": "pong"}`. El worker llama a `get_turnos_a_notificar()` para identificar turnos con `ultimo_ping` hace más de 3 minutos y les envía un `ping_request` WebSocket. Luego `cancelar_inactivos()` cancela los que aún no respondieron.

### Sustento

El mecanismo de ping/pong es el estándar para mantener vivo un WebSocket y detectar inactividad real. Un estudiante con la app abierta responde el ping automáticamente; uno que cerró la app deja de responder. La columna `ultimo_ping` en la DB es la fuente de verdad — funciona incluso si el WebSocket se reconecta (el nuevo ping actualiza la columna). El trade-off aceptado es que el cliente debe implementar el ping periódico; si no lo hace, el turno se cancela aunque el estudiante esté esperando. El cliente React Native debe enviar pings cada ~30 segundos.

## ADR-TUR-005 — Cancelación y llamada publican a RabbitMQ para M4 y M5

**Categoría:** Gestión de Recursos

### Contexto

Cuando el worker cancela un turno por inactividad o cuando se llama al siguiente estudiante, se deben disparar acciones en otros módulos: M4 debe enviar push notification, M5 debe registrar el evento. Se debe decidir cómo se coordinan estas acciones.

### Alternativas

1. **Llamadas directas desde el worker a los servicios de M4 y M5.** Acopla el worker a los módulos de notificaciones y seguimiento. Un fallo en M4 podría afectar la operación del worker.

2. **Publicación en RabbitMQ con routing key por tipo de evento.** El worker publica `turno.cancelado` o `turno.llamado` en el exchange de RabbitMQ. M4 y M5 consumen de sus propias colas independientemente. El worker no sabe ni le importa si hay consumidores.

### Criterios de Elección

- **Desacoplamiento:** el worker no debe depender de M4 ni M5.
- **Resiliencia:** un fallo en M4 no debe afectar la operación de la cola.
- **Extensibilidad:** agregar más consumidores sin modificar el worker.

### Decisión

El worker publica `turno.cancelado` (para M4 y M5) y `turno.llamado` (para M4) en RabbitMQ. Adicionalmente, si el estudiante está conectado por WebSocket, también le envía la notificación directamente por ese canal (`manager.send()`). El WebSocket y RabbitMQ son canales complementarios.

### Sustento

RabbitMQ desacopla completamente el worker de los consumidores. La entrega por WebSocket es más rápida (< 100ms) y llega aunque el servicio de push esté caído. La entrega por push (M4) llega aunque el WebSocket esté desconectado. Los dos canales se complementan para cubrir distintos escenarios de conectividad. El trade-off aceptado es que un mensaje puede llegar dos veces al estudiante (WebSocket + push); la app debe manejar este caso mostrando el mismo estado.

## ADR-TUR-006 — Despliegue del módulo de gestión de turnos: FastAPI modular en monolito

**Categoría:** Mapeo entre Elementos Arquitectónicos

### Contexto

M3 (gestión de turnos) y M2 (gestión de colas) comparten el mismo módulo `queues/` en la implementación actual. El worker de inactividad debe correr en el mismo proceso para acceder al WebSocket manager singleton.

### Alternativas

1. **Worker en proceso separado.** El worker no puede acceder al `QueueConnectionManager` del servidor sin protocolo de comunicación adicional. Requeriría una API inter-proceso para enviar mensajes WebSocket.

2. **Worker como tarea asyncio dentro del mismo proceso FastAPI.** El worker comparte el event loop y el objeto `manager` con el router. Los mensajes WebSocket desde el worker llegan a los mismos clientes conectados al router.

### Criterios de Elección

- **Acceso al singleton** `QueueConnectionManager`.
- **Simplicidad operativa.**

### Decisión

El worker asyncio corre en el mismo proceso FastAPI. En `src/main.py`, al arrancar la app se ejecuta `asyncio.create_task(inactivity_worker())`.

### Sustento

El singleton `manager = QueueConnectionManager()` definido en `manager.py` es la misma instancia importada por el router y por el worker. Esto es posible solo porque ambos corren en el mismo proceso Python. Separar el worker en un proceso diferente requeriría un mecanismo de IPC (Redis Pub/Sub, socket) para que el worker acceda al estado de conexiones del router — complejidad innecesaria. El trade-off aceptado es que un crash del worker afecta al proceso principal; el try/except en el loop del worker previene que errores individuales propaguen.

## ADR-TUR-007 — Bloque de tiempo del turno resuelto desde `turno_dia` en tiempo de ejecución

**Categoría:** Tiempo de Enlace

### Contexto

Cada turno pertenece a una instancia diaria del servicio (`turno_dia`) que tiene su propio horario y capacidad. El bloque de tiempo asignado al turno (qué hora le toca comer) se calcula a partir de `numero_turno` y `raciones_max`.

### Alternativas

1. **Bloques hardcodeados en código.** Cambiar los bloques requiere redespliegue. No apto para operación flexible.

2. **Leídos de `turno_dia` en tiempo de ejecución.** `calcular_turno_asignado(numero_turno, raciones_max)` computa el bloque horario dinámicamente a partir de los parámetros del `turno_dia` activo. El resultado se incluye en `TurnoStatusResponse` cuando el estado es `ATENDIDO`.

### Criterios de Elección

- **Flexibilidad:** el administrador puede cambiar el aforo por bloque sin redespliegue.
- **Sin almacenamiento adicional:** el bloque se calcula, no se persiste.

### Decisión

El bloque de tiempo del turno se resuelve en tiempo de ejecución mediante `calcular_turno_asignado(numero_turno, raciones_max)`. La instancia `turno_dia` es consultada en cada request que necesita los parámetros del día.

### Sustento

Calcular el bloque en tiempo de ejecución evita almacenar datos derivados que podrían quedar inconsistentes si cambia la configuración. `turno_dia` puede tener overrides de `raciones_max` respecto a `turnos_config`, por lo que el cálculo siempre usa los parámetros del día específico. El trade-off aceptado es que el cálculo ocurre en cada request de status; con la fórmula simple que mapea número a bloque horario, el costo computacional es despreciable.

## ADR-TUR-008 — Patrón Singleton (WebSocket manager) y Observer (WebSocket in-process)

**Categoría:** Elección de Tecnología

### Contexto

El sistema necesita notificar en tiempo real a estudiantes cuando su turno es llamado o cancelado. Se debe decidir cómo estructurar el componente que gestiona las conexiones WebSocket y cómo coordinar las notificaciones entre el router y el worker.

### Alternativas

1. **Múltiples instancias del manager.** El router y el worker tendrían managers distintos, con distintos clientes conectados. Las notificaciones del worker no llegarían a los clientes del router.

2. **Singleton compartido: `manager = QueueConnectionManager()` a nivel de módulo.** Una única instancia del manager se importa tanto en el router como en el worker. El mapa `{codigo: WebSocket}` es compartido.

3. **Observer in-process: el manager actúa como Subject que notifica a los WebSocket conectados.** El worker actúa como Observer que llama a `manager.send(codigo, mensaje)` cuando detecta un cambio de estado. Los WebSocket conectados son los Observers finales que reciben el mensaje.

### Criterios de Elección

- **Un único mapa de conexiones** accesible desde router y worker.
- **Notificación push** sin polling del cliente.
- **Desacoplamiento** entre quien detecta el evento (worker) y quien recibe (cliente WebSocket).

### Decisión

`QueueConnectionManager` se implementa como Singleton (`manager = QueueConnectionManager()` en `manager.py`). El router y el worker lo importan directamente. Esta es la implementación del patrón Observer WebSocket in-process documentado en [11.5](../../11/11.5/11.5.md).

### Sustento

El Singleton garantiza que el router y el worker operen sobre el mismo mapa de conexiones `{codigo: WebSocket}`. El patrón Observer se realiza cuando el worker detecta que un turno fue llamado (Subject genera evento) y llama a `manager.send(codigo, {"type": "llamado"})` — el WebSocket del cliente (Observer) recibe el mensaje. `manager.send()` maneja silenciosamente el caso de conexión cerrada desconectando al cliente del mapa. El trade-off aceptado es el acoplamiento por instancia global compartida; esto es intencional y documentado como decisión de diseño.
