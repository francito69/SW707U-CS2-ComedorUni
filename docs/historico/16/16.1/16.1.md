# 16.1. Módulo 1 / Integrante 1

**Módulos cubiertos:** M1 – Autenticación · M4 – Notificaciones · M5 – Seguimiento

**Transacción principal elegida:** *Autenticar estudiante* (M1) — `POST /parse-data` seguido de `POST /verify-biometric`, implementada de extremo a extremo. Se complementa con la consulta de sesión (`GET /me`) y se describen los flujos asíncronos de M4 (notificación) y M5 (seguimiento).

---

## Funcionalidad incluida

### Flujo principal — Autenticación del estudiante (M1)

El estudiante inicia sesión: el backend parsea el HTML de ORCE para obtener su perfil y foto vigente, crea una sesión en Redis y devuelve un `sid`; luego verifica su identidad comparando la selfie contra la foto institucional.

**Entradas:**
- `POST /parse-data`: `home_html`, `cursos_html`, `datos_html` (HTML capturado del portal ORCE).
- `POST /verify-biometric`: `sid`, `photo_base64` (selfie del estudiante).

**Salidas:**
- `parse-data` → `200` con `sid`, `nombre`, `codigo`, `email`, `creditos_llevados`.
- `verify-biometric` → `200` con `verified`, `distance`, `message`.
- Errores: `401` (sid inválido/expirado), `404` (sin foto de referencia), `500` (error de parseo o biometría).

**Componentes C4 que participan** (ver [15.1](../../15/15.1/15.1.md)):

| Componente C4 | Rol en la transacción |
|---|---|
| App Móvil | Captura el HTML de ORCE y la selfie; almacena el `sid` |
| API Backend → `auth.router` | Expone `/parse-data`, `/verify-biometric`, `/me`, `/logout` |
| Servicio de Autenticación | Orquesta scraping + biometría + sesión |
| Servicio de Scraping | Extrae perfil y foto vigente del HTML de ORCE |
| Servicio de Biometría | Compara selfie vs foto vigente (deepface) |
| Gestor de Sesiones → Redis | Crea/valida el `sid` con TTL |
| PostgreSQL (`estudiantes`) | Persiste/actualiza el perfil |

Código: [auth/router.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) · [auth/service.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/service.py) · [auth/biometric.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/biometric.py).

### Flujos complementarios — M4 y M5

- **M4 (Notificaciones):** consumer de RabbitMQ ([notifications/consumer.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/notifications/consumer.py)) que ante `turno.llamado`/`turno.cancelado` despacha push (Expo) y registra el envío.
- **M5 (Seguimiento):** consumer ([tracking/consumer.py](../../s111-actividad-bosquejo-implementacion/backend/src/modules/tracking/consumer.py)) que persiste `turno.atendido`/`turno.encolado` en el historial; el estado en tiempo real se entrega por WebSocket.

## Criterios de elección

| Criterio | Justificación |
|---|---|
| Valor para el negocio | Sin autenticación no hay acceso al sistema: es la puerta de entrada de todo el flujo del estudiante. |
| Frecuencia de uso | Ocurre en cada inicio de sesión y al reabrir la app (`/me`). |
| Riesgo técnico | Es la transacción más compleja de M1 (scraping + biometría + sesión); demostrarla valida el diseño completo. |
| Cobertura de escenarios de calidad | Ejercita seguridad (biometría, sesión con TTL) y rendimiento (verificación en memoria) de la Sección 2. |
| Dependencia de otros módulos | M2/M3/M5 dependen de la sesión creada aquí (`sid`). |

## Instrucciones de ejecución

### Dependencias

- Docker (PostgreSQL/Redis/RabbitMQ) y Python 3.11+.
- Backend en [s111-actividad-bosquejo-implementacion/backend](../../s111-actividad-bosquejo-implementacion/backend).

### 1. Levantar infraestructura y backend

```bash
# Desde s111-actividad-bosquejo-implementacion/
docker compose up -d            # postgres (5433), redis (6379), rabbitmq (5672)

# Desde s111-actividad-bosquejo-implementacion/backend/
pip install -r requirements.txt
python run.py                   # uvicorn en http://localhost:8000 (.env fija DB_PORT=5433)
```

### 2. Ejecutar la transacción principal

```bash
# Login: parsea el HTML de ORCE y crea sesion -> devuelve sid
curl -X POST http://localhost:8000/parse-data \
  -H "Content-Type: application/json" \
  -d '{"home_html":"<html>...</html>","cursos_html":"<html>...</html>","datos_html":"<html>...</html>"}'

# Verificar identidad con el sid devuelto + selfie
curl -X POST http://localhost:8000/verify-biometric \
  -H "Content-Type: application/json" \
  -d '{"sid":"<sid_devuelto>","photo_base64":"/9j/4AAQSkZJRgAB..."}'

# Validar sesion al reabrir la app
curl "http://localhost:8000/me?sid=<sid_devuelto>"
```

> **Datos de prueba:** se requiere HTML real de ORCE y una selfie en base64. Para la sustentación se usa la captura del portal del estudiante; `deepface` descarga sus modelos en la primera ejecución (puede tardar). Documentación interactiva en `http://localhost:8000/docs`.

## Alcance y límites

**Dentro del prototipo:**
- M1: login con scraping de ORCE, verificación biométrica, sesión en Redis con TTL, `/me` y `/logout`.
- M4/M5: consumers que procesan eventos de turno (push e historial) y WebSocket de seguimiento.

**Fuera del prototipo (diseño, ver [15.1](../../15/15.1/15.1.md)):**
- JWT y blacklist de revocación (hoy sesión por `sid`).
- Logging estructurado y política de reintento/DLQ centralizada en los consumers.
- Réplicas, balanceador, réplica standby de PostgreSQL y Redis con AOF en producción.

Quedaron fuera por ser endurecimientos de seguridad/HA cuyo valor se demuestra en el diseño, no en el flujo funcional mínimo.
