# 12.1. Módulo 1 / Integrante 1

**Módulos cubiertos:** M1 – Autenticación · M4 – Notificaciones · M5 – Seguimiento

---

## Preocupaciones transversales identificadas

| Módulo(s) afectado(s) | Aspecto (concern transversal) | Punto de corte (pointcut) | Advice (tipo + descripción) |
|---|---|---|---|
| M1, M4, M5 | Logging de operaciones | Toda función de servicio en M1 y todo handler `_handle()` en M4 y M5 | **around** — registra la entrada (función, parámetros relevantes) antes de ejecutar y la salida (resultado o excepción) al terminar, incluyendo duración |
| M1 | Validación de sesión | Todo endpoint de M1 que recibe `sid` como parámetro (`verify_biometric`, `get_me`, `logout`) | **before** — extrae el `sid`, consulta Redis con `get_session()` y lanza `HTTPException 401` si la sesión no existe o expiró, antes de que el handler ejecute ninguna lógica |
| M4, M5 | Manejo de errores en consumers | Toda función `_handle(message)` de los consumers RabbitMQ de M4 y M5 | **after-throwing** — captura cualquier excepción no manejada, la registra con contexto estructurado (módulo, routing key, timestamp, payload resumido) y decide el comportamiento de acknowledge |

---

## Descripción de cada aspecto

### Aspecto 1 — Logging de operaciones

**Módulos afectados:** M1, M4, M5

**Situación actual:** el logging está implementado como sentencias `print()` dispersas en cada módulo. En M1 hay dos puntos (`[*] Estudiante guardado en DB:` y `[!] Error en comparación biométrica:`); en M4 y M5 cada consumer tiene su propio bloque `except Exception as e: print(...)`. El formato, la granularidad y la presencia del log dependen de quién escribió cada función.

**Por qué conviene tratarlo como aspecto:** el logging no forma parte de la lógica de negocio de ninguno de estos módulos; es una responsabilidad de observabilidad que debe aplicarse de forma uniforme a todas las operaciones. Dispersarlo en el código de negocio mezcla dos responsabilidades distintas y hace que añadir o cambiar el formato (por ejemplo, pasar de `print()` a un logger estructurado en JSON) requiera tocar cada función individualmente.

**Pointcut:** toda función de servicio de M1 ([`src/modules/auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py)) y toda función `_handle()` de los consumers de M4 ([`src/modules/notifications/consumer.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/notifications/consumer.py)) y M5 ([`src/modules/tracking/consumer.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/tracking/consumer.py)).

**Advice (`around`):**
```python
# Especificación conceptual del advice de logging
async def logging_advice(joinpoint):
    logger.info(f"[{joinpoint.module}] → {joinpoint.function}({joinpoint.args_summary})")
    start = time.monotonic()
    try:
        result = await joinpoint.proceed()
        elapsed = time.monotonic() - start
        logger.info(f"[{joinpoint.module}] ✓ {joinpoint.function} ({elapsed:.2f}s)")
        return result
    except Exception as e:
        logger.error(f"[{joinpoint.module}] ✗ {joinpoint.function} — {type(e).__name__}: {e}")
        raise
```

### Aspecto 2 — Validación de sesión

**Módulos afectados:** M1

**Situación actual:** los endpoints `verify_biometric`, `get_me` y `logout` en [`src/modules/auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) llaman a `get_session(sid)` al inicio de su lógica y lanzan `HTTPException 401` si la sesión no existe. Es código de validación repetido que no pertenece al propósito de negocio de cada endpoint (verificar biometría, devolver datos del usuario, cerrar sesión).

En M2/M3, el mismo patrón aparece como la función `_require_session()` extraída en [`src/modules/queues/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/queues/router.py) — lo que prueba que ya se reconoció la repetición, pero la solución fue un helper manual, no una solución transversal.

**Por qué conviene tratarlo como aspecto:** la lógica de validación de sesión es idéntica en todos los endpoints protegidos. Si el mecanismo de sesión cambia (por ejemplo, migrar de Redis a JWT), habría que buscar y modificar cada punto manualmente. Un aspecto centraliza esa lógica en un único lugar; basta con que el endpoint declare que requiere sesión válida.

**Pointcut:** todo endpoint HTTP de M1 que recibe `sid` como parámetro de request body o query param.

**Advice (`before`):**
```python
# Especificación conceptual del advice de validación de sesión
def session_guard_advice(joinpoint):
    sid = joinpoint.extract_param("sid")
    session = get_session(sid)
    if not session:
        raise HTTPException(status_code=401, detail="Sesión inválida o expirada")
    joinpoint.context["session"] = session   # disponible para el handler sin volver a leer Redis
    joinpoint.proceed()
```

### Aspecto 3 — Manejo de errores en consumers

**Módulos afectados:** M4, M5

**Situación actual:** tanto `_handle()` en M4 ([`notifications/consumer.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/notifications/consumer.py)) como en M5 ([`tracking/consumer.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/tracking/consumer.py)) tienen el mismo patrón:

```python
try:
    ...  # lógica del consumer
except Exception as e:
    print(f"[M?] Error procesando mensaje: {e}")
```

El bloque `except` no distingue el tipo de error, no registra el payload que causó el fallo, no decide si el mensaje debe reencolar (`nack` con `requeue=True`) o descartarse, y usa `print()` en lugar de logging estructurado.

**Por qué conviene tratarlo como aspecto:** el comportamiento ante un error de consumer —registrar, clasificar y hacer ack/nack— es idéntico en M4 y M5 (y será igual en cualquier consumer futuro). Incluirlo en la lógica de cada handler mezcla la responsabilidad de procesamiento de mensajes con la de manejo de infraestructura. Un aspecto centraliza la política de error: si se decide añadir reintentos con backoff exponencial, se cambia en un único lugar.

**Pointcut:** toda función `_handle(message: aio_pika.IncomingMessage)` de cualquier consumer RabbitMQ del sistema.

**Advice (`after-throwing`):**
```python
# Especificación conceptual del advice de manejo de errores en consumers
async def consumer_error_advice(joinpoint, exception):
    routing_key = joinpoint.context.get("routing_key", "unknown")
    module      = joinpoint.module
    payload_raw = joinpoint.context.get("message_body", b"")[:200]  # primeros 200 bytes

    logger.error(
        f"[{module}] Error en consumer — routing_key={routing_key} "
        f"error={type(exception).__name__}: {exception} "
        f"payload_preview={payload_raw}"
    )

    if isinstance(exception, (ValueError, KeyError)):
        # Mensaje malformado — descartar sin reencolar
        await joinpoint.context["message"].reject(requeue=False)
    else:
        # Error transitorio (DB caída, push service no disponible) — reencolar
        await joinpoint.context["message"].reject(requeue=True)
```
