## M1 — Autenticación

### Contexto del módulo

El módulo de Autenticación es el punto de entrada al sistema. Su responsabilidad es validar la identidad del estudiante mediante credenciales institucionales Google (`@uni.pe`), crear sesiones personales e intransferibles mediante JWT de corta duración almacenados en cookies HttpOnly, y registrar todos los eventos de acceso para auditoría. También gestiona la captura y almacenamiento de la foto biométrica del estudiante, utilizada por el personal del comedor para confirmar identidad física en el punto de atención.

El módulo es transversal: todos los demás módulos del sistema dependen de él para verificar que cada solicitud proviene de un estudiante activo y autenticado. La verificación de identidad ocurre en cada request autenticado, por lo que su latencia impacta directamente la experiencia del estudiante durante los picos de demanda del horario de comedor.

**Atributos de calidad prioritarios:**

| Atributo | Medida clave |
|---|---|
| Seguridad | 100% de intentos no autorizados bloqueados; 0 sesiones inválidas reutilizadas |
| Disponibilidad | ≥ 99.5% del servicio; recuperación < 5s ante fallo del proveedor externo |
| Rendimiento | Autenticación < 2s; cierre de sesión < 1s; latencia < 3s en hora pico |

**Volumen y concurrencia esperados:** picos de autenticaciones simultáneas al inicio de la jornada académica y en el horario de comedor. El módulo no maneja grandes flujos de datos, pero sí consultas de verificación frecuentes en el camino crítico de cada operación del sistema.

---

### Patrones aplicables

#### Categoría de Módulo: Capas (Layered)

El módulo se organiza internamente en cuatro capas:

- **Capa de API:** expone los endpoints del flujo OAuth (inicio, callback, cierre de sesión) y la gestión de foto biométrica.
- **Capa de Lógica de Negocio:** orquesta la validación del token de Google, la verificación del dominio institucional en el backend, la aplicación del rate limiting sobre los endpoints de autenticación y la detección de cuentas duplicadas.
- **Capa de Integración Externa:** encapsula la comunicación con Google Identity Services para la validación del token y con el servicio de almacenamiento de objetos para las fotos biométricas.
- **Capa de Datos:** persiste el perfil del usuario con identificador interno (UUID desacoplado del proveedor externo), referencia a foto biométrica, estado de cuenta y timestamps de auditoría. También gestiona la lista negra de tokens revocados en Redis y las sesiones activas.

**Justificación:** La seguridad es el atributo dominante del módulo y la separación en capas es la principal garantía de que las reglas de validación institucional no puedan ser eludidas desde la interfaz de entrada. Si se cambia el proveedor de identidad externo o el mecanismo de sesión, la capa de lógica de negocio permanece intacta. Del mismo modo, el almacenamiento de fotos biométricas está encapsulado en la capa de integración, permitiendo cambiar el servicio de almacenamiento sin tocar la lógica de acceso. La mantenibilidad del módulo depende directamente de esta separación, dado que cada regla de seguridad tiene un lugar único y claro donde vive.

---

#### Categoría de Componente y Conector: Cliente-Servidor

El módulo opera con un modelo Cliente-Servidor en dos niveles:

- El **frontend del estudiante** es el cliente que inicia el flujo OAuth y recibe el JWT; el servidor gestiona el callback, valida el token y crea la sesión.
- El módulo actúa a su vez como **cliente** del servicio externo de Google Identity Services al verificar criptográficamente el token recibido.

La verificación de identidad en los requests subsecuentes se realiza mediante un middleware síncrono ejecutado en el mismo proceso que el resto de los módulos. Esto permite verificar el JWT y consultar el estado de la cuenta en Redis como una llamada a función sin latencia de red, cumpliendo el tiempo de respuesta exigido por los escenarios de rendimiento.

**Justificación:** La autenticación es una operación inherentemente síncrona: el estudiante espera el resultado antes de poder realizar cualquier acción en el sistema. El modelo Cliente-Servidor es la elección directa y justificada. Pub/Sub no aplica porque el flujo de login requiere una respuesta inmediata y determinista. Peer-to-Peer no aplica porque los recursos de validación y sesión son centralizados por diseño de seguridad: cualquier descentralización abriría vectores de ataque inaceptables para este módulo.

---

#### Categoría de Asignación: Multi-Tier

El módulo se despliega integrado en el monolito modular junto con el resto del sistema, siguiendo una arquitectura de tres niveles:

- **Tier de Presentación:** balanceador de carga y frontend que inicia el flujo OAuth y presenta la interfaz de login.
- **Tier de Aplicación:** monolito modular donde el middleware de autenticación verifica el JWT en cada request sin latencia de red al ejecutarse en el mismo proceso.
- **Tier de Datos:** PostgreSQL para el perfil de usuario, Redis para la lista negra de tokens y el estado de sesión.

**Justificación:** La separación entre el tier de aplicación y el tier de datos garantiza que la base de usuarios, las sesiones y las fotos biométricas no sean accesibles directamente desde el exterior. Las fotos se sirven mediante URLs pre-firmadas con expiración de 5 minutos, de modo que el acceso está controlado por el tier de aplicación en cada solicitud. Desplegar el módulo dentro del monolito en lugar de como microservicio independiente es una decisión deliberada: la verificación de identidad en el camino crítico de cada request se beneficia de la latencia cero de la llamada a función local. Para el volumen universitario esperado, esta simplicidad operativa supera el beneficio de escalar el módulo de autenticación de forma independiente.

---

### Combinación de patrones

```
Multi-Tier (asignación)
  └── Capas (organización interna del módulo)
        └── Cliente-Servidor (interacción en tiempo de ejecución)
```

No se produce un ADR de patrones para este módulo porque no existen alternativas razonablemente comparables en la dimensión de comunicación: el flujo de autenticación es síncrono por definición y centralizado por requisito de seguridad.

## M4 — Notificaciones

### Contexto del módulo

El módulo de Notificaciones informa a los estudiantes sobre los eventos críticos del ciclo de vida de su turno: asignación, activación, solicitud de confirmación de asistencia, liberación y reasignación. Los eventos se originan en distintos módulos del sistema —el módulo de cola virtual, el de gestión de cola y el de confirmación— y deben llegar al estudiante con latencia mínima. Una notificación tardía de confirmación puede hacer que el estudiante pierda su cupo, por lo que el tiempo de entrega es un atributo crítico.

El canal principal de entrega es Server-Sent Events (SSE): conexión persistente unidireccional servidor→cliente, con reconexión automática y reenvío de eventos perdidos mediante el header `Last-Event-ID` para cubrir casos de red intermitente. El correo institucional actúa como canal de respaldo para cuando el estudiante tiene la app cerrada. Las notificaciones se persisten en base de datos con estados `PENDIENTE / ENTREGADO / EXPIRADO` para garantizar reentrega y trazabilidad. El módulo también gestiona las preferencias de notificación de cada estudiante y registra cada envío para auditoría.

**Atributos de calidad prioritarios:**

| Atributo | Medida clave |
|---|---|
| Rendimiento | Notificación emitida < 2s tras evento crítico; latencia < 3s en hora pico |
| Disponibilidad | ≥ 99% de disponibilidad; 0 pérdida de registro; tasa de entrega ≥ 99% |
| Seguridad | 100% de notificaciones con trazabilidad; cambios de preferencia solo por usuario autorizado |

**Volumen y concurrencia esperados:** ráfagas de notificaciones simultáneas en los horarios de activación de turnos. Se proyectan cientos de conexiones SSE concurrentes durante el horario de comedor, gestionadas con un límite explícito y reconexión con backoff exponencial en el cliente. Los módulos productores de eventos son transaccionales y no deben verse afectados por el estado o la latencia del módulo de Notificaciones.

---

### Patrones aplicables

#### Categoría de Módulo: Capas (Layered)

El módulo se organiza en cuatro capas:

- **Capa de Streaming / API:** gestiona las conexiones SSE activas, el límite de conexiones concurrentes con rechazo controlado (HTTP 503 + `Retry-After`) y la lógica de reconexión con `Last-Event-ID`.
- **Capa de Lógica de Despacho:** determina los canales activos según las preferencias del estudiante, selecciona y renderiza la plantilla del mensaje con sus variables dinámicas, y coordina con el módulo de cola el inicio del temporizador de confirmación una vez confirmada la entrega.
- **Capa de Adaptadores de Canal:** implementaciones específicas por canal — SSE para tiempo real y SMTP para correo de respaldo. Cada adaptador es independiente; agregar un nuevo canal (push nativo, SMS) implica añadir un adaptador sin modificar la lógica de despacho.
- **Capa de Persistencia:** almacena el historial de notificaciones con su estado y payload por tipo, y las preferencias del estudiante.

**Justificación:** La separación de la lógica de despacho de los adaptadores de canal es la decisión de diseño más relevante del módulo. Si en el futuro se incorpora un canal adicional, solo se añade un adaptador nuevo sin tocar la lógica de despacho ni los módulos productores. Esto favorece directamente la **mantenibilidad** y reduce el riesgo de regresión en funcionalidad existente. La capa de persistencia separada garantiza que el historial y la trazabilidad de envíos sean independientes del canal utilizado, satisfaciendo el atributo de **seguridad** (auditoría completa).

---

#### Categoría de Componente y Conector: Publicar-Suscribir (Pub/Sub)

*(Ver ADR a continuación para el análisis detallado de alternativas.)*

Los módulos productores publican eventos de dominio (`TurnoAsignado`, `CupoLiberado`, `ConfirmacionPendiente`, `TurnoLiberado`, `TurnoReasignado`) mediante un bus de eventos interno en memoria. El módulo de Notificaciones suscribe a estos eventos y los procesa de forma asíncrona, sin que los módulos productores conozcan los canales de entrega ni esperen confirmación de despacho.

La entrega final al estudiante usa SSE: una vez que el módulo de Notificaciones procesa el evento y genera el mensaje, lo envía por la conexión SSE activa del estudiante. Si el estudiante está desconectado, la notificación queda en estado `PENDIENTE` y se reenvía al reconectar mediante `Last-Event-ID`.

---

#### Categoría de Asignación: Multi-Tier

El módulo se despliega dentro del monolito modular:

- **Tier de API:** las conexiones SSE son gestionadas por el backend en Python con FastAPI y Uvicorn (servidor ASGI), aprovechando el modelo de I/O asíncrono basado en `async/await`, lo que permite manejar cientos de conexiones concurrentes sin modelo de hilos bloqueantes.
- **Tier de Aplicación:** lógica de despacho, adaptadores de canal y gestión de preferencias.
- **Tier de Datos:** PostgreSQL para el historial de notificaciones con estados y Redis para el estado de entrega de alta frecuencia.

**Justificación:** El despliegue dentro del monolito permite que el bus de eventos interno opere sin latencia de red entre módulos, lo que es determinante para cumplir el tiempo de despacho de < 2s. FastAPI con Uvicorn maneja las conexiones SSE concurrentes eficientemente mediante corrutinas asíncronas en un único proceso. Si el volumen de conexiones creciera significativamente, el módulo puede extraerse como servicio independiente con un broker externo; el desacoplamiento vía Pub/Sub hace que esta migración no requiera cambios en los módulos productores.

### ADR: Patrón de comunicación para el módulo de Notificaciones

**Categoría de decisión:** Modelo de Coordinación — elección de patrón de Componente y Conector entre los módulos productores de eventos y el módulo de Notificaciones.

---

**Contexto:**

El módulo de Notificaciones recibe eventos generados en distintos módulos del sistema. La asignación de turno proviene del módulo de cola virtual, la liberación de cupo del módulo de gestión de cola, y la solicitud de confirmación del módulo de confirmación. Estos eventos tienen naturaleza crítica: si la notificación de confirmación no llega al estudiante en segundos, su cupo puede expirar y ser liberado a otro estudiante.

Los módulos productores son transaccionales y procesan operaciones de alta concurrencia durante el horario de comedor. El módulo de Notificaciones puede tener picos de carga propios —ráfagas de envíos simultáneos— que no deben propagarse como degradación a los módulos de negocio. Todos los módulos se despliegan en el mismo proceso en esta iteración.

---

**Alternativas:**

**Alternativa 1 — Cliente-Servidor síncrono (llamada directa entre módulos)**

Cada módulo productor invoca directamente al módulo de Notificaciones cuando ocurre un evento relevante, esperando respuesta antes de continuar.

- Simple de implementar y fácil de rastrear en logs.
- Acoplamiento temporal fuerte: si el módulo de Notificaciones está degradado o lento, el módulo de cola experimenta la misma latencia, afectando directamente el procesamiento de turnos en hora pico.
- Agregar un nuevo canal de salida (correo, SMS, push) requiere modificar el contrato de llamada en cada módulo productor.
- No favorece la disponibilidad independiente de cada módulo.

**Alternativa 2 — Publicar-Suscribir asíncrono con bus de eventos interno**

Los módulos productores publican eventos de dominio en un bus interno; el módulo de Notificaciones suscribe y procesa de forma asíncrona. En esta iteración, el bus se implementa con colas asíncronas de Python (`asyncio.Queue`) en el mismo proceso; si el sistema escala, puede reemplazarse por un broker externo sin modificar a los productores.

- Desacoplamiento temporal y lógico: una degradación del módulo de Notificaciones no afecta al módulo de cola.
- Agregar o quitar canales de salida solo requiere modificar el módulo de Notificaciones.
- Los eventos no entregados por el bus (proceso caído) se recuperan desde el historial persistido en base de datos con estado `PENDIENTE`.
- Introduce indirección en el flujo que puede dificultar el rastreo inicial; se mitiga con logging estructurado en el módulo de Notificaciones.

---

**Criterios de elección:**

| Criterio | Peso | Justificación |
|---|---|---|
| Desacople entre módulos productores y canal de entrega | Alto | Los módulos transaccionales no deben verse afectados por el estado del módulo de Notificaciones |
| Resiliencia ante degradación del módulo de Notificaciones | Alto | Una falla en notificaciones no debe impedir procesar turnos |
| Extensibilidad de canales sin modificar productores | Medio | Se prevé incorporar nuevos canales en iteraciones futuras |
| Rendimiento ante ráfagas simultáneas | Alto | Ráfagas en horario pico requieren procesamiento concurrente sin bloquear al productor |
| Complejidad operativa | Medio | El bus interno elimina la necesidad de un broker externo en esta iteración |

---

**Decisión:**

Se adopta el patrón **Publicar-Suscribir** para la comunicación entre los módulos productores y el módulo de Notificaciones, implementado mediante un bus de eventos interno en memoria (usando el módulo `asyncio` y colas asíncronas de Python). La entrega final al estudiante se realiza mediante SSE.

---

**Sustento:**

El desacoplamiento temporal que ofrece Pub/Sub es determinante para que una degradación del módulo de Notificaciones no se propague al módulo de cola virtual durante el procesamiento de turnos en hora pico. Esto se alinea directamente con el atributo de **disponibilidad** del sistema.

La arquitectura de suscriptores por canal permite incorporar nuevos medios de comunicación sin modificar ningún módulo productor, lo que favorece la **mantenibilidad** y reduce el riesgo de regresiones en los módulos transaccionales.

El bus interno en memoria es suficiente para el volumen universitario esperado y elimina la complejidad operativa de un broker externo en esta iteración. El trade-off aceptado es que si el proceso se reinicia, los eventos en tránsito en el bus se pierden; esto se mitiga con el historial persistido en base de datos con estado `PENDIENTE`, que permite reenviar notificaciones no entregadas al reconectar el cliente SSE.

---

### Combinación de patrones

```
Multi-Tier (asignación)
  └── Capas (organización interna del módulo)
        ├── Pub/Sub interno (coordinación con módulos productores)
        └── SSE como mecanismo de entrega al cliente final
```

## M5 — Seguimiento

### Contexto del módulo

El módulo de Seguimiento proporciona visibilidad en tiempo real sobre el estado de los turnos, la posición en la cola y el historial completo de eventos del proceso. Es consumido por los estudiantes para consultar su estado actual y su historial de turnos, y por el personal administrativo para auditoría, reportes y monitoreo en tiempo real del comedor.

El módulo registra automáticamente todos los eventos relevantes del sistema con timestamp, actor y descripción, garantizando trazabilidad completa. Los eventos provienen de los módulos de cola virtual, confirmación, validación en comedor y gestión de cola. El dashboard de monitoreo en tiempo real para el personal del comedor se alimenta de contadores en Redis actualizados incrementalmente con cada evento, mientras que las estadísticas históricas se sirven desde vistas materializadas actualizadas cada 5 minutos para no competir con las escrituras de la tabla de eventos durante el horario de comedor.

Los eventos se almacenan en PostgreSQL con particionamiento mensual, con una política de retención de 6 meses y archivado antes del descarte. El historial de inasistencias y penalizaciones se mantiene en tablas propias de forma indefinida.

**Atributos de calidad prioritarios:**

| Atributo | Medida clave |
|---|---|
| Disponibilidad | ≥ 99.5%; 0 pérdida de historial; recuperación < 5s ante fallo transitorio |
| Rendimiento | Consulta de estado < 2s; posición en cola < 2s; historial reciente < 3s |
| Usabilidad | Estado comprensible sin instrucción adicional; ambigüedad resuelta < 10s |
| Seguridad | 100% de consultas no autorizadas rechazadas; 100% de acciones auditables |

**Volumen y concurrencia esperados:** consultas concurrentes frecuentes durante toda la jornada académica, con picos en los horarios de activación de turnos. Las escrituras (registro de eventos) son intensivas durante el horario de comedor; las lecturas para reportes y estadísticas se orientan a datos pre-calculados para no competir con la ingesta.

---

### Patrones aplicables

#### Categoría de Módulo: Capas (Layered)

El módulo se organiza en capas diferenciadas según el tipo de operación:

- **Capa de API:** expone endpoints REST para consulta de estado del turno, posición en cola, historial de eventos y reportes. También expone el stream SSE del dashboard de monitoreo en tiempo real para el personal del comedor.
- **Capa de Lógica de Consulta:** calcula la posición en cola a partir del estado en Redis, agrega eventos del historial, filtra la información según el rol del usuario (estudiante ve solo sus datos; personal autorizado accede a cualquier estudiante) y genera reportes administrativos a partir de vistas materializadas.
- **Capa de Ingesta de Eventos:** consume los eventos de dominio publicados por los módulos de negocio y los persiste en la tabla de eventos. Para eventos de alta criticidad (no-show, penalización), la persistencia ocurre de forma síncrona dentro de la misma transacción. Para el resto, la ingesta es asíncrona.
- **Capa de Persistencia:** tabla de eventos particionada mensualmente, tabla de inasistencias append-only, tabla de penalizaciones activas con versionado de reglas, vistas materializadas para estadísticas históricas y contadores en Redis para indicadores en tiempo real.

**Justificación:** La separación entre la capa de ingesta de eventos y la capa de consulta es especialmente importante en este módulo. La ingesta es intensiva en escrituras durante el horario de comedor, mientras que las consultas de historial y reportes son lecturas complejas con agregaciones. Mezclarlas en una sola capa generaría contención de recursos y degradaría la **disponibilidad** del módulo. La capa de lógica de consulta también centraliza el control de acceso por rol, favoreciendo el atributo de **seguridad**: un estudiante nunca puede ver el historial de otro, y esta validación ocurre en un único lugar.

---

#### Categoría de Componente y Conector (1): MVC

La interfaz de consulta para el estudiante sigue el patrón Modelo-Vista-Controlador:

- **Modelo:** entidades de turno activo, posición en cola y evento de historial.
- **Vista:** pantallas de estado del turno con acciones disponibles según el estado, posición en la cola con estimación de tiempo, e historial cronológico de turnos.
- **Controlador:** recibe la solicitud del estudiante, valida su rol, invoca la lógica de consulta correspondiente y retorna la vista apropiada con el estado actualizado.

**Justificación:** Las pantallas de seguimiento presentan información de estado que cambia frecuentemente —posición en cola, acciones disponibles según el estado del turno— y deben hacerlo de forma clara e inmediata. MVC desacopla la presentación de la lógica de obtención de datos, permitiendo que la interfaz evolucione sin afectar la lógica de consulta. Esto favorece directamente el atributo de **usabilidad**: la interfaz puede iterarse para mejorar la claridad sin riesgo de romper la lógica de negocio. El controlador es además el punto único donde se valida el rol del usuario antes de invocar cualquier consulta, reforzando la **seguridad**.

---

#### Categoría de Componente y Conector (2): Publicar-Suscribir (ingesta de eventos)

Para registrar los eventos de auditoría, el módulo de Seguimiento actúa como **suscriptor** en el bus de eventos interno compartido con el módulo de Notificaciones. Los módulos productores publican eventos enriquecidos —con todos los datos necesarios para el registro, incluyendo posición en cola al momento del evento, tiempo de espera y actor involucrado— de modo que el módulo de Seguimiento sea completamente pasivo y no necesite consultar a ningún otro módulo para completar un registro.

Cada evento publicado por los módulos de negocio lleva un UUID único generado en origen. La tabla de eventos usa `INSERT ... ON CONFLICT DO NOTHING` sobre ese UUID para garantizar idempotencia: si un evento llega dos veces por un reintento del bus, el segundo se descarta silenciosamente sin duplicados en el historial.

**Justificación:** El patrón Pub/Sub para la ingesta garantiza que el módulo de Seguimiento no añada latencia al camino crítico de los módulos transaccionales. Si el módulo de Seguimiento sufre un fallo transitorio, los módulos de cola y confirmación continúan operando sin degradación. Cuando el módulo se recupera, los eventos pendientes en el bus se procesan y el historial se completa sin pérdida, cumpliendo el escenario de **disponibilidad** de 0 pérdida de historial con recuperación < 5s.

---

#### Categoría de Asignación: Multi-Tier

El módulo se despliega dentro del monolito modular:

- **Tier de API:** endpoints REST y stream SSE del dashboard, servidos por el mismo proceso Node.js.
- **Tier de Aplicación:** lógica de consulta, ingesta de eventos, cálculo de posición y generación de reportes.
- **Tier de Datos:** PostgreSQL con particionamiento mensual para eventos, Redis para contadores en tiempo real del dashboard, y vistas materializadas para estadísticas históricas.

**Justificación:** La separación del tier de datos del tier de aplicación permite optimizar la base de datos de seguimiento —índices parciales, particionamiento mensual, vistas materializadas con refresh concurrente— de forma independiente al servicio de consulta. Redis centraliza los indicadores en tiempo real (cola actual, cupos disponibles, estudiantes atendidos en el día) que el dashboard consume con latencia de lectura O(1), sin competir con las escrituras intensivas a la tabla de eventos durante el horario de comedor.

---

### Combinación de patrones

```
Multi-Tier (asignación)
  └── Capas (organización interna del módulo)
        ├── MVC (interacción con el estudiante a través de la interfaz)
        └── Pub/Sub (ingesta de eventos desde módulos transaccionales)
```

No se produce un ADR de patrones adicional para este módulo. La elección de Pub/Sub para la ingesta de eventos comparte los mismos fundamentos que el ADR del módulo de Notificaciones: ambos módulos son consumidores del mismo bus de eventos interno. La decisión de MVC para la interfaz de consulta no presenta alternativas comparables en el contexto de una aplicación web donde la presentación cambia con mayor frecuencia que la lógica de consulta.
