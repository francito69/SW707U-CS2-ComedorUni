## M6 — Reasignación de turnos

### Contexto del módulo

El módulo de **Reasignación** automatiza la detección de cupos liberados (ya sea porque un turno expiró o no se confirmó) y la asignación eficiente de estos cupos al siguiente estudiante elegible en lista de espera. Su responsabilidad es gestionar este proceso manteniendo el orden FIFO de la cola, y aplicando control de concurrencia y bloqueos transaccionales para evitar dobles asignaciones.

Este módulo debe ejecutarse en segundo plano (de manera asíncrona) para no bloquear la atención principal de la API que utilizan los estudiantes. Durante los picos de demanda —por ejemplo, cuando múltiples turnos expiran en bloque tras el tiempo límite de reserva— la concurrencia de eventos de liberación aumenta, por lo que el sistema debe soportar estos picos sin degradar la experiencia de usuario.

**Atributos de calidad prioritarios:**

| Atributo | Medida clave |
|---|---|
| Disponibilidad | El flujo de la API principal no sufre interrupciones por la reasignación. |
| Confiabilidad | 0% de dobles asignaciones o errores de secuencialidad FIFO. |
| Rendimiento | Respuesta de API inmediata; la reasignación ocurre en background (latencia asíncrona aceptable). |
| Escalabilidad | Capacidad de aumentar trabajadores para el procesamiento de la cola sin afectar módulos de origen. |

**Volumen y concurrencia esperados:** Picos de demanda específicos causados por la expiración simultánea de lotes de turnos no confirmados. Los eventos se originan independientemente de la navegación manual de un usuario final, tratándose de eventos internos del sistema.

---

### Patrones aplicables

#### Categoría de Módulo: Capas (Layered)

El módulo se organiza lógicamente mediante capas para separar el ciclo de de reasignación:
- **Capa de Control/Consumo:** Escucha y recibe eventos asíncronos de liberación de cupo provenientes del broker.
- **Capa de Lógica de Negocio:** Lógica de validación, selección del siguiente candidato (FIFO) y control de bloqueo para reservar el turno sin colisiones.
- **Capa de Notificación/Salida:** Delega la comunicación del cambio (informar al usuario reasignado) generando un nuevo evento hacia el módulo de notificaciones.
- **Capa de Acceso a Datos:** Ejecución de consultas transaccionales con bloqueo excluyente relacional, preservando la integridad del estado.

**Justificación:** Permite aislar la validación y reserva del turno de la tecnología del oyente (RabbitMQ u otra) y de la base de datos (PostgreSQL), mejorando la mantenibilidad, escalonamiento y asegurando la integridad transaccional requerida.

#### Categoría de Asignación: Multi-Tier

El módulo de reasignación se despliega como parte del stack distribuido pero especializado como worker, separado de la atención HTTP de la API pública en términos lógicos, con bases de datos transaccionales separadas de la capa de aplicación.

**Justificación:** Garantiza que los picos de reasignación no saturen la capa web/API, proporcionando estabilidad operativa, alineado fuertemente con los atributos de rendimiento y escalabilidad (es posible escalar los trabajadores/consumers sin escalar los web servers HTTP).

#### Categoría de Componente y Conector: Publicar-Suscribir (Pub/Sub)

*(Ver ADR a continuación para el análisis detallado de alternativas)*

Un productor (módulo de Turnos) publica eventos tipo \CupoLiberado\ a un broker de mensajería (ej. RabbitMQ), mientras que un consumidor en el módulo de Reasignación se suscribe, procesa el evento y asigna el turno a un estudiante en espera.

---

### ADR: Patrón de comunicación para el módulo de Reasignación

**Categoría de decisión:** Modelo de Coordinación (elección de patrón de Componente y Conector)

**Contexto:** 
Cuando un turno expira, la disponibilidad de la API para el resto de los estudiantes no debe verse afectada por el procesamiento subsecuente de buscar en la base de datos, validar, asignar y disparar notificaciones.

**Alternativas:**
1. **Cliente-Servidor síncrono (REST):** El controlador HTTP de expiración libera el turno y, en ese mismo hilo, llama a reasignar invocando directamente las funciones/endpoints para encontrar y transferir al candidato, todo en el mismo request.
- Simple de implementar al inicio.
- Acopla temporalmente el proceso de expiración con la reasignación, afectando el tiempo de respuesta.
- Podría bloquear conexiones bajo alta carga y generar timeout.
2. **Procesamiento totalmente en memoria local:** Se manejan estructuras concurrentes locales para aplicar la reasignación en hilos asíncronos.
- Baja latencia.
- Inconsistencia frente a caídas del proceso (pérdida de la memoria de las reasignaciones pendientes).
- Impide el crecimiento horizontal seguro (múltiples pods causarían colisiones o perderían sincronía).
3. **Publicar-Suscribir asíncrono sobre un broker (RabbitMQ):** El módulo de origen emite el evento y la reasignación es manejada a su ritmo por suscriptores dedicados.
- Desacople que protege la API.
- Reintentos confiables y mitigación de fallos transitorios en caso de desconexiones parciales.
- Requiere infraestructura adicional y monitoreo de colas.

**Criterios de Elección:**
- **Disponibilidad:** Liberación y reasignación no afectan el hilo principal.
- **Rendimiento percibido:** Respuestas inmediatas al liberar o expirar. 
- **Escalabilidad:** Separar consumidores de productores.
- **Confiabilidad:** Pérdida cero de eventos operando bajo transaccionalidad asíncrona.

**Decisión:** 
Se adopta el patrón **Publicar-Suscribir** (Pub/Sub asociado a RabbitMQ o sistema de colas).

**Sustento:** 
El patrón desacopla temporal y lógicamente el evento de liberación de su procesamiento exhaustivo minimizando fallas transitorias de impacto sobre la API de los estudiantes. Esto es esencial para tolerar la concurrencia generada en bloque. Asimismo, permite delimitar la reasignación automática protegiéndola con consumidores especializados, cumpliendo con la prioridad de **Rendimiento** en tiempo de respuesta inicial y ofreciendo control preciso sobre las métricas de fallos insalvables mediante DLQ (Dead Letter Queues), sosteniendo la **Confiabilidad**.

---

### Combinación de patrones

```
Multi-Tier (asignación global distribuida)
  ├── Publicar-Suscribir (comunicación y gatillado asíncrono)
  └── Capas (organización del ciclo de reasignar y guardar transacciones)
```

## M7 — Configuración

### Contexto del módulo

El módulo de **Configuración** centraliza los parámetros críticos de la plataforma: tiempos máximos de tolerancia por turno, bloques horarios disponibles, factor de capacidad pico y reglas para las ventanas de reserva. Al ser estos datos los que rigen el comportamiento de otros módulos, modificaciones mal gestionadas, concurrentes o dispersas pueden comprometer la operación del sistema completo.

Su patrón de carga está altamente sesgado: las re-escrituras o modificaciones (hechas por administradores) son muy escasas (unas cuantas por semana/día), pero su tasa de lectura concurrente es extrema, en cada transacción de los demás módulos. Por esta razón, el modelo necesita cachear respuestas seguras pero poder invalidarlas coordinadamente tras la actuación del administrador autorizado.

**Atributos de calidad prioritarios:**

| Atributo | Medida clave |
|---|---|
| Rendimiento | Alta velocidad en las lecturas inter-módulos (baja latencia); soporte masivo de consultas de caché. |
| Seguridad | Exclusividad total a perfiles Administradores autorizados y trazabilidad en bitácoras. |
| Mantenibilidad | Centralización lógica (sola fuente de verdad) y validación estructurada de parámetros. |
| Confiabilidad | Consistencia tras cambios de configuración, sin generar estados superpuestos e inválidos. |

**Volumen y concurrencia esperados:** Lecturas concurrentes ultra rápidas, requeridas en todo momento del uso de la aplicación. Escrituras manuales controladas con concurrencia nula o mínima.

---

### Patrones aplicables

#### Categoría de Asignación: Multi-Tier

El módulo, aunque concentrado internamente, participa activamente como un tier específico de lógica administrativa desde su presentación y en el almacenamiento de su fuente de la verdad en BD (para trazabilidad). 

**Justificación:** Brinda el plano protector para evitar que estudiantes puedan llegar a la API web con permisos. La arquitectura protege las bases de configuración situándolas tras el blindaje interno de los firewalls y APIs privadas.

#### Categoría de Módulo: Capas (Layered)

Se organiza en capas claras: 
- **Presentación:** API REST de uso estricto para administradores con fuerte escrutinio de permisos.
- **Lógica de Validación y Vigencia:** Capa responsable de evaluar que la configuración a aplicarse sea coherente antes de integrarse globalmente, previniendo reglas en pánico. 
- **Persistencia:** Almacenamiento histórico de vigencias e historial detallado, y manejo seguro de la consistencia.

**Justificación:** El aislamiento es necesario para no combinar la seguridad y administración con la mera entrega de configuraciones hacia el resto de los módulos. Refuerza mantenibilidad y previene inyecciones o desorden normativo.

#### Categoría de Componente y Conector: Cliente-Servidor (Lectura) + Publicar-Suscribir (Eventos de Notificación Caché)

*(Ver ADR a continuación)*

El flujo externo lo visualizan los administradores a través de Cliente-Servidor (API REST Clásica). Internamente, la distribución a los micro-cachés se hace informando un evento de actualización en canales de Publicar-Suscribir.

---

### ADR: Patrón de diseño combinado para el módulo de Configuración

**Categoría de decisión:** Módulo + Componente y Conector + Asignación

**Contexto:** 
Dado que otros módulos (como el de Turnos o la Cola Virtual) dependen de las variables estipuladas en el Módulo M7, dichas lecturas son frecuentes. Cuando el administrador efectúa un ajuste, debe hacerse efectivo inmediatamente en las operativas de creación a futuro, pero de forma consistente y en todo subsistema.

**Alternativas:**
1. **Configuración distribuida e individualista.** Cada módulo almacena en sus archivos o registros de BD sus parámetros.
- Total aislamiento y latencia cero intermódulos.
- Imposibilita la auditoría global. 
- En actualizaciones, la inconsistencia es brutal y altamente riesgosa.
2. **Cliente-Servidor central y directo (REST) sin Caché integrado al Módulo.** Toda validación pide la regla por HTTP a Configuración cada vez.
- Seguridad garantizada y *single source of truth* real.
- Latencia incrementada penalizando el sistema a niveles inaceptables durante uso rutinario de módulos satelitales.
3. **Módulo con roles en Capas + API (Cliente-Servidor) y Notificación Pub/Sub para invalidar cachés.** Se ofrece el API administrativa REST blindada; frente al cambio, el módulo graba como fuente de la verdad y disemina por Pub/Sub un mensaje de invalidación o nueva configuración global para recarga en otros módulos.
- Centralización impecable y auditabilidad.
- Latencia en lecturas por usar microcachés funcionales de altísimo performance. 
- La propagación del cambio está garantizada mediante control en paralelo ecosistema asíncrono.

**Criterios de Elección:**
- **Seguridad:** Aislamiento para escritura de parámetros.
- **Rendimiento:** Lecturas inter-módulo sin castigos de latencia.
- **Consistencia controlada:** No deben haber lapsos prolongados de dos configuraciones distintas operando concurrentemente.

**Decisión:** 
Se adopta un marco de **Capas** para validaciones internas, **Cliente-Servidor** para operaciones manuales con administradores y un puente **Publicar-Suscribir** para notificar y propagar las variaciones hacia los demás módulos para propiciar la purga e invalidación del caché de lectura.

**Sustento:** 
Las lecturas masivas y recurrentes chocan contra los principios de recarga e integridad global de la aplicación. Para conciliar ambos, emplear módulos de Capas asegura correctos versionamientos seguros (historial) controlados por la administración vía patrón Cliente-Servidor (que ofrece control total y predictibilidad REST); finalmente se contrarresta la alta latencia con Pub/Sub asíncrono para inhabilitar registros viejos cacheados e impartir al vuelo nuevos valores. Esto preserva de las peores secuelas al atributo vital de Rendimiento sin arriesgar Consistencia o Mantenibilidad de Configuración.

---

### Combinación de patrones

```
Multi-Tier (desagregación de red y base de datos auditable persistente)
  ├── Capas (Separación de roles de interfaz web, validación lógica y control de histórico DB)
  ├── Cliente-Servidor (Interacciones vía API con administradores)
  └── Publicar-Suscribir (Eventos hacia el exterior para mantener limpias y frescas a las memorias caché satelitales)
```
