# 17.1. Módulo 1 / Integrante 1

**Módulos cubiertos:** M1 – Autenticación · M4 – Notificaciones · M5 – Seguimiento

Esta sección documenta los escenarios de calidad que el prototipo aborda **en el código** (no solo en el diseño), con trazabilidad completa: escenario → táctica implementada → estructura C4 → código que la materializa → forma de verificarlo. Se priorizan los escenarios que motivaron las tácticas de la [Sección 2](../../14/14.1/14.1.md).

---

## Escenarios abordados en el código

| # | Escenario de calidad | Atributo | Táctica / solución implementada | Estructura C4 que lo soporta | Evidencia en el código | Forma de verificarlo |
|---|---|---|---|---|---|---|
| 1 | Una petición usa un `sid` inválido o expirado | Seguridad | Validación de sesión antes de ejecutar lógica; `401` | API Backend → Gestor de Sesiones (Componentes M1, [15.1](../../15/15.1/15.1.md)) | [`auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) → `get_session` en `verify-biometric`/`me`/`logout` | `curl ".../me?sid=inexistente"` → `401` |
| 2 | Un impostor presenta una selfie que no es del estudiante | Seguridad | Verificación biométrica (umbral de distancia); identidad no verificada | Servicio de Biometría (M1) | [`auth/biometric.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/biometric.py) → `compare_faces` | `POST /verify-biometric` con foto distinta → `verified: false` |
| 3 | Un dispositivo nuevo inicia sesión con las mismas credenciales que otro | Seguridad | Detección de conflicto: la sesión previa **no** se expulsa automáticamente; se marca `session_conflict` y la decisión queda al usuario | Gestor de Sesiones → Redis | [`auth/redis_store.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/redis_store.py) → `create_session` (conflicto por `device_id`) | `parse-data` desde otro dispositivo → `session_conflict: true`; la sesión vieja sigue viva |
| 4 | Una sesión queda abandonada y no debe vivir indefinidamente | Seguridad / Continuidad | Datos auxiliares con **TTL** (8 h) en Redis; expiración automática | Redis Sesiones (despliegue, [15.1](../../15/15.1/15.1.md)) | [`auth/redis_store.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/redis_store.py) → `SESSION_TTL`, `setex` | `redis-cli TTL session:<sid>` → > 0, ≤ 28800 |
| 5 | La foto institucional no debe quedar almacenada de forma permanente | Seguridad / Privacidad | Minimización: la foto vive solo en la sesión Redis, no en PostgreSQL | Gestor de Sesiones → Redis (no DB) | [`auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) → `upsert_estudiante` no recibe la foto; va a `create_session` | Inspeccionar `estudiantes`: no hay columna/valor de foto |
| 6 | El estudiante cierra sesión y su `sid` no debe seguir válido | Seguridad | Revocación explícita: `logout` borra la sesión (y el índice de usuario) | Gestor de Sesiones → Redis | [`auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) → `logout` / [`redis_store.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/redis_store.py) → `delete_session` | `POST /logout`; luego `/me?sid=<sid>` → `401` |
| 7 | No hay foto de referencia en la sesión al verificar biometría | Continuidad / Manejo de errores | Chequeo previo y `404` controlado (no se invoca el modelo sin insumos) | `auth.router` → Gestor de Sesiones | [`auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) → `verify-biometric` (`if not foto_ref`) | `verify-biometric` con sesión sin foto → `404` |
| 8 | El modelo biométrico falla en tiempo de ejecución | Continuidad / Manejo de errores | Try/except que traduce el fallo en `500` controlado (sin exponer traceback) | Servicio de Biometría | [`auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) → `try/except` sobre `compare_faces` | Forzar una imagen inválida en base64 → `500` con mensaje genérico |
| 9 | El encolamiento no debe fallar por falta del registro del estudiante | Integridad referencial | El login persiste/actualiza al estudiante (upsert) antes de crear la sesión | `auth.router` → PostgreSQL (`estudiantes`) | [`auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) → `upsert_estudiante` | Tras `parse-data`, existe la fila en `estudiantes` (FK de `turnos` satisfecha) |
| 10 | El historial de asistencia no debe duplicarse | Integridad / Auditoría | Constraint `UNIQUE (estudiante_id, turno_dia_id)` en el historial | Consumer M5 → PostgreSQL | [`001_init.sql`](../../s111-actividad-bosquejo-implementacion/backend/migrations/001_init.sql) → `historial_asistencia` UNIQUE | Reprocesar `turno.atendido` no crea dos filas para el mismo turno |
| 11 | Un mensaje de notificación falla o llega malformado | Continuidad | Manejo de excepciones en el consumer + descarte de payload sin `push_token`/`evento` | Consumer M4 (Componentes M4/M5) | [`notifications/consumer.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/notifications/consumer.py) → `_handle` (try/except, guard) | Publicar evento sin `push_token`: se descarta y el consumer sigue vivo |
| 12 | Un evento de seguimiento llega incompleto | Continuidad | Validación de campos obligatorios antes de persistir | Consumer M5 | [`tracking/consumer.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/tracking/consumer.py) → `if not all([est_id, td_id, numero_turno])` | Publicar evento sin `estudiante_id`: se descarta sin error |
| 13 | Al tomar la sesión en un dispositivo nuevo, el anterior debe cerrarse al instante desde cualquier pantalla | Seguridad / Continuidad | Conexión de sesión permanente por dispositivo (WS indexado por `sid`) + revocación push en tiempo real | WS de sesión `/session/ws/{sid}` → Gestor de Sesiones ([15.1](../../15/15.1/15.1.md)) | [`session_manager.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/session_manager.py) → `revoke`; [`auth/router.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/router.py) → `/session/takeover`, `/session/ws/{sid}`; [`UserContext.tsx`](../../s111-actividad-bosquejo-implementacion/frontend/src/constants/UserContext.tsx) | 2 dispositivos + "Continuar aquí": el 1.º recibe `session_revoked` y vuelve al login |
| 14 | El mismo dispositivo re-inicia sesión: no debe pedir decisión | Usabilidad | `device_id` persistido: una sesión previa del mismo dispositivo no cuenta como conflicto | Gestor de Sesiones → Redis | [`auth/redis_store.py`](../../s111-actividad-bosquejo-implementacion/backend/src/modules/auth/redis_store.py) → `create_session` (compara `device_id`) | Re-login en el mismo dispositivo → `session_conflict: false` (sin modal) |

## Detalle por escenario

### Escenarios 1, 4–6 — Seguridad de sesión y biometría (M1)

```python
# auth/router.py (extracto)
session = get_session(data.sid)
if not session:
    raise HTTPException(status_code=401, detail="Sesión inválida o expirada")

# auth/redis_store.py (extracto)
SESSION_TTL = 8 * 3600
r.setex(f"session:{sid}", SESSION_TTL, payload)   # TTL automatico

def delete_session(sid):                     # revocacion en logout
    ...
    r.delete(f"session:{sid}")
```

**Verificación (backend levantado, ver [16.1](../../16/16.1/16.1.md)):**
```bash
curl -s -o /dev/null -w "%{http_code}\n" "http://localhost:8000/me?sid=inexistente"   # 401
docker exec -it comedor-redis redis-cli TTL session:<sid>                              # > 0
# logout y reintento
curl -X POST http://localhost:8000/logout -H "Content-Type: application/json" -d '{"sid":"<sid>"}'
curl -s -o /dev/null -w "%{http_code}\n" "http://localhost:8000/me?sid=<sid>"          # 401
```

### Escenarios 3, 13–14 — Sesión multi-dispositivo (M1)

El login **no** expulsa la sesión previa automáticamente: detecta conflicto por `device_id` y difiere la decisión. Cuando el usuario elige "Continuar aquí", `takeover_session` deja activa la nueva y `session_manager.revoke` cierra a la vieja en tiempo real por su WebSocket de sesión.

```python
# auth/redis_store.py — create_session (extracto)
old_sid = r.get(f"user_session:{codigo}")
conflicto = bool(old_sid and old_sid != sid and r.exists(f"session:{old_sid}")
                 and json.loads(r.get(f"session:{old_sid}")).get("device_id") != device_id)
r.setex(f"session:{sid}", SESSION_TTL, payload)
if not conflicto:
    r.setex(f"user_session:{codigo}", SESSION_TTL, sid)   # sin conflicto: activa
    return None
return old_sid                                            # conflicto: decide el usuario

# auth/session_manager.py — revoke (extracto)
await ws.send_json({"type": "session_revoked", "mensaje": "..."})
await ws.close(code=4002)
```

**Verificación (2 dispositivos):** inicia sesión en A; luego en B con la misma cuenta → tras la biometría, B muestra el modal. Al pulsar "Continuar aquí", A recibe `session_revoked` por `/session/ws/{sid}` y vuelve al login al instante; `GET /me?sid=<sidA>` → `401`.

### Escenarios 11–12 — Resiliencia de consumers (M4/M5)

Cada `_handle` envuelve el procesamiento en `try/except` y descarta mensajes incompletos, evitando que un mensaje malformado tumbe el consumer (aislamiento de fallos / bulkhead).

```python
# notifications/consumer.py (extracto)
async with message.process():
    try:
        ...
        if not push_token or not evento:
            return                          # descarta malformado
        await send_push(...)
    except Exception as e:
        print(f"[M4] Error procesando mensaje: {e}")   # el consumer sigue vivo

# tracking/consumer.py (extracto)
if not all([est_id, td_id, numero_turno]):
    return                                  # descarta evento incompleto
```

**Verificación:** publicar en RabbitMQ (`http://localhost:15672`, guest/guest) un mensaje sin `push_token` en `m4.notificaciones`; el log muestra el descarte y el consumer continúa procesando los siguientes.
